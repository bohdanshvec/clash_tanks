# AGENTS.md

## 1. Проект

Учебный проект — браузерная пошаговая танковая карточная стратегия,
вдохновлённая WoT: Generals.

Проект не является копией оригинальной игры. Планируется использовать
собственные названия, карты, изображения и игровые материалы.

Основной стек:

- Ruby 3.4.10
- RubyGems 3.6.9
- Rails 8.1.3.1
- RVM 1.29.12
- Ubuntu 22.04
- Hotwire
- Stimulus
- Turbo
- PostgreSQL 17.x — целевая версия нового проекта
- PostgreSQL 12 и 14 в системе не изменять и не удалять
- PostgreSQL 17 установлен на порту 5434

Проект:

clash_tanks

Локальный запуск:

bin/dev


## 2. Основная идея игры

Игрок управляет армией на игровом поле, использует карты,
перемещает подразделения, атакует противника и выполняет игровые действия
по правилам пошаговой стратегии.

Основная игровая сущность — КАРТА.

Карта может иметь разное назначение.

Основные типы карт:

1. Техника
   - танк или другое боевое подразделение;
   - имеет характеристики;
   - может находиться на игровом поле;
   - может перемещаться и атаковать.

2. Приказ
   - игровое действие или эффект;
   - может изменять состояние игры согласно правилам;
   - может воздействовать на технику, штаб или другие игровые объекты.

3. Взвод
   - вспомогательное подразделение;
   - может усиливать штаб;
   - например, добавлять огневую мощь или HP;
   - конкретные механики будут определены позднее.

Каждая карта в будущем будет иметь свой уровень (вес).

Вес карты будет использоваться для формирования колод и балансировки
матчей. Планируется, что в бою будут участвовать колоды с приблизительно
одинаковым суммарным весом.

На раннем этапе конкретная система расчёта веса ещё не реализуется.
Первые карты и первые колоды будут создаваться с приблизительно
одинаковым весом.

Система должна позволять добавлять новые типы карт без
переписывания игрового движка.

Игра разрабатывается постепенно — сначала минимальная рабочая версия,
затем дополнительные игровые механики.


## 3. Главный архитектурный принцип

Игровой движок Rails не должен зависеть от конкретного источника
решений игрока.

Источник решения должен быть абстрагирован.

Возможные источники:

1. Человек-игрок.
2. Локальная AI-модель.
3. Внешняя AI-модель через API.
4. В дальнейшем — другие варианты.

Общая схема:

Game
  ↓
Decision Provider
  ↓
Action
  ↓
Game Engine
  ↓
проверка правил
  ↓
изменение состояния игры


Rails является главным арбитром игры.

AI не имеет права непосредственно изменять состояние игры.

AI только предлагает Action.

Rails проверяет предложенное действие и только после успешной проверки
применяет его.


## 4. Game Engine

Game Engine является центральным компонентом игры.

Именно Game Engine отвечает за:

- правила игры;
- проверку допустимости действий;
- порядок ходов;
- перемещение;
- атаки;
- расчёт урона;
- использование карт;
- изменение ресурсов;
- изменение состояния подразделений;
- победу и поражение;
- другие игровые механики.

Контроллеры Rails не должны содержать основную игровую логику.

Stimulus/JavaScript не является источником истины игровых правил.

Браузер может отображать доступные действия и отправлять их
на сервер, но окончательное решение о допустимости действия
принадлежит Game Engine.


### Архитектура Engine

`GameEngine::Engine` является координатором выполнения действий.

Engine не должен превращаться в большой класс, содержащий реализацию
всех игровых действий.

Конкретная игровая логика действий выносится в отдельные классы.

Предварительная структура:

GameEngine::Engine
    ↓
Action
    ↓
конкретная реализация действия

Например:

- Move
- Attack
- PlayCard
- EndTurn

Конкретные классы действий могут находиться в:

app/services/game_engine/actions/

или в другой структуре, выбранной при реализации.

Engine отвечает за общий процесс:

1. получает GameState;
2. получает Action;
3. проверяет общие условия;
4. определяет обработчик конкретного Action;
5. передаёт выполнение соответствующему классу;
6. получает Result;
7. возвращает Result вызывающему коду.

Таким образом, добавление нового игрового действия не должно требовать
переписывания большого `GameEngine::Engine`.


## 5. Game State

Текущее состояние партии должно быть представлено отдельным
понятием GameState.

GameState не должен быть привязан непосредственно к HTTP-запросу.

Game Engine работает с GameState.

Состояние активной партии хранится в `Game.state` в PostgreSQL
в формате JSONB.

Не следует записывать в PostgreSQL каждое промежуточное изменение
состояния отдельно, если это не требуется архитектурой игры.


### Минимальная структура GameState

На текущем этапе GameState содержит:

- `turn_number` — номер хода;
- `current_player_id` — игрок, чей сейчас ход;
- `players` — состояние участников;
- `field` — игровое поле.

Пример:

{
  "turn_number": 1,
  "current_player_id": 42,
  "players": {
    "42": {
      "hand": [],
      "resources": 0,
      "remaining_time": null
    },
    "57": {
      "hand": [],
      "resources": 0,
      "remaining_time": null
    }
  },
  "field": [
    [null, null, null, null, {"type": "headquarters", "player_id": 57}],
    [null, null, null, null, null],
    [{"type": "headquarters", "player_id": 42}, null, null, null, null]
  ]
}


### Игровое поле

Поле имеет размер:

- 3 строки;
- 5 клеток.

То есть:

3 × 5 = 15 клеток.

Координаты:

- строки: `0..2`;
- столбцы: `0..4`.

В поле всегда находятся два штаба:

- штаб одного игрока — в нижней левой клетке;
- штаб другого игрока — в верхней правой клетке.

Клетки поля могут содержать игровые объекты.

На текущем этапе реализована минимальная работа с полем:

- создание пустого поля;
- создание начального поля со штабами;
- проверка координат;
- получение объекта по координатам;
- размещение объекта;
- перемещение объекта;
- проверка занятости клетки;
- запрет перемещения штаба;
- запрет перемещения объекта на клетку штаба.

### Неизменяемость исходного поля

Операции изменения поля не должны изменять переданное исходное поле.

Например:

старое поле
    ↓
операция
    ↓
новое поле

Исходное поле остаётся неизменным.

Это позволяет Game Engine создавать новое состояние игры
без скрытого изменения предыдущего состояния.

В частности, `GameEngine::GameState.place_object` и
`GameEngine::GameState.move_object` создают новое поле.

### Перемещение

Одно перемещение техники на одну клетку является одним
отдельным игровым действием.

При этом один ход игрока может содержать множество действий.

Например, в течение одного хода игрок потенциально может:

- разыграть несколько карт;
- выполнить несколько перемещений техники;
- выполнить другие разрешённые действия.

Запас хода конкретной техники может позволять ей выполнить
несколько отдельных перемещений за один ход.

Например:

movement = 2

означает возможность выполнить:

1. первое перемещение на одну клетку;
2. второе перемещение на одну клетку.

Каждое такое перемещение является отдельным Action.

Количество перемещений и другие ограничения будут реализованы
в правилах техники и Game Engine на соответствующих этапах.

### Направления перемещения

Правила игрового поля не определяют, какие направления разрешены
конкретной технике.

Разные типы техники могут иметь разные возможности перемещения.

Например:

- одна техника может перемещаться только по горизонтали и вертикали;
- другая техника может перемещаться также по диагонали;
- другие варианты могут быть добавлены позднее.

Поэтому диагональное перемещение не запрещается на уровне GameState.

Возможность конкретного перемещения должна проверяться правилами
соответствующей техники и Game Engine.

### Штаб

Штаб:

- является объектом игрового поля;
- не может быть перемещён;
- занимает свою клетку;
- не может быть заменён другим объектом;
- клетка штаба не является допустимой клеткой назначения
  для перемещения техники.

Конкретные правила взаимодействия с вражеским штабом будут определены
на последующих этапах.


### Информация о картах

Состояние руки игрока является частью GameState.

При передаче состояния конкретному игроку или AI нельзя раскрывать
ему скрытую информацию противника.

В частности:

- игрок должен видеть свои карты;
- игрок не должен видеть карты противника;
- AI не должен получать карты руки противника;
- при необходимости GameState должен преобразовываться в
  представление, предназначенное конкретному участнику.

Полное внутреннее состояние партии может храниться на сервере,
но Decision Provider должен получать только ту информацию,
которую имеет право знать соответствующий игрок или AI.


## 6. Game / Player / GamePlayer

Основные модели:

### Game

Конкретная игровая партия.

На текущем этапе содержит:

- `id`;
- `created_at`;
- `updated_at`;
- `status`;
- `state`.

Статус партии:

- `waiting` — партия ожидает второго участника;
- `started` — партия началась;
- `finished` — партия завершена.

Новая игра создаётся со статусом `waiting`.

### Player

Участник игры.

Player может представлять:

- человека;
- AI.

Игра не должна различать Human Player и AI Player на уровне
основных игровых правил.

Оба используют одинаковый механизм действий.

### GamePlayer

Связь участника с конкретной игрой.

Одна игра может иметь двух участников.

Один Player может участвовать в нескольких играх.

GamePlayer является отдельной моделью связи:

Player
  ↓
GamePlayer
  ↓
Game

Текущие связи моделей:

Player
  has_many :game_players
  has_many :games, through: :game_players

Game
  has_many :game_players
  has_many :players, through: :game_players

GamePlayer
  belongs_to :game
  belongs_to :player


## 7. Создание и начало игры

Игра не должна сразу переходить в состояние `started`.

Сценарий:

### Игра с человеком

1. Первый игрок создаёт игру.
2. Игра получает статус `waiting`.
3. Второй игрок присоединяется к этой игре.
4. После появления двух участников игра переходит в `started`.
5. Создаётся начальный GameState.
6. Определяется первый игрок.
7. Начинается первый ход.

### Игра с AI

1. Игрок создаёт игру.
2. Игра получает статус `waiting`.
3. К игре присоединяется AI.
4. Игра переходит в `started`.
5. Создаётся начальный GameState.
6. Определяется первый игрок.
7. Начинается первый ход.

Таким образом, для Game Engine не имеет значения,
является второй участник человеком или AI.

### Ограничение количества участников

На текущем этапе одна Game рассчитана ровно на двух участников.

`GamePlayer` используется для связи обоих участников
с одной игрой.


## 8. Action

Любое игровое действие должно представляться как Action.

Примеры:

- Move
- Attack
- PlayCard
- EndTurn
- другие действия, которые будут добавляться позднее.

Action представляет намерение выполнить игровое действие.

Action не должен самостоятельно изменять GameState.

Action содержит данные, необходимые для описания действия,
например:

- тип действия;
- игрок, выполняющий действие;
- идентификатор объекта;
- координаты;
- другие параметры, необходимые конкретному действию.

Конкретная игровая логика Action должна находиться
в соответствующем обработчике действия, а не в общем классе Action.

Общая схема:

Player
  ↓
Action
  ↓
Game Engine
  ↓
validate
  ↓
конкретный Action handler
  ↓
новый GameState
  ↓
Result


Один игровой ход может содержать множество Action.

Например, один игрок в рамках одного хода может:

- разыграть несколько карт;
- выполнить несколько перемещений;
- выполнить другие разрешённые действия.

`EndTurn` завершает ход и переводит игру к следующему игроку.

При этом `EndTurn` не означает, что каждый ход обязан содержать
только одно действие.

Game Engine должен проверять:

- кто выполняет действие;
- чей сейчас ход;
- существует ли объект;
- принадлежит ли объект игроку;
- допустимо ли действие;
- хватает ли ресурсов;
- соблюдены ли остальные правила игры.

Только после успешной проверки действие применяется.


## 9. Result

Результат выполнения Action должен быть отделён от самого Action.

`Result` не содержит основную игровую логику и не изменяет
переданный GameState.

Результат должен сообщать вызывающему коду, что произошло
при попытке выполнения действия.

Result может содержать информацию о:

- успешности действия;
- новом состоянии игры;
- ошибке;
- причине отказа;
- событиях, которые произошли в результате действия.


### Важное архитектурное решение

Game Engine не изменяет переданный GameState напрямую.

При успешном выполнении действия создаётся новое состояние,
которое передаётся через Result.

Общая схема:

старый GameState
      ↓
   Action
      ↓
Game Engine
      ↓
валидация
      ↓
создание нового GameState
      ↓
Result
      ↓
новый GameState


Это позволяет сделать выполнение действий более предсказуемым
и не допускать скрытого изменения исходного состояния.

Result не должен самостоятельно применять игровые правила
или изменять GameState.


## 10. AI-противник

Первоначально планируется использовать:

Qwen3 1.7B

Запуск:

Ollama + Qwen3 1.7B

Модель должна работать локально на компьютере разработчика.

Ориентир по времени ответа AI:

до ~10 секунд.

В дальнейшем модель можно заменить без изменения игрового движка.


## 11. Взаимодействие с AI

AI получает только информацию, необходимую для принятия решения
и разрешённую конкретному участнику.

AI может получать:

- необходимые правила игры;
- доступное ему состояние игры;
- состояние игрового поля;
- собственные карты;
- собственные ресурсы;
- историю предыдущих ходов, если она необходима;
- список допустимых действий.

AI не должен получать скрытую информацию противника.

В частности, AI не должен получать:

- карты руки противника;
- скрытые данные противника;
- другие данные, которые по правилам игры неизвестны участнику.

AI возвращает выбранное действие.

Предпочтительный формат ответа — структурированный ответ.

Например:

{
  "action_id": 17
}

или другой согласованный формат Action.


AI не должен самостоятельно изменять:

- здоровье подразделений;
- положение объектов;
- ресурсы;
- состояние поля;
- карты;
- другие данные игры.

Все изменения выполняются Game Engine.


## 12. Допустимые действия

Game Engine должен уметь определить список действий,
которые допустимы в текущем состоянии игры.

Decision Provider получает список действий,
доступных соответствующему участнику.

AI выбирает одно из допустимых действий.

Это позволяет отделить:

- принятие стратегического решения;
- проверку правил игры.

Даже если AI вернул неправильное или недопустимое действие,
Game Engine должен его отклонить.


## 13. Decision Provider

Источник решений должен быть отделён от Game Engine.

Предварительная концепция:

Decision Provider
    ├── Human
    ├── Ollama
    ├── External API
    └── другие реализации в будущем

Game Engine не должен напрямую зависеть от:

- Ollama;
- Qwen;
- конкретной AI-модели;
- внешнего API.

Game Engine работает только с Action.


## 14. AI Provider

AI Provider отвечает только за получение решения от AI.

Предварительная структура может быть следующей:

app/services/ai/

    decision_provider.rb
    ollama/
        client.rb
        decision_provider.rb

Конкретная структура может измениться во время разработки.

AI Provider не имеет права напрямую изменять GameState.

## 16. Карты

Карта является общей игровой сущностью.

Не следует архитектурно разделять понятия:

"Карта" и "Танк"

как две независимые игровые сущности верхнего уровня.

Танк является одним из типов карты.

Предварительная концепция:

Card
  ├── Technique
  ├── Order
  └── Platoon

Каждая карта в будущем будет иметь уровень (вес).

Вес карты предназначен для балансировки силы колоды.

Планируется, что перед началом боя игроки будут использовать
колоды с приблизительно одинаковым суммарным весом.

На раннем этапе система веса не реализуется.

Первые карты и первые колоды будут иметь приблизительно одинаковый вес,
чтобы обеспечить базовый баланс без отдельной механики подбора по весу.

Названия конкретных классов, наследования или другого способа
реализации будут определены при создании карточной системы.

На ранних этапах не следует преждевременно усложнять модель карт.


## 17. Игровое поле

Игровое поле является частью состояния игры.

Размер поля:

3 строки × 5 клеток.

В поле всегда присутствуют два штаба:

- нижний левый угол;
- верхний правый угол.

На поле могут находиться игровые объекты,
в первую очередь техника.

Игровое поле должно быть независимо от интерфейса.

Stimulus только отображает состояние поля и отправляет действия.

Правила размещения и перемещения объектов находятся
в Game Engine.

### Текущее состояние реализации поля

Реализовано:

- поле размером 3 × 5;
- координаты строк `0..2`;
- координаты столбцов `0..4`;
- два штаба в начальном состоянии;
- проверка корректности координат;
- получение объекта по координатам;
- размещение объекта в свободной клетке;
- запрет размещения в занятую клетку;
- перемещение объекта;
- запрет перемещения штаба;
- запрет перемещения на занятую клетку;
- запрет перемещения на клетку штаба;
- сохранение исходного поля при операциях;
- создание нового поля после изменения.

### Важное ограничение ответственности

`GameState` отвечает за структуру поля и базовую целостность
операций с клетками.

`GameState` не определяет, может ли конкретная техника перемещаться
в определённом направлении.

Полноценные правила действия `Move` будут реализованы позднее
на этапе 8.

В частности, на этапе 8 необходимо будет проверять:

- принадлежность техники игроку;
- наличие техники на исходной клетке;
- допустимость направления;
- расстояние перемещения;
- запас хода;
- остальные правила перемещения.

### Направления движения техники

Разные типы техники могут иметь разные правила движения.

Некоторые типы техники могут перемещаться:

- горизонтально;
- вертикально.

Некоторые типы техники могут также перемещаться:

- по диагонали.

Поэтому диагональное перемещение не запрещается самим игровым полем.

Правила конкретной техники будут определяться её характеристиками
и проверяться Game Engine.

### Количество действий за ход

Один ход игрока может содержать множество действий.

Например:

- разыграть несколько карт;
- переместить технику несколько раз;
- выполнить другие разрешённые действия.

Одно перемещение техники на одну клетку является одним Action.

Если техника имеет запас хода, равный 2, это означает,
что она потенциально может выполнить два отдельных действия
перемещения за один ход.

Запас хода и ограничения количества действий относятся
к характеристикам техники и игровым правилам, а не к базовой
структуре `GameState`.

### Штаб

Штаб:

- находится в фиксированной стартовой клетке;
- не может быть перемещён;
- занимает клетку;
- не может быть заменён другим объектом;
- не является допустимой клеткой назначения для перемещения техники.

Конкретные правила атаки и взаимодействия со штабом будут определены
на последующих этапах.


## 18. Хранение данных

PostgreSQL используется для:

- игроков;
- партий;
- связей игроков с партиями;
- карт и их постоянных характеристик;
- результатов игр;
- при необходимости истории ходов;
- состояния активных партий.

Состояние активной игры хранится в `Game.state` как JSONB.

Быстро изменяющееся игровое состояние не следует хранить
в cookies.

Не использовать cookies как основной механизм хранения
состояния игры.

Не использовать PostgreSQL для записи каждого промежуточного
изменения состояния, если это не требуется архитектурой игры.

- проверяет, что клетка свободна;
- создаёт новое поле;
- не изменяет исходное поле.

`move_object`:

- проверяет исходные координаты;
- проверяет координаты назначения;
- проверяет наличие объекта;
- запрещает перемещение штаба;
- проверяет, что клетка назначения свободна;
- запрещает перемещение на клетку штаба;
- создаёт новое поле;
- не изменяет исходное поле.

Полноценное действие `Move` пока не реализовано.

Оно относится к этапу 8.

### 23.5. Правила перемещения

Зафиксировано:

- одно перемещение на одну клетку является одним Action;
- один ход игрока может содержать множество Action;
- техника может выполнить несколько отдельных перемещений
  в рамках одного хода, если позволяет её запас хода;
- запас хода является характеристикой техники;
- некоторые типы техники могут перемещаться по диагонали;
- другие типы техники могут иметь более ограниченные направления;
- правила конкретной техники не должны находиться непосредственно
  в `GameState`;
- клетка штаба недоступна для перемещения;
- штаб не может быть перемещён.

Полные правила перемещения будут реализованы вместе с техникой
и `Move Action` на соответствующих этапах.


### 23.6. Жизненный цикл Game

Проверены статусы:

    waiting
    started
    finished

Проверены переходы:

    waiting → started
    started → finished

Также проверено, что:

- новая Game имеет статус `waiting`;
- `waiting?` возвращает `true`;
- `started?` возвращает `true` после `started!`;
- `finished?` возвращает `true` после `finished!`.


### 23.7. GameEngine::StartGame

Создан и проверен сервис:

`GameEngine::StartGame`

Он:

1. получает Game;
2. получает участников через GamePlayer;
3. проверяет наличие ровно двух участников;
4. создаёт начальный GameState;
5. назначает первого игрока;
6. сохраняет состояние игры;
7. переводит Game из `waiting` в `started`.

Запуск игры проверен на Game с двумя участниками.


### 23.8. GameEngine::Action

Создан:

`GameEngine::Action`

Action представляет намерение выполнить игровое действие.

Action не изменяет GameState.

Он отделён от конкретной реализации игровых правил.


### 23.9. GameEngine::Result

Создан:

`GameEngine::Result`

Result отделён от Action.

Result сообщает результат выполнения действия.

Принято архитектурное решение, что Result не изменяет
переданный GameState.

При успешном выполнении действия новое состояние
создаётся отдельно и возвращается через Result.


### 23.10. GameEngine::Engine

Создан:

`GameEngine::Engine`

Engine является координатором выполнения действий.

Engine:

- принимает GameState;
- принимает Action;
- определяет обработчик;
- передаёт действие соответствующему обработчику;
- получает Result;
- возвращает Result;
- обрабатывает неизвестный тип Action.

Engine не содержит реализацию всех игровых действий внутри себя.

Конкретные действия будут выноситься в отдельные классы.


### 23.11. Архитектура игровых действий

Принято решение не помещать `Move`, `Attack`, `PlayCard`,
`EndTurn` и другие действия непосредственно в `Engine`.

Каждое действие в будущем должно иметь собственный обработчик.

Предполагаемая структура:

app/services/game_engine/actions/

    move.rb
    attack.rb
    play_card.rb
    end_turn.rb

Конкретные файлы будут создаваться по мере реализации соответствующих
игровых механик.

Это решение принято для того, чтобы `GameEngine::Engine`
не превратился в большой класс-монстр.


### 23.12. Один ход и множество действий

Зафиксировано архитектурное правило:

Один ход игрока может содержать множество действий.

Например, игрок может в рамках одного хода:

- разыграть несколько карт;
- перемещать технику несколько раз;
- выполнять другие разрешённые действия.

`EndTurn` завершает весь ход.

Таким образом:

    Game
      ↓
    Turn
      ↓
    Action
    Action
    Action
    Action
      ↓
    EndTurn

Конкретные ограничения количества действий будут определяться
правилами соответствующих механик.
