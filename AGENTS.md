## 1. Проект

**clash_tanks** — учебный браузерный пошаговый танковый карточный стратегический проект, вдохновлённый WoT: Generals.

Проект не является копией оригинальной игры.

Основная цель проекта — изучение Ruby on Rails на примере полноценной игровой архитектуры с отделением игровой логики от интерфейса и источника решений игрока.

## 4. Главный архитектурный принцип

Игровой движок является единственным арбитром состояния игры.

Источник решения отделён от игрового движка.

Источником решения может быть:

- человек;
- локальный AI;
- внешний AI/API;
- другой Decision Provider.

Общая схема:

```
Decision Provider
       |
       | Action
       v
Game Engine
       |
       | проверка правил
       | применение действия
       v
GameState
```

- Decision Provider предлагает действие.
- Game Engine самостоятельно проверяет его допустимость и изменяет состояние игры.
- Decision Provider не имеет права самостоятельно изменять GameState.

## 5. Game Engine

Игровой движок отвечает за:

- проверку действий;
- применение действий;
- соблюдение игровых правил;
- порядок ходов;
- перемещение;
- атаки;
- расчёт урона;
- использование карт;
- изменение ресурсов;
- изменение состояния техники;
- завершение хода;
- определение победы и поражения.

Game Engine не должен зависеть от конкретного источника решений.

Он не должен знать, кто предложил действие:

- человек;
- AI;
- внешний API.

## 6. Структура Game Engine

Основные компоненты:

- `GameEngine::Action`
- `GameEngine::Result`
- `GameEngine::Engine`

### GameEngine::Action

Описывает намерение игрока.

Action:

- содержит необходимые параметры действия;
- не изменяет состояние игры;
- может быть создан человеком или AI;
- передаётся в Game Engine для проверки.

Один ход может содержать несколько последовательных Actions.

Пример:

```ruby
GameEngine::Action.new(
  player_id: 42,
  type: "play_card",
  payload: {
    card_id: 15,
    row: 2,
    column: 1
  }
)
```

Payload использует параметры, необходимые конкретному Action.

### GameEngine::Result

Содержит результат выполнения Action.

Result может содержать:

- успешность выполнения;
- новое состояние игры;
- ошибку;
- события результата.

Result не должен самостоятельно изменять существующий GameState.

Пример успешного результата:

```ruby
Result.new(
  success: true,
  state: new_state,
  events: [
    { type: "technique_played" }
  ]
)
```

Пример ошибки:

```ruby
Result.new(
  success: false,
  error: "Not enough resources"
)
```

### GameEngine::Engine

Координирует выполнение действий.

Engine:

- принимает Action;
- определяет соответствующий обработчик;
- передаёт действие обработчику;
- получает Result;
- возвращает Result.

Engine не должен содержать всю игровую логику в одном классе.

## 7. Маршрутизация Actions

`GameEngine::Engine` использует таблицу обработчиков.

Текущая маршрутизация:

```ruby
ACTIONS = {
  "move" => Actions::Move,
  "attack" => Actions::Attack,
  "play_card" => Actions::PlayCard,
  "end_turn" => Actions::EndTurn
}.freeze
```

Таким образом, сейчас поддерживаются:

- `move`
- `attack`
- `play_card`
- `end_turn`

Не следует добавлять Action в маршрутизацию заранее, если соответствующий обработчик ещё отсутствует.

## 8. Обработчики действий

Игровая логика разделена на отдельные обработчики.

Текущие реализованные обработчики:

- `Move`
- `Attack`
- `PlayCard`
- `EndTurn`

Предполагается дальнейшее расширение системы Actions по мере появления игровых механик.

Конкретная структура файлов и классов может изменяться по мере развития проекта, но контроллеры Rails не должны становиться местом хранения игровой логики.

## 9. GameState

Основное состояние игры хранится в:

```
Game.state
```

Тип поля:

```
JSONB
```

Минимальная структура GameState:

```ruby
{
  "turn_number" => 1,
  "current_player_id" => 42,
  "players" => {
    "42" => {
      "nation_id" => 10,
      "hand" => [],
      "deck" => [],
      "resources" => 0,
      "remaining_time" => nil
    },
    "57" => {
      "nation_id" => 20,
      "hand" => [],
      "deck" => [],
      "resources" => 0,
      "remaining_time" => nil
    }
  },
  "field" => [...]
}
```

GameState является актуальным снимком состояния конкретной партии.

`Game.state` хранится в PostgreSQL в колонке JSONB модели `Game`.

### Главный принцип

Клиент или Decision Provider передаёт в Game Engine только намерение — Action.

Они не передают новый GameState и не изменяют существующее состояние напрямую.

После успешного выполнения Action Game Engine формирует новое состояние, которое становится актуальным `Game.state`.

Игровые операции должны создавать новое состояние, а не неожиданно изменять исходное состояние объекта.

Особенно это относится к операциям над:

- игровым полем;
- рукой;
- колодой;
- ресурсами;
- состоянием техники;
- другими изменяемыми частями GameState.

## 10. Неизменяемость GameState

Успешный Action возвращает новый GameState.

Исходный GameState не должен изменяться непосредственно Action.

Для изменения состояния используется копирование, в текущих Actions — `deep_dup`.

Пример принципа:

```ruby
new_state = @state.deep_dup
```

После этого изменяется только `new_state`.

Оригинальный:

```ruby
@state
```

остаётся неизменным.

Это правило распространяется на:

- поле;
- руку;
- колоду;
- ресурсы;
- состояние техники;
- другие изменяемые данные.

## 11. Начальное состояние и StartGame

`GameEngine::StartGame` отвечает за создание начального GameState.

На старте игры StartGame получает данные участников через GamePlayer.

GamePlayer связывает:

- конкретную игру;
- конкретного игрока;
- выбранную этим игроком Nation;
- выбранную этим игроком Deck.

Таким образом, выбор Nation и Deck является характеристикой участия игрока в конкретной партии.

После формирования `Game.state` игровые Actions должны работать с текущим состоянием партии, а не получать изменяемые характеристики игровых объектов повторными запросами к ActiveRecord.

## 12. GameState.initial

Начальное состояние создаётся на основании участников.

Минимальный формат участника:

```ruby
{
  player_id: 42,
  nation_id: 10
}
```

При запуске реальной игры StartGame передаёт также:

```ruby
{
  player_id: 42,
  nation_id: 10,
  hand: [...],
  deck: [...]
}
```

`GameState.initial` не выполняет запросы к базе данных.

Начальное состояние игрока содержит:

- `nation_id`
- `hand`
- `deck`
- `resources`
- `remaining_time`

Начальные штабные объекты содержат:

- `type`
- `player_id`
- `nation_id`

Конкретные характеристики HQ не должны придумываться до их определения в `GAME_RULES.md`.

## 13. Игровое поле

Размер поля:

```
3 × 5
```

Всего:

```
15 клеток
```

Координаты:

```
row: 0..2
column: 0..4
```

Начальные позиции штабов:

```
Player 1 HQ -> [2][0]
Player 2 HQ -> [0][4]
```

GameState поддерживает:

- создание пустого поля;
- создание начального поля;
- размещение объектов;
- получение объекта по координатам;
- проверку координат;
- проверку занятости;
- перемещение объектов;
- запрет перемещения штаба;
- запрет перемещения объекта на штаб.

GameState не должен самостоятельно определять конкретные правила движения техники.

Конкретные правила движения определяются игровыми правилами и проверяются Game Engine.

## 14. HQ в GameState

HQ является объектом игрового поля и входит в текущий снимок `Game.state`.

Базовая структура:

```ruby
{
  "type" => "headquarters",
  "player_id" => 42,
  "nation_id" => 2
}
```

В дальнейшем в объект HQ в `Game.state` должны попадать текущие игровые характеристики HQ, необходимые игровому движку.

Важно:

- текущие изменяемые характеристики HQ должны находиться в `Game.state`;
- Nation является источником первоначальных характеристик HQ;
- после начала игры Actions работают с текущими данными HQ из `Game.state`;
- Actions не должны обращаться к Nation для получения текущего HP или других изменяемых характеристик;
- отдельная ActiveRecord-модель `Headquarter` не создаётся без отдельного архитектурного решения.

## 15. Game, Player, GamePlayer

Основные модели:

- `Game`
- `Player`
- `GamePlayer`

### Game

Основные поля:

- `id`
- `created_at`
- `updated_at`
- `status`
- `state`

`status`:

- `waiting`
- `started`
- `finished`

`state` хранит GameState в JSONB.

### Player

Player является постоянным игроком системы.

Player не имеет постоянной принадлежности к Nation или Deck.

Связи:

```ruby
has_many :game_players
has_many :games, through: :game_players
has_many :decks
```

### GamePlayer

GamePlayer используется для связи игрока с конкретной игрой.

GamePlayer содержит:

- `game_id`
- `player_id`
- `nation_id`
- `deck_id`

Для комбинации:

```
game_id + player_id
```

существует уникальное ограничение.

GamePlayer связан с:

- Game;
- Player;
- Nation;
- Deck.

Таким образом, конкретная партия определяет:

- каким игроком является участник;
- какую Nation он использует;
- какую Deck он использует.

## 16. Nation

Nation является источником принадлежности карт к конкретной нации.

Nation используется для:

- принадлежности Card;
- выбора нации игроком в конкретной партии;
- первоначальных характеристик, связанных с нацией.

Выбранная Nation для партии хранится через:

```
GamePlayer.nation_id
```

Не следует добавлять в Nation игровые характеристики с выдуманными значениями.

Когда конкретные характеристики HQ или другие характеристики Nation будут окончательно определены правилами, структура хранения рассматривается отдельно.

В текущем проекте существует 3 Nation.

При создании тестовых данных не следует придумывать дополнительные Nation без необходимости.

## 18. Card

Card является основной сущностью карты.

На текущем этапе Card содержит:

- `nation`
- `name`
- `card_type`
- `weight`
- `price`

### Значение характеристик

`weight`:

- характеристика уровня/баланса колоды;
- не является стоимостью розыгрыша;
- не является расходом fuel;
- не должен использоваться вместо `price`.

`price`:

- стоимость розыгрыша карты;
- измеряется в fuel;
- используется Game Engine при PlayCard;
- не является характеристикой техники на поле.

### Валидации Card

Модель Card проверяет:

- наличие `name`;
- наличие `card_type`;
- наличие `weight`;
- `weight` — положительное целое число;
- наличие `price`;
- `price` — целое число не меньше 0.

Игровые правила использования карты не должны переноситься в обычные ActiveRecord validations.

## 19. Technique

Technique содержит характеристики конкретной техники, связанной с Card.

На текущем этапе Technique содержит:

- `technique_type`;
- `attack_range`;
- `movement_count`;
- `movement_type`;
- `firepower`;
- `hp`;
- `fuel`.

### technique_type

Допустимые значения:

- `light_tank`
- `medium_tank`
- `heavy_tank`
- `tank_destroyer`
- `artillery`

### movement_type

Допустимые значения:

- `orthogonal`
- `diagonal`

`orthogonal` — прямолинейное перемещение по горизонтали или вертикали.

`diagonal` — перемещение с возможностью движения по диагонали.

### Валидации Technique

Модель Technique проверяет:

- `technique_type` входит в допустимый список;
- `attack_range` — положительное целое число;
- `movement_count` — положительное целое число;
- `movement_type` входит в допустимый список;
- `firepower` — положительное целое число;
- `hp` — положительное целое число;
- `fuel` — целое число не меньше 0.

Модель Technique не должна проверять сложные игровые зависимости между типом техники и игровым поведением.

Такие проверки относятся к Game Engine.

### Игровое соответствие типов техники

Для текущих правил:

```
light_tank
  movement_type: orthogonal
  movement_count: 2

medium_tank
  movement_type: diagonal
  movement_count: 1

heavy_tank
  movement_type: orthogonal
  movement_count: 1

tank_destroyer
  movement_type: orthogonal
  movement_count: 1

artillery
  movement_type: orthogonal
  movement_count: 1
```

Эти соответствия являются игровыми правилами и применяются Game Engine.

`attack_range` хранит базовую дальность атаки техники.

Специальное поведение отдельных типов техники реализуется Game Engine.

Armor не является характеристикой Technique.

Technique не должна самостоятельно реализовывать:

- боевые правила;
- правила движения;
- правила размещения;
- правила ресурсов;
- специальные боевые взаимодействия.

## 20. Ability

Модель отдельной способности.

На текущем этапе система способностей не используется для реализации специальных боевых правил.

Не следует расширять систему Ability без конкретной игровой необходимости.

## 21. TechniqueAbility

Join-модель между Technique и Ability.

Существующие модели Ability и TechniqueAbility сохраняются.

Дальнейшее использование способностей определяется последующими этапами и актуальным `GAME_RULES.md`.

## 22. Deck

Deck является постоянной сохранённой колодой игрока.

Deck хранится в ActiveRecord/PostgreSQL и используется для формирования стартовой колоды конкретной партии.

Связь:

```
Player -> Deck
Deck -> Nation
Deck -> DeckCard
Deck -> Card через DeckCard
```

Модель Deck содержит:

- `player_id`
- `nation_id`
- `name`

Также Deck имеет:

```ruby
has_many :deck_cards
has_many :cards, through: :deck_cards
```

### card_count

Deck предоставляет:

```ruby
def card_count
  deck_cards.sum(:quantity)
end
```

Это количество физических копий карт в сохранённой колоде.

### Назначение Deck

Deck — постоянная конфигурация колоды игрока.

Она не является текущей колодой партии.

После начала игры Deck не должна изменяться действиями:

- Draw;
- PlayCard;
- Move;
- Attack.

Текущая колода партии находится в:

```
Game.state
```

## 23. DeckCard

DeckCard связывает Deck и Card.

Структура:

```
Deck
  |
  +--- DeckCard --- Card
```

DeckCard содержит:

- `deck_id`
- `card_id`
- `quantity`

`quantity`:

- минимум 1;
- максимум 3.

Для одной комбинации:

```
deck_id + card_id
```

действует уникальность.

### Ограничение Nation

Карта должна принадлежать той же Nation, что и Deck.

Проверяется:

```ruby
deck.nation_id == card.nation_id
```

Это ограничение относится к постоянной конфигурации Deck.

## 24. GameState: карты, hand и deck

После запуска партии данные постоянной Deck копируются в GameState.

Это важное архитектурное разделение:

```
Persistent Deck
     |
     | StartGame
     v
GameState["players"][player_id]["deck"]
```

После этого текущая партия не зависит от изменений сохранённой Deck.

### Игрок в GameState

Пример:

```ruby
{
  "nation_id" => 10,
  "hand" => [...],
  "deck" => [...],
  "resources" => 0,
  "remaining_time" => nil
}
```

### Hand

`hand` содержит полные объекты карт.

Карты в руке не представлены только ID.

### Deck

`deck` содержит полные объекты оставшихся карт.

Порядок карт в `deck` имеет значение.

Deck уже перемешивается при запуске игры.

### Graveyard

Кладбище является частью игровой механики, но отдельная полноценная публичная зона пока не реализована.

В будущем в него будут уходить:

- сыгранные Order;
- уничтоженные Technique;
- другие карты/объекты согласно `GAME_RULES.md`.

Кладбище не должно раскрываться противнику.

## 25. Формирование карт из Deck

Для формирования GameState используется:

```ruby
GameEngine::GameState.cards_from_deck(deck)
```

Метод получает сохранённую Deck и формирует массив отдельных экземпляров карт.

Если:

```
DeckCard.quantity = 3
```

то GameState получает три отдельных объекта карты.

Например:

```ruby
[
  { "card_id" => 15, ... },
  { "card_id" => 15, ... },
  { "card_id" => 15, ... }
]
```

Таким образом, внутри GameState каждая копия карты является отдельным объектом.

Persistent `DeckCard.quantity` при этом не изменяется.

## 26. Формат карты в GameState

Для карт в `hand` и `deck` используется единый формат.

### Базовый объект карты

```ruby
{
  "card_id" => 15,
  "name" => "Т-34",
  "card_type" => "technique",
  "nation_id" => 10,
  "weight" => 1,
  "price" => 2
}
```

### Technique-карта

Для Technique добавляется:

```ruby
"technique" => {
  "technique_type" => "medium_tank",
  "attack_range" => 1,
  "movement_count" => 1,
  "movement_type" => "diagonal",
  "firepower" => 4,
  "hp" => 10,
  "fuel" => 2
}
```

Полный пример:

```ruby
{

  "card_type" => "technique",
  "nation_id" => 10,
  "weight" => 1,
  "price" => 2,

    "technique_type" => "medium_tank",

    "fuel" => 2

}
```

Order не имеет вложенного `technique`.

Пример:

## 27. Карта на поле

После успешного розыгрыша Technique карта из руки превращается в объект техники на поле.

Формат карты в руке и формат техники на поле не являются одинаковыми.

Причина:

- карта в руке содержит данные Card и вложенные данные Technique;
- объект на поле содержит текущее изменяемое состояние техники.

## 28. Формат Technique на поле

Текущий согласованный формат:

```ruby
{
  "type" => "technique",
  "card_id" => 15,
  "player_id" => 42,
  "nation_id" => 10,
  "name" => "Т-34",
  "technique_type" => "medium_tank",
  "hp" => 10,
  "firepower" => 4,
  "fuel" => 2,
  "attack_range" => 1,
  "movement_count" => 1,
  "movement_type" => "diagonal",
  "has_attacked" => false,
  "has_counterattacked" => false
}
```

### В объекте Technique на поле НЕ должно быть:

- `price`;
- `weight`;
- `card_type`;
- вложенного `"technique"`.

### Изменяемые характеристики

На поле хранятся текущие значения:

- `hp`;
- `movement_count`;
- `has_attacked`;
- `has_counterattacked`.

Начальные значения копируются из карты при розыгрыше.

После этого Game Engine работает с данными GameState.

Card/Technique из ActiveRecord не являются источником текущего состояния уже разыгранной техники.

## 29. Скрытая информация

GameState на сервере может содержать полную информацию партии.

Например:

- полную руку игрока;
- полную колоду игрока;
- полную руку противника;
- полную колоду противника.

Однако перед передачей клиенту или Decision Provider состояние должно фильтроваться.

Нельзя раскрывать игроку:

- содержимое руки противника;
- содержимое колоды противника;
- порядок карт в колоде противника;
- содержимое кладбища;
- другую скрытую информацию.

AI должен получать тот же уровень информации, который доступен соответствующему игроку.

## 30. StartGame и Deck

Текущая реализация StartGame:

1. Проверяет, что Game находится в состоянии `waiting`.
2. Получает GamePlayer.
3. Требует ровно двух участников.
4. Получает Deck каждого GamePlayer.
5. Преобразует Deck в полные объекты карт через `GameState.cards_from_deck`.
6. Перемешивает карты.
7. Берёт первые 6 карт в `hand`.
8. Остальные карты помещает в `deck`.
9. Случайно выбирает первого игрока.
10. Создаёт GameState.
11. Переводит Game в `started`.

Размер начальной руки:

```ruby
INITIAL_HAND_SIZE = 6
```

Persistent Deck при этом не изменяется.

## 31. Реализованные Actions

На текущем этапе реализованы:

- `Move`
- `Attack`
- `PlayCard`
- `EndTurn`

## 32. Move

Move проверяет:

- существование игрока;
- принадлежность хода игроку;
- корректность координат;
- наличие техники в исходной клетке;
- принадлежность техники игроку;
- наличие доступного перемещения;
- свободность клетки назначения;
- допустимое направление движения.

После успешного перемещения:

- исходная клетка освобождается;
- техника помещается в новую клетку;
- `movement_count` уменьшается на один;
- исходный GameState не изменяется.

`movement_count` на поле — это оставшееся количество перемещений, а не исходная характеристика техники.

Отдельного флага `"moved"` нет.

## 33. Attack

Attack реализует текущие определённые правила базового боя.

Реализованные проверки и механики включают:

- атаку техники;
- проверку принадлежности атакующего;
- проверку цели;
- дальность атаки;
- ограничение одной атаки техники за ход;
- нанесение урона;
- уничтожение техники при HP <= 0;
- обычную контратаку;
- ограничение одной контратаки;
- уничтожение атакующего контратакой;
- специальное правило ПТ-САУ;
- правило ПТ-САУ против ПТ-САУ;
- атаку штаба по штабу;
- атаку штаба по технике с использованием правила поддержки;
- отсутствие контратаки штаба при атаке штабом.

Для техники используются флаги:

- `"has_attacked"`
- `"has_counterattacked"`

Не использовать для текущей структуры другие названия вроде:

- `attacked`
- `counterattacked`
- `moved`

если для этого нет отдельного архитектурного решения.

Не все боевые механики из `GAME_RULES.md` ещё реализованы.

## 34. EndTurn

EndTurn проверяет:

- существование игрока;
- принадлежность ему текущего хода.

После успешного завершения:

- увеличивается `turn_number`;
- `current_player_id` переключается на другого участника;
- возвращается событие `turn_ended`;
- исходный GameState не изменяется.

Таймеры, обязательный draw, fuel и восстановление показателей пока не входят в EndTurn.

## 35. PlayCard

PlayCard — текущий основной Action Stage 9.

Цель Stage 9 — реализовать базовый механизм розыгрыша карт через Game Engine.

Общая схема:

```
Action(play_card)
        |
        v
GameEngine::Engine
        |
        v
Actions::PlayCard
        |
        | проверки
        | изменение нового состояния
        v
новый GameState
```

PlayCard работает только с текущим GameState.

Action не передаёт новый GameState.

## 36. PlayCard: текущая реализация

На текущем этапе PlayCard реализует базовый розыгрыш Technique.

Поддерживаются проверки:

- существование игрока;
- принадлежность текущего хода игроку;
- наличие карты в руке;
- соответствие карты `card_id`;
- тип карты `technique`;
- достаточное количество `resources`;
- корректность координат;
- свободность клетки;
- соседство клетки с собственным HQ.

### Action

Пример:

```ruby
GameEngine::Action.new(
  player_id: 42,
  type: "play_card",
  payload: {
    card_id: 15,
    row: 2,
    column: 1
  }
)
```

Используются symbol keys:

- `:card_id`
- `:row`
- `:column`

Это соответствует текущему стилю Move и Attack.

## 37. PlayCard: стоимость

Для разыгрываемой карты используется:

```ruby
card["price"]
```

`price` списывается из:

```ruby
player["resources"]
```

Например:

```
resources = 5
price = 2
```

после успешного розыгрыша:

```
resources = 3
```

`price` является стоимостью розыгрыша.

`technique["fuel"]` не является стоимостью розыгрыша.

fuel техники будет использоваться для расчёта ресурсов в соответствующем игровом этапе.

## 38. PlayCard: размещение Technique

Technique можно разместить только на свободной клетке, соседней с собственным HQ.

Проверяются все 8 соседних направлений.

Для HQ в:

```
[2][0]
```

допустимыми соседними клетками являются:

```
[1][0]
[1][1]
[2][1]
```

Например:

```
[0][1]
```

не является соседней клеткой этому HQ.

Важно не ошибаться при написании тестов на диагональное соседство.

Если все допустимые клетки заняты:

- Technique не разыгрывается;
- карта остаётся в руке;
- `resources` не изменяются;
- исходный GameState остаётся неизменным.

## 39. PlayCard: удаление карты

После успешного розыгрыша удаляется одна конкретная копия карты из `hand`.

Если в руке две одинаковые карты:

```ruby
[
  { "card_id" => 15, ... },
  { "card_id" => 15, ... }
]
```

после одного успешного PlayCard должна остаться одна:

```ruby
[
  { "card_id" => 15, ... }
]
```

Persistent Deck при этом не изменяется.

## 49. Контроллеры и интерфейс

Rails-контроллеры не должны содержать игровую логику.

Контроллер должен:

- получить запрос;
- определить пользователя/игру;
- создать Action;
- передать Action в Game Engine;
- обработать Result;
- вернуть ответ.

Stimulus/JavaScript не являются источником истины.

Клиентский код может отвечать за:

- интерфейс;
- отображение состояния;
- взаимодействие пользователя;
- анимации;
- отправку действий.

Но окончательная проверка действия всегда выполняется на сервере.

## 50. Защита GameState

Клиент не должен иметь возможность самостоятельно определить допустимость игрового действия.

Например, клиент не может быть источником истины для:

- возможности движения;
- возможности атаки;
- стоимости карты;
- количества топлива;
- доступности действия;
- победы;
- поражения.

Все критические проверки выполняются Game Engine.

## 51. Decision Provider

Decision Provider отвечает только за получение решения игрока.

Предполагаемая архитектура:

```
DecisionProvider
├── Human
├── Ollama
└── External API
```

Decision Provider должен возвращать Action или эквивалентное решение, которое затем проверяется Game Engine.

Game Engine не должен зависеть от конкретной реализации Decision Provider.

### 55.3. Проверяемость

### 55.6. Не изобретать незаданные правила

## 56. ActiveRecord и GameState

ActiveRecord используется для постоянных данных и формирования начального состояния партии.

В частности:

- `Player`;
- `Game`;
- `GamePlayer`;
- `Nation`;
- `Card`;
- `Technique`;
- `Ability`;
- `TechniqueAbility`;
- `Deck`;
- `DeckCard`.

После формирования GameState обычные игровые Actions должны работать с GameState.

Не следует выполнять запросы к ActiveRecord при каждом:

- Draw;
- PlayCard;
- Move;
- Attack;

только ради получения уже скопированных в GameState данных.

Например, если Technique уже находится на поле:

```ruby
{
  "type" => "technique",
  "hp" => 7,
  ...
}
```

текущий HP должен браться из GameState, а не из:

```ruby
Technique.find(...)
```

## 57. Правило разделения постоянных и текущих данных

Постоянные данные:

- `Nation`
- `Card`
- `Technique`
- `Deck`
- `DeckCard`

Текущие данные партии:

```

```

описывают конкретное состояние конкретной партии.

Принцип:

```

       |
       | создание партии
       v

       |
       | игровые Actions
       v

```

После начала партии GameState становится источником текущих изменяемых характеристик.

## 66. Главное правило проекта

- `GAME_RULES.md` = ЧТО делает игра.
- `AGENTS.md` = КАК это технически реализуется.
- Game Engine = единственный арбитр правил и состояния.
- Decision Provider = источник решения.
- AI = предлагает Action, но не управляет GameState напрямую.
- `Game.state` = актуальный снимок состояния конкретной партии.
- Клиент/AI передают в Game Engine намерение (Action), а не новый GameState.
- Модель Technique = корректность данных.
- Game Engine = проверка игрового поведения Technique.
- GamePlayer = участие конкретного Player в конкретной Game, выбранная Nation и выбранная Deck.
- Nation = источник первоначальных данных, относящихся к нации.
- Card = определение карты.
- Deck = постоянная сохранённая колода игрока.
- DeckCard = количество копий Card в постоянной Deck.
- GameState = актуальные данные конкретной партии.
- `hand` и `deck` внутри GameState содержат полные объекты карт.
