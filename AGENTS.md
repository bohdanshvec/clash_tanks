## 2. Проект и обязательные ограничения

`clash_tanks` — учебная браузерная пошаговая карточная стратегия про танки. Проект вдохновлён WoT: Generals, но использует собственные названия, правила, карты и материалы.

Язык пользовательского интерфейса — украинский. Все новые и изменяемые надписи интерфейса, кнопки, подписи, заголовки и сообщения игроку должны быть на украинском языке.

### Архитектурный инвариант

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

Обязательные правила:

- `GameEngine` — единственный арбитр игровых правил.
- UI, Controllers, JavaScript, Stimulus, Turbo и AI не изменяют `GameState` напрямую.
- `GameActionRunner` применяет действия и сохраняет только успешный результат.
- AI использует только разрешённое состояние и серверный список допустимых действий.
- Скрытая информация противника не должна передаваться UI или AI.
- Не придумывать игровые механики вне `GAME_RULES.md`.
- Не изменять игровую механику без согласования с пользователем.
- Не вводить Redis.
- Не изменять и не удалять PostgreSQL 12 и PostgreSQL 14 без прямого указания пользователя.

При противоречии документации, кода и подтверждённых решений сообщить пользователю. Не выбирать самостоятельно, какое правило считать правильным.

## 5. Работа с графикой и интерфейсом

Перед созданием, изменением или подключением графики сверяться с `ART_STYLE.md`.

Обязательные принципы:

- Использовать утверждённые форматы, структуру каталогов и правила именования изображений.
- Повторно использовать существующие helpers для формирования путей к изображениям.
- Не создавать параллельные каталоги и дублирующие механизмы без необходимости.
- Проверять фактическую прозрачность PNG, а не только наличие альфа-канала.
- Проверять совмещение иллюстрации и рамки в браузере.
- Не встраивать в изображения динамические характеристики, названия, индикаторы и игровые данные.
- Не растягивать изображения с искажением пропорций.
- Не удалять старые ресурсы до подтверждения корректной работы новых путей.
- Не определять допустимость игровых действий средствами CSS или JavaScript.
- Не вычислять игровые результаты на стороне интерфейса.
- Не создавать клиентскую систему расчёта урона или игровых правил.

Графические эффекты и анимации только отображают состояние и события, определённые серверной игровой логикой. Они не меняют правила и не принимают игровые решения.

Подробные требования к изображениям, рамкам, индикаторам, компонентам игрового поля и визуальному оформлению находятся в `ART_STYLE.md`.

## 8. Тестирование и проверка

Запускать тесты при изменении поведения, серверного контракта или игровой логики.

Не дублировать существующее покрытие без конкретной причины.

### Автоматические тесты

Не утверждать, что проверка прошла, если пользователь не сообщил результат или проверка фактически не выполнялась.

Последний подтверждённый полный запуск тестов:

```text
606 runs
2293 assertions
0 failures
0 errors
0 skips
```

Это исторический результат конкретного запуска, а не гарантия состояния текущего рабочего каталога.

### Визуальные изменения

Изменения интерфейса проверять в браузере. В зависимости от затронутого компонента проверять:

- загрузку изображений и рамок;
- фактическую прозрачность и совмещение слоёв;
- расположение динамических элементов;
- цветовую индикацию;
- изменение состояния после игровых действий;
- Turbo-обновления;
- отсутствие ошибок загрузки ресурсов;
- адаптивность и отсутствие переполнения;
- корректность отображения завершённой партии.

Успешная сборка ассетов не подтверждает правильность отображения в браузере.

### Propshaft и CSS

Проект использует Rails 8 и Propshaft.

При добавлении CSS-компонентов:

1. Проверить существующую структуру стилей.
2. Выбрать соответствующий каталог и путь.
3. Проверить подключение файла.
4. Проверить доступность ассета через Propshaft.
5. Проверить результат в браузере.

При необходимости выполнять:

```bash
bin/rails assets:precompile
```

При `Propshaft::MissingAssetError` сначала проверить существование файла, путь, подключение и состояние предварительно собранных ресурсов.

Не считать `assets:precompile` универсальным исправлением ошибок. Не создавать дополнительную систему сборки CSS без необходимости.
