# AGENTS.md

## 1. Проект

Учебный проект — браузерная пошаговая танковая карточная стратегия,
вдохновлённая WoT: Generals.

Проект не является копией оригинальной игры. Планируется использовать
собственные названия, карты, изображения и игровые материалы.

Проект:

clash_tanks

Основной стек:

- Ruby 3.4.10
- RubyGems 3.6.9
- Rails 8.1.3.1
- RVM 1.29.12
- Ubuntu 22.04
- Hotwire
- Stimulus
- Turbo
- PostgreSQL 17.x

PostgreSQL 17 установлен на порту 5434.

PostgreSQL 12 и 14 в системе не изменять и не удалять.

Локальный запуск:

bin/dev


## 2. Основная идея игры

Игрок управляет армией на игровом поле, использует карты,
перемещает подразделения, атакует противника и выполняет игровые действия
по правилам пошаговой стратегии.

Основная игровая сущность — КАРТА.

Основные типы карт:

1. Техника
   - танк или другое боевое подразделение;
   - имеет характеристики;
   - может находиться на игровом поле;
   - может перемещаться и атаковать.

2. Приказ
   - игровое действие или эффект;
   - может изменять состояние игры согласно правилам;
   - может воздействовать на технику, штаб или другие игровые объекты.

3. Взвод
   - вспомогательное подразделение;
   - может усиливать штаб;
   - например, добавлять огневую мощь или HP;
   - конкретные механики будут определены позднее.

Каждая карта в будущем будет иметь уровень (вес).

Вес карты предназначен для формирования колод и балансировки матчей.
Планируется, что колоды игроков будут иметь приблизительно одинаковый
суммарный вес.

Система балансировки по весу пока не реализуется.

Система должна позволять добавлять новые типы карт без переписывания
игрового движка.

Игра разрабатывается постепенно: сначала минимальная рабочая версия,
затем дополнительные игровые механики.


## 3. Главный архитектурный принцип

Игровой движок Rails не должен зависеть от конкретного источника
решений игрока.

Источник решения должен быть абстрагирован.

Возможные источники:

1. Человек-игрок.
2. Локальная AI-модель.
3. Внешняя AI-модель через API.
4. Другие варианты в будущем.

Общая схема:

Game
  ↓
Decision Provider
  ↓
Action
  ↓
Game Engine
  ↓
проверка правил
  ↓
изменение состояния игры

Rails является главным арбитром игры.

AI не имеет права непосредственно изменять состояние игры.

AI только предлагает Action.

Rails проверяет предложенное действие и только после успешной проверки
применяет его.


## 4. Game Engine

Game Engine является центральным компонентом игры.

Он отвечает за:

- правила игры;
- проверку допустимости действий;
- порядок ходов;
- перемещение;
- атаки;
- расчёт урона;
- использование карт;
- изменение ресурсов;
- изменение состояния подразделений;
- победу и поражение;
- другие игровые механики.

Контроллеры Rails не должны содержать основную игровую логику.

Stimulus/JavaScript не является источником истины игровых правил.

Браузер может отображать доступные действия и отправлять их
на сервер, но окончательное решение о допустимости действия
принадлежит Game Engine.


### Архитектура Engine

`GameEngine::Engine` является координатором выполнения действий.

Engine не должен содержать реализацию всех игровых действий внутри себя.

Конкретная логика действий выносится в отдельные классы.

Предварительная структура:

GameEngine::Engine
    ↓
Action
    ↓
конкретный обработчик действия

Например:

- Move
- Attack
- PlayCard
- EndTurn

Конкретные обработчики могут находиться в:

app/services/game_engine/actions/

или в другой структуре, выбранной при реализации.

Engine отвечает за общий процесс:

1. получает GameState;
2. получает Action;
3. проверяет общие условия;
4. определяет обработчик Action;
5. передаёт выполнение соответствующему классу;
6. получает Result;
7. возвращает Result.

Добавление нового игрового действия не должно требовать переписывания
большого `GameEngine::Engine`.


## 5. GameState

Текущее состояние партии представлено отдельным понятием GameState.

GameState не привязан непосредственно к HTTP-запросу.

Game Engine работает с GameState.

Состояние активной партии хранится в `Game.state` в PostgreSQL
в формате JSONB.

Не следует записывать в PostgreSQL каждое промежуточное изменение
состояния отдельно, если это не требуется архитектурой игры.

### Минимальная структура GameState

Текущий GameState содержит:

- `turn_number` — номер хода;
- `current_player_id` — игрок, чей сейчас ход;
- `players` — состояние участников;
- `field` — игровое поле.

Пример:

{
  "turn_number": 1,
  "current_player_id": 42,
  "players": {
    "42": {
      "hand": [],
      "resources": 0,
      "remaining_time": null
    },
    "57": {
      "hand": [],
      "resources": 0,
      "remaining_time": null
    }
  },
  "field": [
    [null, null, null, null, {"type": "headquarters", "player_id": 57}],
    [null, null, null, null, null],
    [{"type": "headquarters", "player_id": 42}, null, null, null, null]
  ]
}


### Неизменяемость GameState и поля

Операции изменения состояния не должны скрыто изменять переданный
исходный объект.

В частности:

- `GameEngine::GameState.place_object` создаёт новое поле;
- `GameEngine::GameState.move_object` создаёт новое поле.

Исходное поле остаётся неизменным.

Это позволяет Game Engine создавать новое состояние игры
без скрытого изменения предыдущего состояния.


### Игровое поле

Поле имеет размер:

- 3 строки;
- 5 клеток.

Всего:

3 × 5 = 15 клеток.

Координаты:

- строки: `0..2`;
- столбцы: `0..4`.

В начальном поле находятся два штаба:

- штаб одного игрока — в нижней левой клетке `[2][0]`;
- штаб другого игрока — в верхней правой клетке `[0][4]`.

Клетки поля могут содержать игровые объекты.

Текущая базовая работа с полем включает:

- создание пустого поля;
- создание начального поля со штабами;
- проверку координат;
- получение объекта по координатам;
- размещение объекта;
- перемещение объекта;
- проверку занятости клетки;
- запрет перемещения штаба;
- запрет перемещения объекта на клетку штаба;
- сохранение исходного поля неизменным.


### Перемещение

Одно перемещение техники на одну клетку является одним отдельным
игровым действием.

Один ход игрока может содержать множество Action.

Например, в рамках одного хода игрок потенциально может:

- разыграть несколько карт;
- выполнить несколько перемещений;
- выполнить другие разрешённые действия.

Запас хода конкретной техники может позволять ей выполнить
несколько отдельных перемещений за один ход.

Например:

movement = 2

означает возможность выполнить два отдельных перемещения
на одну клетку.

Количество перемещений и остальные ограничения будут определяться
характеристиками техники и игровыми правилами.


### Направления перемещения

GameState не определяет направления движения конкретной техники.

Разные типы техники могут иметь разные возможности перемещения.

Например:

- горизонтальное и вертикальное движение;
- горизонтальное, вертикальное и диагональное движение;
- другие варианты в будущем.

Поэтому диагональное перемещение не запрещается на уровне GameState.

Правила конкретной техники должны проверяться Game Engine.


### Штаб

Штаб:

- является объектом игрового поля;
- находится в фиксированной стартовой клетке;
- не может быть перемещён;
- занимает свою клетку;
- не может быть заменён другим объектом;
- клетка штаба не является допустимой клеткой назначения
  для перемещения техники.

Правила атаки и взаимодействия со штабом будут определены позднее.


### Скрытая информация

Состояние руки игрока является частью GameState.

При передаче состояния конкретному игроку или AI нельзя раскрывать
скрытую информацию противника.

Игрок должен видеть свои карты, но не карты противника.

AI должен получать только информацию, доступную соответствующему
участнику.

При необходимости внутренний GameState должен преобразовываться
в представление, предназначенное конкретному участнику.


## 6. Game / Player / GamePlayer

### Game

Конкретная игровая партия.

Поля:

- `id`;
- `created_at`;
- `updated_at`;
- `status`;
- `state`.

`state` хранится в PostgreSQL как JSONB.

Статусы:

- `waiting` — партия ожидает второго участника;
- `started` — партия началась;
- `finished` — партия завершена.

Новая игра создаётся со статусом `waiting`.


### Player

Участник игры.

Player может представлять:

- человека;
- AI.

Основные игровые правила не должны различать Human Player и AI Player.

Оба используют одинаковый механизм действий.


### GamePlayer

Связь участника с конкретной игрой.

Одна игра рассчитана на двух участников.

Один Player может участвовать в нескольких играх.

Связи:

Player:

    has_many :game_players
    has_many :games, through: :game_players

Game:

    has_many :game_players
    has_many :players, through: :game_players

GamePlayer:

    belongs_to :game
    belongs_to :player


## 7. Создание и начало игры

Игра не должна сразу переходить в состояние `started`.

Для игры с человеком:

1. первый игрок создаёт игру;
2. игра получает статус `waiting`;
3. второй игрок присоединяется;
4. после появления двух участников игра переходит в `started`;
5. создаётся начальный GameState;
6. определяется первый игрок;
7. начинается первый ход.

Для игры с AI:

1. игрок создаёт игру;
2. игра получает статус `waiting`;
3. к игре присоединяется AI;
4. игра переходит в `started`;
5. создаётся начальный GameState;
6. определяется первый игрок;
7. начинается первый ход.

Game Engine не должен зависеть от того, является участник человеком
или AI.

На текущем этапе одна Game рассчитана ровно на двух участников.


## 8. Action

Любое игровое действие представляется как Action.

Примеры:

- Move;
- Attack;
- PlayCard;
- EndTurn;
- другие действия в будущем.

Action представляет намерение выполнить действие.

Action не изменяет GameState самостоятельно.

Action содержит данные, необходимые для описания действия, например:

- тип действия;
- игрок, выполняющий действие;
- идентификатор объекта;
- координаты;
- другие параметры конкретного действия.

Конкретная игровая логика должна находиться в обработчике действия,
а не в общем классе Action.

Общая схема:

Player
  ↓
Action
  ↓
Game Engine
  ↓
validate
  ↓
конкретный Action handler
  ↓
новый GameState
  ↓
Result


### Один ход и множество действий

Один ход игрока может содержать множество Action.

Например:

Game
  ↓
Turn
  ↓
Action
Action
Action
Action
  ↓
EndTurn

`EndTurn` завершает текущий ход.

Один ход не равен одному Action.


## 9. Result

Результат выполнения Action отделён от самого Action.

`GameEngine::Result` не содержит основную игровую логику
и не изменяет переданный GameState.

Result может сообщать:

- успешность действия;
- новое состояние игры;
- ошибку;
- причину отказа;
- события, произошедшие в результате действия.

При успешном выполнении действия создаётся новое состояние,
которое передаётся через Result.

Общая схема:

старый GameState
      ↓
   Action
      ↓
Game Engine
      ↓
валидация
      ↓
новый GameState
      ↓
Result


## 10. Карточная система

Карта является общей игровой сущностью.

Танк не является отдельной сущностью верхнего уровня:
техника является типом карты.

Предварительная концепция:

Card
  ├── Technique
  ├── Order
  └── Platoon

Конкретная реализация типов карт будет развиваться постепенно.

Не следует преждевременно создавать сложную систему наследования,
если она не требуется текущей механикой.

### Текущая реализация

Созданы:

- `Nation`;
- `Card`;
- `Technique`;
- `Ability`;
- `TechniqueAbility`.

Связи:

Nation
  ↓
Card
  ↓
Technique
  ↓
TechniqueAbility
  ↓
Ability

`Card` принадлежит `Nation`.

`Card` может иметь одну `Technique`.

`Technique` принадлежит `Card`.

`Technique` имеет много `TechniqueAbility`.

`Technique` имеет много `Ability` через `TechniqueAbility`.

`Ability` имеет много `TechniqueAbility`.

`Ability` имеет много `Technique` через `TechniqueAbility`.

`TechniqueAbility` принадлежит:

- `Technique`;
- `Ability`.


### Nation

`Nation` хранит:

- `name`;
- `code`.

Для `name` требуется наличие значения.

Для `code` требуется наличие значения и уникальность.


### Card

`Card` хранит:

- `nation`;
- `name`;
- `card_type`;
- `weight`.

Для `name` требуется наличие значения.

Для `card_type` требуется наличие значения.

`weight` должен быть:

- целым числом;
- больше нуля.

Система балансировки колод по весу пока не реализуется.

Текущий `weight` является базовой характеристикой карты,
не полноценной системой балансировки.


### Technique

`Technique` в текущей реализации представляет тип карты `Technique`
и связан с `Card`.

Характеристики боевой техники:

- HP;
- атака;
- броня;
- стоимость;
- дальность;
- перемещение;

будут добавлены на следующем этапе.

Поэтому текущая модель `Technique` пока не считается
полноценной боевой техникой.


### Ability

`Ability` хранит:

- `name`;
- `code`.

Для `name` требуется наличие значения.

Для `code` требуется наличие значения и уникальность.


### TechniqueAbility

`TechniqueAbility` является связующей моделью между `Technique`
и `Ability`.

Одна и та же пара:

    technique + ability

не должна создаваться повторно.

Уникальность пары обеспечивается на уровне базы данных.


## 11. Хранение данных

PostgreSQL используется для:

- игроков;
- партий;
- связей игроков с партиями;
- карт;
- характеристик карт;
- результатов игр;
- при необходимости истории ходов;
- состояния активных партий.

Состояние активной игры хранится в:

`Game.state`

в формате JSONB.

Быстро изменяющееся игровое состояние не следует хранить
в cookies.

Не использовать cookies как основной механизм хранения
состояния игры.

Не использовать PostgreSQL для записи каждого промежуточного
изменения состояния, если это не требуется архитектурой игры.


## 12. AI-противник

Первоначально планируется:

Qwen3 1.7B

Запуск:

Ollama + Qwen3 1.7B

Модель должна работать локально на компьютере разработчика.

Ориентир по времени ответа AI:

до ~10 секунд.

В дальнейшем модель можно заменить без изменения Game Engine.


## 13. Decision Provider

Источник решений должен быть отделён от Game Engine.

Предварительная концепция:

Decision Provider
    ├── Human
    ├── Ollama
    ├── External API
    └── другие реализации

Game Engine не должен напрямую зависеть от:

- Ollama;
- Qwen;
- конкретной AI-модели;
- внешнего API.

Game Engine работает с Action.


## 14. AI Provider

AI Provider отвечает только за получение решения от AI.

Предварительная структура:

app/services/ai/

    decision_provider.rb
    ollama/
        client.rb
        decision_provider.rb

Конкретная структура может измениться во время разработки.

AI Provider не имеет права напрямую изменять GameState.


## 15. Допустимые действия

Game Engine должен уметь определить список действий,
допустимых в текущем состоянии игры.

Decision Provider получает список действий,
доступных соответствующему участнику.

AI выбирает одно из допустимых действий.

Даже если AI вернул неправильное или недопустимое действие,
Game Engine должен его отклонить.

Game Engine должен проверять:

- кто выполняет действие;
- чей сейчас ход;
- существует ли объект;
- принадлежит ли объект игроку;
- допустимо ли действие;
- хватает ли ресурсов;
- соблюдены ли остальные игровые правила.

Разрабатывать постепенно.

Каждый этап должен оставлять проект работоспособным.

### Этап 4 — Game Engine и Action — ВЫПОЛНЕН

Реализованы:

- `GameEngine::Action`;
- `GameEngine::Result`;
- `GameEngine::Engine`;
- архитектура отдельных обработчиков игровых действий.

Зафиксировано:

- Action представляет намерение;
- Action не изменяет GameState;
- Engine является координатором;
- конкретные действия выносятся в отдельные классы;
- Result отделён от Action;
- Result не изменяет исходный GameState;
- успешное действие создаёт новое состояние;
- новое состояние передаётся через Result;
- Game Engine является арбитром правил.

Этап завершён.

### Этап 6 — карточная система — ВЫПОЛНЕН

Созданы базовые модели карточной системы:

- `Nation`;
- `Card`;
- `Technique`;
- `Ability`;
- `TechniqueAbility`.

Реализованы основные связи:

- Nation → Cards;
- Card → Nation;
- Card → Technique;
- Technique → Card;
- Technique → Abilities через TechniqueAbility;
- Ability → Techniques через TechniqueAbility.

Реализованы базовые валидации:

`Nation`:

- наличие `name`;
- наличие `code`;
- уникальность `code`.

`Ability`:

- наличие `name`;
- наличие `code`;
- уникальность `code`.

`Card`:

- наличие `name`;
- наличие `card_type`;
- `weight` — положительное целое число.

`TechniqueAbility`:

- связь с Technique;
- связь с Ability;
- запрет повторения одной и той же пары
  `technique_id + ability_id` на уровне базы данных.

Тестовые фикстуры `nations.yml` и `abilities.yml` удалены.

После пересоздания тестовой базы данных все тесты проходят.

Текущий результат:

    50 runs, 132 assertions, 0 failures, 0 errors, 0 skips

Этап завершён.
