# AGENTS.md

## 1. Проект

**clash_tanks** — учебный браузерный пошаговый танковый карточный стратегический проект, вдохновлённый WoT: Generals.

Проект не является копией оригинальной игры.

Основная цель проекта — изучение Ruby on Rails на примере полноценной игровой архитектуры с отделением игровой логики от интерфейса и источника решений игрока.

- RubyGems 3.6.9
- Rails 8.1.3.1
- RVM 1.29.12

## 4. Главный архитектурный принцип

Игровой движок является единственным арбитром состояния игры.

Источник решения отделён от игрового движка.

Источником решения может быть:

- человек;
- локальный AI;
- внешний AI/API;
- другой Decision Provider.

Общая схема:

```
Decision Provider
       |
       | Action
       v
Game Engine
       |
       | проверка правил
       | применение действия
       v
GameState
```

- Decision Provider предлагает действие.
- Game Engine самостоятельно проверяет его допустимость и изменяет состояние игры.
- Decision Provider не имеет права самостоятельно изменять GameState.

## 5. Game Engine

Игровой движок отвечает за:

- проверку действий;
- применение действий;
- соблюдение игровых правил;
- порядок ходов;
- перемещение;
- атаки;
- расчёт урона;
- использование карт;
- изменение ресурсов;
- изменение состояния техники;
- завершение хода;
- определение победы и поражения.

Game Engine не должен зависеть от конкретного источника решений.

Он не должен знать, кто предложил действие:

- человек;
- AI;
- внешний API.

## 6. Структура Game Engine

Основные компоненты:

- `GameEngine::Action`
- `GameEngine::Result`
- `GameEngine::Engine`

### GameEngine::Action

Описывает намерение игрока.

Action:

- содержит необходимые параметры действия;
- не изменяет состояние игры;
- может быть создан человеком или AI;
- передаётся в Game Engine для проверки.

Один ход может содержать несколько последовательных Actions.

### GameEngine::Result

Содержит результат выполнения Action.

Result может содержать:

- успешность выполнения;
- новое состояние игры;
- ошибку;
- события результата.

Result не должен самостоятельно изменять существующий GameState.

### GameEngine::Engine

Координирует выполнение действий.

Engine:

- принимает Action;
- определяет соответствующий обработчик;
- передаёт действие обработчику;
- получает Result;
- возвращает Result.

Engine не должен содержать всю игровую логику в одном классе.

## 7. Обработчики действий

Игровая логика разделена на отдельные обработчики.

Текущие реализованные обработчики:

- `Move`
- `Attack`
- `EndTurn`

Планируемый обработчик:

- `PlayCard`

Конкретная структура файлов и классов может изменяться по мере развития проекта, но контроллеры Rails не должны становиться местом хранения игровой логики.

### Текущая маршрутизация Engine

`GameEngine::Engine` маршрутизирует известные типы Action к соответствующим обработчикам.

На текущем этапе поддерживаются:

- `move`
- `attack`
- `end_turn`

`play_card` пока не подключается, поскольку соответствующий обработчик ещё не реализован.

Не следует добавлять Action в маршрутизацию заранее, если соответствующий обработчик ещё отсутствует.

## 8. GameState

Основное состояние игры хранится в:

```
Game.state
```

Тип поля:

```
JSONB
```

Минимальная структура GameState:

- `turn_number`
- `current_player_id`
- `players`
- `field`

GameState является актуальным снимком состояния конкретной партии.

`Game.state` хранится в PostgreSQL в колонке JSONB модели `Game`.

### Основной принцип

Клиент или Decision Provider передаёт в Game Engine только намерение — Action.

Они не передают новый GameState и не изменяют существующее состояние напрямую.

После успешного выполнения Action Game Engine формирует новое состояние, которое становится актуальным `Game.state`.

Игровые операции должны создавать новое состояние, а не неожиданно изменять исходное состояние объекта.

Особенно это относится к операциям над игровым полем.

### Начальное состояние

`GameEngine::StartGame` отвечает за создание начального GameState.

На старте игры StartGame получает данные участников через GamePlayer.

GamePlayer связывает:

- конкретную игру;
- конкретного игрока;
- выбранную этим игроком Nation.

Таким образом, выбор Nation является характеристикой участия игрока в конкретной партии, а не постоянной характеристикой модели Player.

При создании начального GameState информация о Nation переносится в состояние партии.

После формирования `Game.state` игровые Actions должны работать с текущим состоянием партии, а не получать изменяемые характеристики игровых объектов повторными запросами к ActiveRecord-моделям.

### GameState.initial

Начальное состояние создаётся на основании участников следующего вида:

```ruby
[
  { player_id: 42, nation_id: 1 },
  { player_id: 57, nation_id: 2 }
]
```

`GameState.initial` не выполняет запросы к базе данных.

Начальное состояние игроков содержит как минимум:

- `nation_id`
- `hand`
- `resources`
- `remaining_time`

Начальные штабные объекты содержат:

- `type`
- `player_id`
- `nation_id`

Конкретные числовые характеристики HQ пока не добавляются в production GameState, поскольку их значения ещё не определены в `GAME_RULES.md`.

## 9. Игровое поле

Размер поля:

```
3 × 5
```

Всего:

```
15 клеток
```

Координаты:

```
row: 0..2
column: 0..4
```

Начальные позиции штабов определены в `GAME_RULES.md`.

В текущей реализации:

```
Player 1 HQ -> [2][0]
Player 2 HQ -> [0][4]
```

GameState поддерживает:

- создание пустого поля;
- создание начального поля;
- размещение объектов;
- получение объекта по координатам;
- проверку координат;
- проверку занятости;
- перемещение объектов;
- запрет перемещения штаба;
- запрет перемещения объекта на штаб.

GameState не должен самостоятельно определять конкретные правила движения техники.

Конкретные правила движения определяются игровыми правилами и проверяются Game Engine.

### HQ в GameState

HQ является объектом игрового поля и входит в текущий снимок `Game.state`.

HQ содержит:

- `player_id`
- `nation_id`

Текущая базовая структура:

```ruby
{
  "type" => "headquarters",
  "player_id" => 42,
  "nation_id" => 1
}
```

В дальнейшем в объект HQ в `Game.state` должны попасть текущие игровые характеристики HQ, необходимые игровому движку, например HP, firepower и другие определённые правилами характеристики.

Важно:

- текущие характеристики HQ должны находиться в `Game.state`;
- Nation является источником первоначальных характеристик HQ;
- после начала игры Actions должны работать с текущими данными HQ из `Game.state`;
- Actions не должны обращаться к Nation для получения текущего HP или других изменяемых характеристик;
- отдельная ActiveRecord-модель `Headquarter` не создаётся.

Конкретные числовые характеристики HQ для наций пока не определены в `GAME_RULES.md`.

Поэтому нельзя придумывать или фиксировать значения HP, firepower, fuel и других характеристик HQ до определения этих значений в правилах.

## 10. Game, Player, GamePlayer

Основные модели:

- `Game`
- `Player`
- `GamePlayer`

### Game

Основные поля:

- `id`
- `created_at`
- `updated_at`
- `status`
- `state`

`status`:

- `waiting`
- `started`
- `finished`

`state` хранит GameState в JSONB.

### GamePlayer

Используется для связи игроков с конкретной игрой.

Для комбинации:

```
game_id + player_id
```

существует уникальное ограничение.

### Nation и GamePlayer

Выбранная игроком Nation относится к конкретной партии.

В GamePlayer реализована связь:

```
GamePlayer -> Nation
```

и поле:

```
nation_id
```

Модель GamePlayer имеет связи:

```ruby
belongs_to :game
belongs_to :player
belongs_to :nation
```

Player не получает постоянную принадлежность к Nation.

`nation_id` сейчас является nullable на уровне существующей миграции базы данных, чтобы сохранить совместимость с ранее созданными записями. На уровне модели `belongs_to :nation` требует наличие Nation для новых GamePlayer.

## 11. Жизненный цикл игры

Игра создаётся в состоянии:

```
waiting
```

После присоединения необходимого количества участников игра переходит в:

```
started
```

При запуске игры:

```
GameEngine::StartGame
```

создаёт начальный GameState и определяет первого игрока.

После выполнения условий окончания игра переходит в:

```
finished
```

### StartGame

StartGame работает с объектами GamePlayer.

Для каждого участника он получает как минимум:

```ruby
{
  player_id: ...,
  nation_id: ...
}
```

Эти данные передаются в `GameState.initial`.

Текущая реализация требует ровно двух GamePlayer.

Первый игрок определяется случайно при запуске игры.

GameState не выполняет запросы к базе данных или ActiveRecord-моделям.

## 12. Карточная система

Основные модели карточной системы:

- `Nation`
- `Card`
- `Technique`
- `Ability`
- `TechniqueAbility`

Связи:

```
Nation
  |
  v
Card
  |
  v
Technique
  |
  v
TechniqueAbility
  |
  v
Ability
```

### Nation

Nation является источником принадлежности карт к конкретной нации.

Выбор Nation для партии хранится через GamePlayer.

Характеристики HQ относятся к выбранной Nation как к источнику первоначальных данных, однако конкретные числовые характеристики HQ пока не определены в `GAME_RULES.md`.

Не следует добавлять в Nation поля характеристик HQ с выдуманными значениями.

Когда конкретные характеристики HQ будут определены правилами, структура хранения должна быть отдельно рассмотрена и зафиксирована.

### Card

Карта имеет, среди прочего:

- `nation`;
- `name`;
- `card_type`;
- `weight`.

Характеристики, относящиеся непосредственно к конкретной карте, могут храниться на уровне Card.

В частности:

- HP;
- firepower;
- price.

Эти поля должны добавляться только на соответствующих этапах и согласно актуальному `GAME_RULES.md`.

`weight` является отдельной характеристикой и не является `price`.

Типы карт определяются в `GAME_RULES.md`.

### Technique

Technique представляет характеристики и тип конкретной боевой техники, связанной с картой.

На текущем этапе Technique содержит:

- `technique_type`;
- `attack_range`;
- `movement_count`;
- `movement_type`.

#### technique_type

Допустимые значения:

- `light_tank`
- `medium_tank`
- `heavy_tank`
- `tank_destroyer`
- `artillery`

#### movement_type

Допустимые значения:

- `orthogonal`
- `diagonal`

`orthogonal` — прямолинейное перемещение по горизонтали или вертикали.

`diagonal` — перемещение с возможностью движения по диагонали.

#### Валидация Technique

Модель Technique проверяет только корректность самих значений:

- `technique_type` должен входить в список допустимых типов;
- `attack_range` должен быть положительным целым числом;
- `movement_count` должен быть положительным целым числом;
- `movement_type` должен входить в список допустимых типов перемещения.

Модель Technique не проверяет соответствие конкретного типа техники конкретным игровым характеристикам.

Такие проверки являются игровой логикой и выполняются Game Engine согласно `GAME_RULES.md`.

#### Текущие характеристики типов техники

Для определённых на данный момент правил:

```
light_tank
  movement_type: orthogonal
  movement_count: 2

medium_tank
  movement_type: diagonal
  movement_count: 1

heavy_tank
  movement_type: orthogonal
  movement_count: 1

tank_destroyer
  movement_type: orthogonal
  movement_count: 1

artillery
  movement_type: orthogonal
  movement_count: 1
```

Эти соответствия являются игровыми правилами и должны применяться Game Engine, а не валидациями модели.

`attack_range` хранит базовую дальность атаки техники.

Специальное поведение отдельных типов техники, включая дальнюю атаку artillery (САУ), реализуется в Game Engine.

Armor не является характеристикой Technique.

Technique не должна самостоятельно реализовывать боевые правила, правила движения или специальные боевые взаимодействия.

Специальное поведение tank_destroyer (ПТ-САУ) также не реализуется через Ability на текущем этапе. Это игровое поведение Game Engine.

### Ability

Модель отдельной способности.

На текущем этапе система способностей не используется для реализации специальных боевых правил.

### TechniqueAbility

Join-модель между Technique и Ability.

Существующие модели Ability и TechniqueAbility сохраняются, но их дальнейшее применение определяется будущими этапами и актуальным `GAME_RULES.md`.

## 13. Реализованные Actions

В Stage 8 реализованы следующие Actions:

- `Move`
- `Attack`
- `EndTurn`

### Move

Move проверяет:

- существование игрока;
- принадлежность хода игроку;
- корректность координат;
- наличие техники в исходной клетке;
- принадлежность техники игроку;
- наличие доступного перемещения;
- свободность клетки назначения;
- допустимое направление движения.

После успешного перемещения:

- исходная клетка освобождается;
- техника помещается в новую клетку;
- количество оставшихся перемещений уменьшается на один;
- исходный GameState не изменяется.

### Attack

Attack реализует текущие определённые правила базового боя, включая:

- атаку техники;
- проверку принадлежности атакующего;
- проверку цели;
- дальность атаки;
- ограничение одной атаки техники за ход;
- нанесение урона;
- уничтожение техники при HP <= 0;
- обычную контратаку;
- ограничение одной контратаки;
- уничтожение атакующего контратакой;
- специальное правило ПТСАУ;
- правило ПТСАУ против ПТСАУ;
- атаку штаба по штабу;
- атаку штаба по технике с использованием правила поддержки;
- отсутствие контратаки штаба при атаке штабом.

Не все боевые механики из `GAME_RULES.md` ещё реализованы. В частности, механики, требующие дополнительных характеристик и систем, должны реализовываться на соответствующих последующих этапах.

### EndTurn

EndTurn проверяет:

- существование игрока;
- принадлежность ему текущего хода.

После успешного завершения:

- увеличивается `turn_number`;
- `current_player_id` переключается на другого участника;
- возвращается событие `turn_ended`;
- исходный GameState не изменяется.

Таймеры, fuel и восстановление других показателей пока не изменяются в EndTurn. Они относятся к отдельному этапу ресурсов и хода.

### Result и неизменяемость состояния

Успешные Actions возвращают новый GameState.

Исходный GameState не должен изменяться непосредственно Action.

Для создания изменённого состояния используется копирование существующего состояния.

## 15. Контроллеры и интерфейс

Rails-контроллеры не должны содержать игровую логику.

Контроллер должен:

- получить запрос;
- определить пользователя/игру;
- создать Action;
- передать Action в Game Engine;
- обработать Result;
- вернуть ответ.

Stimulus/JavaScript не являются источником истины.

Клиентский код может отвечать за:

- интерфейс;
- отображение состояния;
- взаимодействие пользователя;
- анимации;
- отправку действий.

Но окончательная проверка действия всегда выполняется на сервере.

## 16. Защита GameState

Клиент не должен иметь возможность самостоятельно определить допустимость игрового действия.

Например, клиент не может быть источником истины для:

- возможности движения;
- возможности атаки;
- стоимости карты;
- количества топлива;
- доступности действия;
- победы;
- поражения.

Все критические проверки выполняются Game Engine.

## 17. Скрытая информация

Информация для игрока должна фильтроваться перед передачей клиенту или Decision Provider.

Игрок получает только разрешённую ему информацию.

В частности, нельзя раскрывать:

- карты руки противника;
- содержимое колоды противника;
- порядок карт в колоде противника;
- содержимое кладбища.

AI должен получать тот же уровень информации, который доступен соответствующему игроку.

AI не должен получать скрытую информацию только потому, что технически она присутствует внутри GameState.

## 18. Хранение состояния

Основное игровое состояние хранится в PostgreSQL в поле:

```
Game.state
```

с типом:

```
JSONB
```

`Game.state` является актуальным состоянием конкретной партии.

Не следует хранить постоянно изменяющееся состояние каждого промежуточного действия в отдельных строках базы данных без архитектурной необходимости.

Cookies не используются как основное хранилище игрового состояния.

## 19. Decision Provider

Decision Provider отвечает только за получение решения игрока.

Предполагаемая архитектура:

```
DecisionProvider
├── Human
├── Ollama
└── External API
```

Decision Provider должен возвращать Action или эквивалентное решение, которое затем проверяется Game Engine.

Game Engine не должен зависеть от конкретной реализации Decision Provider.

## 20. AI

Планируемый локальный AI:

```
Ollama
Qwen3 1.7B
```

Предполагаемая структура:

```
app/services/ai/decision_provider.rb
app/services/ai/ollama/client.rb
app/services/ai/ollama/decision_provider.rb
```

AI должен:

- получить разрешённую информацию об игре;
- проанализировать состояние;
- выбрать действие;
- вернуть Action;
- передать Action в Game Engine.

AI не изменяет GameState напрямую.

## 21. Информация, доступная AI

AI должен получать только информацию, доступную соответствующему игроку.

В зависимости от текущих правил это может включать:

- собственные карты;
- собственные ресурсы;
- собственную технику;
- собственный штаб;
- собственные взводы;
- видимую часть игрового поля;
- количество карт противника;
- количество карт в колоде противника;
- доступные действия;
- необходимую историю действий.

AI не должен получать:

- скрытые карты противника;
- порядок карт в колоде противника;
- содержимое кладбища;
- другую скрытую информацию.

## 22. Структура приложения

Игровая логика должна находиться преимущественно в соответствующих доменных классах и сервисах.

## 23. Принципы разработки

### 23.1. Простота

Проект учебный.

Не следует добавлять сложные архитектурные решения без необходимости.

### 23.2. Разделение ответственности

Каждый класс должен выполнять одну понятную роль.

### 23.3. Проверяемость

Игровая логика должна быть удобна для тестирования без браузера.

### 23.4. Независимость AI

Игровой движок не должен зависеть от Ollama, Qwen или другого конкретного AI.

### 23.5. Сервер является источником истины

Нельзя полагаться на клиентский JavaScript для обеспечения правил игры.

### 23.6. Не изобретать незаданные правила

Если игровая механика не определена в `GAME_RULES.md`, сначала необходимо определить её как игровое решение и зафиксировать в `GAME_RULES.md`.

## 31. Главное правило проекта

- `GAME_RULES.md` = ЧТО делает игра.
- `AGENTS.md` = КАК это технически реализуется.
- Game Engine = единственный арбитр правил и состояния.
- Decision Provider = источник решения.
- AI = предлагает Action, но не управляет GameState напрямую.
- `Game.state` = актуальный снимок состояния конкретной партии.
- Клиент/AI передают в Game Engine намерение (Action), а не новый GameState.
- Модель Technique = корректность данных.
- Game Engine = проверка игрового поведения Technique.
- GamePlayer = участие конкретного Player в конкретной Game и выбранная для этой партии Nation.
- Nation = источник первоначальных данных, относящихся к нации.
- GameState = актуальные данные конкретной партии.
- Actions работают с текущим GameState и не должны получать изменяемое игровое состояние повторно из ActiveRecord.
