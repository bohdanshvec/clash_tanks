# AGENTS.md

## 1. Проект

`clash_tanks` — учебный браузерный пошаговый танковый карточный стратегический проект, вдохновлённый WoT: Generals.

Проект не является копией оригинальной игры.

Основная цель проекта — изучение Ruby on Rails на примере полноценной игровой архитектуры с отделением игровой логики от интерфейса и источника решений игрока.

## 3. Источники истины

- `GAME_RULES.md` — **ЧТО** делает игра.
- `AGENTS.md` — **КАК** это технически реализуется.

### Приоритет

Если вопрос касается игровой механики, использовать `GAME_RULES.md`.

Если вопрос касается архитектуры, структуры кода, технической реализации или процесса разработки, использовать `AGENTS.md`.

Информация из старых чатов не является источником истины и не должна переопределять текущие версии этих двух файлов.

Если реализация противоречит `GAME_RULES.md`, необходимо исправлять реализацию, а не молча изменять правила.

Если принимается новое игровое решение, его необходимо зафиксировать в `GAME_RULES.md`.

Если принимается новое архитектурное или техническое решение, его необходимо зафиксировать в `AGENTS.md`.

Не следует дублировать подробные игровые правила из `GAME_RULES.md` в `AGENTS.md`.

## 4. Главный архитектурный принцип

Игровой движок является единственным арбитром состояния игры.

Источник решения отделён от игрового движка.

Источником решения может быть:

- человек;
- локальный AI;
- внешний AI/API;
- другой Decision Provider.

Общая схема:

```text
Decision Provider
       |
       | Action
       v
Game Engine
       |
       | проверка правил
       | применение действия
       v
GameState
```

Decision Provider предлагает действие.

Game Engine самостоятельно проверяет его допустимость и изменяет состояние игры.

Decision Provider не имеет права самостоятельно изменять `GameState`.

---

## 5. Game Engine

Игровой движок отвечает за:

- проверку действий;
- применение действий;
- соблюдение игровых правил;
- порядок ходов;
- перемещение;
- атаки;
- расчёт урона;
- использование карт;
- изменение ресурсов;
- изменение состояния техники;
- завершение хода;
- определение победы и поражения.

Game Engine не должен зависеть от конкретного источника решений.

Он не должен знать, кто предложил действие:

- человек;
- AI;
- внешний API.

---

## 6. Структура Game Engine

Основные компоненты:

```text
GameEngine::Action
GameEngine::Result
GameEngine::Engine
```

### `GameEngine::Action`

Описывает намерение игрока.

Action:

- содержит необходимые параметры действия;
- не изменяет состояние игры;
- может быть создан человеком или AI;
- передаётся в Game Engine для проверки.

Один ход может содержать несколько последовательных Actions.

### `GameEngine::Result`

Содержит результат выполнения Action.

Result может содержать:

- успешность выполнения;
- новое состояние игры;
- ошибку;
- события результата.

Result не должен самостоятельно изменять существующий `GameState`.

### `GameEngine::Engine`

Координирует выполнение действий.

Engine:

1. принимает Action;
2. проверяет допустимость;
3. передаёт действие соответствующему обработчику;
4. получает результат;
5. возвращает новый результат состояния.

## 7. Обработчики действий

Игровая логика должна быть разделена на отдельные обработчики.

Планируемые обработчики:

```text
Move
Attack
PlayCard
EndTurn
```

Конкретная структура файлов и классов может изменяться по мере развития проекта, но контроллеры Rails не должны становиться местом хранения игровой логики.

---

## 8. GameState

Основное состояние игры хранится в:

```ruby
Game.state
```

Тип поля:

```text
JSONB
```

Минимальная структура GameState:

```text
turn_number
current_player_id
players
field
```

GameState является состоянием текущей партии.

### Основной принцип

Игровые операции должны создавать новое состояние, а не неожиданно изменять исходное состояние объекта.

Особенно это относится к операциям над игровым полем.

---

## 9. Игровое поле

Размер поля:

```text
3 × 5
```

Всего:

```text
15 клеток
```

Координаты:

```text
row: 0..2
column: 0..4
```

Начальные позиции штабов определены в `GAME_RULES.md`.

В текущей реализации:

```text
Player 1 HQ -> [2][0]
Player 2 HQ -> [0][4]
```

GameState уже поддерживает:

- создание пустого поля;
- создание начального поля;
- размещение объектов;
- получение объекта по координатам;
- проверку координат;
- проверку занятости;
- перемещение объектов;
- запрет перемещения штаба;
- запрет перемещения объекта на штаб.

GameState не должен самостоятельно определять конкретные правила движения техники.

Конкретные правила движения определяются игровыми правилами и проверяются Game Engine.

## 10. Game, Player, GamePlayer

Основные модели:

```text
Game
Player
GamePlayer
```

### Game

Основные поля:

```text
id
created_at
updated_at
status
state
```

`status`:

```text
waiting
started
finished
```

`state` хранит GameState в JSONB.

### GamePlayer

Используется для связи игроков с конкретной игрой.

Для комбинации:

```text
game_id + player_id
```

существует уникальное ограничение.

---

## 11. Жизненный цикл игры

Игра создаётся в состоянии:

```text
waiting
```

После присоединения необходимого количества участников игра переходит в:

```text
started
```

При запуске игры:

```text
GameEngine::StartGame
```

создаёт начальный GameState и определяет первого игрока.

После выполнения условий окончания игра переходит в:

```text
finished
```

## 12. Карточная система

Основные модели карточной системы:

```text
Nation
Card
Technique
Ability
TechniqueAbility
```

Связи:

```text
Nation
  |
  v
Card
  |
  v
Technique
  |
  v
TechniqueAbility
  |
  v
Ability
```

### Card

Карта имеет, среди прочего:

- nation;
- name;
- card_type;
- weight.

Типы карт определяются в `GAME_RULES.md`.

### Technique

`Technique` представляет техническую модель боевой техники, связанной с картой.

Техническая реализация характеристик должна соответствовать `GAME_RULES.md`.

Если конкретная характеристика ещё не определена в `GAME_RULES.md`, её нельзя самостоятельно придумывать во время реализации.

### Ability

Представляет отдельную способность техники.

### TechniqueAbility

Join-модель между `Technique` и `Ability`.

## 14. Контроллеры и интерфейс

Rails-контроллеры не должны содержать игровую логику.

Контроллер должен:

1. получить запрос;
2. определить пользователя/игру;
3. создать Action;
4. передать Action в Game Engine;
5. обработать Result;
6. вернуть ответ.

Stimulus/JavaScript не являются источником истины.

Клиентский код может отвечать за:

- интерфейс;
- отображение состояния;
- взаимодействие пользователя;
- анимации;
- отправку действий.

Но окончательная проверка действия всегда выполняется на сервере.

---

## 15. Защита GameState

Клиент не должен иметь возможность самостоятельно определить допустимость игрового действия.

Например, клиент не может быть источником истины для:

- возможности движения;
- возможности атаки;
- стоимости карты;
- количества топлива;
- доступности действия;
- победы;
- поражения.

Все критические проверки выполняются Game Engine.

---

## 16. Скрытая информация

Информация для игрока должна фильтроваться перед передачей клиенту или Decision Provider.

Игрок получает только разрешённую ему информацию.

В частности, нельзя раскрывать:

- карты руки противника;
- содержимое колоды противника;
- порядок карт в колоде противника;
- содержимое кладбища.

AI должен получать тот же уровень информации, который доступен соответствующему игроку.

AI не должен получать скрытую информацию только потому, что технически она присутствует внутри `GameState`.

---

## 17. Хранение состояния

Основное игровое состояние хранится в PostgreSQL в поле:

```ruby
Game.state
```

с типом:

```text
JSONB
```

Не следует хранить постоянно изменяющееся состояние каждого промежуточного действия в отдельных строках базы данных без архитектурной необходимости.

Cookies не используются как основное хранилище игрового состояния.

---

## 18. Decision Provider

Decision Provider отвечает только за получение решения игрока.

Предполагаемая архитектура:

```text
DecisionProvider
├── Human
├── Ollama
└── External API
```

Decision Provider должен возвращать Action или эквивалентное решение, которое затем проверяется Game Engine.

Game Engine не должен зависеть от конкретной реализации Decision Provider.

---

## 19. AI

Планируемый локальный AI:

```text
Ollama
Qwen3 1.7B
```

Предполагаемая структура:

```text
app/services/ai/decision_provider.rb
app/services/ai/ollama/client.rb
app/services/ai/ollama/decision_provider.rb
```

AI должен:

1. получить разрешённую информацию об игре;
2. проанализировать состояние;
3. выбрать действие;
4. вернуть Action;
5. передать Action в Game Engine.

AI не изменяет GameState напрямую.

---

## 20. Информация, доступная AI

AI должен получать только информацию, доступную соответствующему игроку.

В зависимости от текущих правил это может включать:

- собственные карты;
- собственные ресурсы;
- собственную технику;
- собственный штаб;
- собственные взводы;
- видимую часть игрового поля;
- количество карт противника;
- количество карт в колоде противника;
- доступные действия;
- необходимую историю действий.

AI не должен получать:

- скрытые карты противника;
- порядок карт в колоде противника;
- содержимое кладбища;
- другую скрытую информацию.

## 21. Структура приложения

Игровая логика должна находиться преимущественно в соответствующих доменных классах и сервисах.

Предполагаемое разделение:

```text
app/
├── models/
├── services/
│   ├── game_engine/
│   └── ai/
├── controllers/
└── javascript/
```

Конкретная структура может изменяться по мере развития проекта.

Главный принцип — не переносить игровую логику в Controllers или Stimulus.

## 22. Принципы разработки

### 22.1 Простота

Проект учебный.

Не следует добавлять сложные архитектурные решения без необходимости.

### 22.2 Разделение ответственности

Каждый класс должен выполнять одну понятную роль.

### 22.3 Проверяемость

Игровая логика должна быть удобна для тестирования без браузера.

### 22.4 Независимость AI

Игровой движок не должен зависеть от Ollama, Qwen или другого конкретного AI.

### 22.5 Сервер является источником истины

Нельзя полагаться на клиентский JavaScript для обеспечения правил игры.

### 22.6 Не изобретать незаданные правила

Если игровая механика не определена в `GAME_RULES.md`, сначала необходимо определить её как игровое решение и зафиксировать в `GAME_RULES.md`.

## 23. Рабочий процесс

При начале нового этапа:

1. Прочитать актуальный `AGENTS.md`.
2. Прочитать актуальный `GAME_RULES.md`.
3. Определить текущий этап разработки.
4. Проверить существующую реализацию.
5. Реализовать только необходимые изменения.
6. Добавить или изменить тесты.
7. Запустить тесты.
8. Проверить соответствие `GAME_RULES.md`.
9. Обновить `AGENTS.md`, если изменилось техническое состояние или архитектура.
10. Обновить `GAME_RULES.md`, если было принято новое игровое решение.
11. После завершения существенного этапа сделать отдельный Git commit.

## 29. Правило работы с двумя документами

При продолжении проекта в новом чате пользователь предоставляет:

```text
AGENTS.md
GAME_RULES.md
```

Эти два файла являются актуальным состоянием проекта.

Необходимо:

- сначала ознакомиться с обоими файлами;
- не использовать старые решения из памяти чатов, если они противоречат файлам;
- следовать `GAME_RULES.md` при реализации игровой механики;
- следовать `AGENTS.md` при реализации архитектуры;
- после изменения архитектуры обновлять `AGENTS.md`;
- после изменения игровых правил обновлять `GAME_RULES.md`.
