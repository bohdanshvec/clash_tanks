## Проект и обязательные границы

clash_tanks — учебная браузерная пошаговая карточная стратегия про танки. Проект вдохновлён WoT: Generals, но использует собственные названия, правила, карты и материалы.

Главный инвариант:

Decision Provider → Action → GameActionRunner → GameEngine → GameState

GameEngine — единственный арбитр игровых правил. Controllers, UI, JavaScript, Stimulus, Turbo и AI не изменяют GameState напрямую, не определяют правила и не обходят Engine. GameActionRunner отвечает за безопасное применение Action и сохранение только успешного результата.

Не придумывать игровые механики, отсутствующие в GAME_RULES.md. Не изменять и не удалять PostgreSQL 12 и 14 без явного указания. При противоречии документации или кода не выбирать вариант самостоятельно: сообщить пользователю.

## Stage 21 — что уже реализовано

### AI-игрок, колоды и создание AI-игры

- Game поддерживает режимы `pvp` и `ai`; `Player#ai?` отличает технического игрока.
- Уникальный частичный индекс не допускает более одного постоянного AI-игрока.
- `AiPlayers::Setup` идемпотентно находит или создаёт постоянного игрока `ai@clash-tanks.local` с именем ИИ.
- `AiPlayers::DecksSetup` идемпотентно подготавливает три постоянные колоды: США — лёгкая техника (вес 13), СССР — средняя техника (вес 22), Германия — тяжёлая техника (вес 28). Колоды построены из существующих карт; не создавать AI-игрока и AI-колоды заново для каждой партии.
- `Matchmaking::AiDeckSelector` выбирает полную совместимую AI-колоду в пределах ±10% веса; при нескольких совпадениях выбирает ближайший вес.
- Реализован серверный сервис создания AI-игры и его тесты. Не считать старое утверждение «AI-режим в `GamesController#create` полностью отсутствует» актуальным без повторной проверки текущего кода.

### Decision Provider и применение действий

- Реализованы `DecisionProviders::Context`, `DecisionProviders::AI`, `GameEngine::Action`, адаптеры Groq и OpenAI.
- `DecisionProviders::AI` проверяет формат ответа, нормализует payload и ограничивает повторные попытки некорректного решения (`MAX_ATTEMPTS = 3`). Тесты используют подменяемый источник решений; автоматические тесты не должны вызывать реальный API.
- `GameActionRunner` применяет действие под блокировкой игры, проверяет digest состояния на устаревшее решение и сохраняет состояние только после успешного результата Engine. Отказанное или устаревшее действие не должно менять состояние.
- `Games::RunAiTurns` выполняет последовательность AI-действий через `DecisionProviders::AI` → `GameActionRunner` → `GameEngine`. Максимум — 20 действий за запуск; сервис перечитывает игру и прекращает цикл при смене активного игрока, завершении игры, ошибке или достижении лимита.
- `Games::RunAiTurns` использует PostgreSQL advisory lock для исключения параллельных AI-циклов одной игры и ограниченные повторы при устаревшем состоянии (`MAX_STALE_STATE_RETRIES = 3`). Не менять PostgreSQL 12/14 и не вводить Redis.
- `GamesController` запускает AI при открытии игры, если ход принадлежит AI, и после человеческого действия, если ход перешёл к AI.
- События AI передаются в существующий Turbo flow для обоих участников; каждому строится собственный `VisibleState`.
- Исправлена проблема с замороженным массивом событий: события копируются перед добавлением результатов AI.
- Тестами проверены ошибки provider, повторный запуск после временной ошибки, Turbo-события AI, скрытая информация, ограничения цикла, блокировки, устаревший digest, сохранение только успешного Action и остановка при изменении состояния или хода.

## Текущее состояние Groq

Groq подключён как основной AI-провайдер. Модель по умолчанию — `openai/gpt-oss-20b`.

В `DecisionProviders::GroqAdapter` реализованы:

- выбор действия по индексу из серверного списка разрешённых действий;
- передача `legal_actions` без повторного включения `available_actions` в `game_state`;
- запрос JSON-ответа;
- проверка индекса и возврат исходного объекта разрешённого действия;
- логирование использования prompt/completion/total tokens;
- логирование HTTP-ошибок и доступных rate-limit headers;
- ограниченные повторы HTTP 429, если из заголовка или тела ответа удалось получить положительную задержку.

### Обнаруженные проблемы Groq

**HTTP 429 — ограничение токенов в минуту (TPM).**

При реальных запросах возникали ошибки ограничения токенов. Адаптер повторяет запрос только тогда, когда может определить положительную задержку из заголовка или тела ответа. Повтор не гарантирует успех при исчерпании лимита.

**HTTP 400 — `json_validate_failed`.**

Наблюдался ответ API:

```text
Failed to validate JSON. Please adjust your prompt.
```

Ошибка возникала при использовании JSON-режима с моделью `openai/gpt-oss-20b`. Причина пока не подтверждена.

HTTP 400 `json_validate_failed` и HTTP 429 — разные проблемы. Не считать HTTP 400 ошибкой превышения TPM без подтверждающих данных.

**Высокое потребление completion tokens.**

В диагностической выборке из восьми успешных запросов зарегистрировано:

| Метрика | Значение |
|---|---:|
| Prompt tokens | 10 627 |
| Completion tokens | 4 289 |
| Total tokens | 14 916 |

Это показатели только восьми успешных запросов, а не полный расход за минуту.

В некоторых запросах completion tokens значительно превышали ожидаемый объём короткого JSON с `action_index`.

В текущем адаптере не установлен параметр `max_completion_tokens` или `max_tokens`. Добавлять его можно только после проверки актуальной совместимости с API и моделью.
