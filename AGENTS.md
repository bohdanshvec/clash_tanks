## Проект и обязательные границы

`clash_tanks` — учебная браузерная пошаговая карточная стратегия про танки. Проект вдохновлён WoT: Generals, но использует собственные названия, правила, карты и материалы.

Язык пользовательского интерфейса — украинский. Все новые и изменяемые надписи интерфейса, кнопки, подписи, заголовки и сообщения игроку должны оставаться на украинском языке.

Главный архитектурный инвариант:

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

- `GameEngine` — единственный арбитр игровых правил.
- UI, Controllers, JavaScript, Stimulus, Turbo и AI не изменяют `GameState` напрямую.
- `GameActionRunner` применяет действия и сохраняет только успешный результат.
- AI использует только разрешённое состояние и серверный список допустимых действий.
- Скрытая информация противника не должна передаваться UI или AI.
- Не придумывать игровые механики вне `GAME_RULES.md`.
- Не изменять игровую механику без согласования с пользователем.
- Не вводить Redis.
- Не изменять и не удалять PostgreSQL 12 и PostgreSQL 14 без прямого указания пользователя.

При противоречии документации, кода и подтверждённых решений сообщить пользователю. Не выбирать самостоятельно, какое правило считать правильным.

## Правила работы с изображениями

Перед созданием или подключением графики сверяться с `ART_STYLE.md`.

### Утверждённые форматы

- `1024 × 1024 px` — квадратный формат объектов на игровом поле: штабов, техники и взводов.
- `848 × 1264 px` — вертикальный формат полных карт в каталоге, колодах, редакторе и руке игрока.

Приказы используют только вертикальный формат.

Изображение объекта и его прозрачная рамка — отдельные ресурсы. При многослойном отображении рамка располагается над иллюстрацией.

Эти размеры относятся к исходным ресурсам, а не к обязательным CSS-размерам на экране. CSS может масштабировать изображение без создания отдельных файлов для разных размеров отображения.

Не растягивать изображения с искажением пропорций.

До подключения проверять соответствие размеров, взаимное положение слоёв, прозрачность и визуальное совмещение рамки с иллюстрацией.

### Структура графических ресурсов

Для изображений карт утверждена структура:

```text
app/assets/images/cards/{nation}/{type}/
```

Поддерживаемые нации:

- `germany`;
- `usa`;
- `ussr`.

Поддерживаемые типы:

- `headquarters`;
- `technique`;
- `order`;
- `platoon`.

Не создавать параллельные каталоги для тех же изображений без необходимости.

Старые графические ресурсы не удалять до подтверждения корректной работы новых путей.

### Именование изображений

Использовать утверждённую схему:

```text
{nation}_{display}_{type}_{card_code_without_nation_and_type_prefix}.png
```

Где:

- `nation` — код нации;
- `display` — `field` или `card`;
- `type` — тип карты;
- последняя часть — код карты без префиксов нации и типа.

Для рамок:

```text
{nation}_{display}_{type}_border.png
{nation}_{display}_{type}_{variant}_border.png
```

Поддерживать Unicode в кодах карт.

В частности, немецкая буква `ß` должна сохраняться в имени изображения.

Не заменять Unicode-символы произвольной транслитерацией.

### Универсальные helpers

Для формирования путей использовать существующие helpers:

```ruby
card_image_path
card_border_path
```

Не дублировать формирование путей в отдельных ERB-шаблонах, если соответствующий helper уже существует.

Не создавать отдельные исключения для каждой карты без необходимости.

Если helper не поддерживает конкретный случай, сначала проверить его контракт и актуальные данные карты.

### Прозрачность PNG

**Прозрачность рамок обязательна.**

Наличие альфа-канала не гарантирует, что изображение действительно содержит прозрачные пиксели.

PNG может иметь режим RGBA, но оставаться полностью непрозрачным.

Перед подключением рамки необходимо:

1. Проверить размер.
2. Проверить фактическую прозрачность.
3. Проверить центральную область иллюстрации.
4. Проверить совмещение с изображением.
5. Проверить результат в браузере.

Область, предназначенная для иллюстрации, должна быть прозрачной.

Декоративные элементы рамки должны сохраняться.

Не удалять все светлые пиксели автоматически: светлые элементы могут быть частью рамки.

Если непрозрачный белый фон закрывает иллюстрацию, исправлять исходный PNG, а не маскировать проблему случайными CSS-правилами.

### Динамические данные

Не встраивать в PNG:

- динамические названия;
- характеристики;
- стоимость;
- текст способностей;
- индикаторы движения;
- индикаторы атаки;
- другие изменяемые игровые данные.

Такие данные должны отображаться интерфейсом из актуального состояния и данных карты.

Для числовых характеристик действует правило:

- `0` — существующая характеристика со значением ноль;
- `–` — характеристика неприменима.

Не заменять числовой ноль прочерком.

Не отображать характеристику, если она не предусмотрена соответствующим компонентом и не относится к данному типу карты.

### Различия типов карт

Разные типы карт могут иметь разные композиции рамок.

Единый художественный стиль не означает одинаковое расположение всех характеристик.

Для штабов, техники, взводов и приказов использовать соответствующие рамки.

Для взводов предусмотрены варианты:

- `attack`;
- `defense`.

Вариант должен выбираться по актуальным данным карты.

Для техники со способностью предусматривается отдельная область описания в вертикальном формате.

Для приказов предусматривается собственная область текста эффекта.

Не использовать характеристики техники в рамке приказа, если они не относятся к этому типу карты.

### Обозначения классов техники

Для квадратных карт техники утверждены обозначения:

| Тип | Обозначение |
|---|---|
| Лёгкий танк | Ромб |
| Средний танк | Горизонтальный узкий прямоугольник |
| Тяжёлый танк | Квадрат |
| ПТ-САУ | Треугольник |
| САУ | Вертикальный узкий прямоугольник |

Символ размещается в верхнем правом элементе рамки.

Текущий утверждённый цвет всех символов — красный.

Не вводить цветовое разделение по принадлежности техники без согласования.

Символы должны формироваться средствами CSS или SVG.

Не встраивать их в PNG.

### Индикаторы движения

Для техники используются индикаторы движения в виде колёс.

Количество индикаторов определяется `movement_limit`.

Использованные перемещения определяются `movement_count`.

Красный цвет обозначает ещё не использованное перемещение.

Стандартный цвет обозначает использованное перемещение.

При определении активного состояния учитывать текущего игрока и владельца техники.

Во время хода противника колёса не должны отображаться как доступные для перемещения владельцем.

Красный индикатор не гарантирует наличие допустимого маршрута.

Не вычислять допустимость перемещения в CSS или JavaScript.

### Огневая мощь

Для штабов и техники используется цветовая индикация состояния атаки и контратаки.

Основные данные:

- `has_attacked`;
- `has_counterattacked`.

Красный цвет показывает, что соответствующее действие ещё не использовано.

Стандартный цвет показывает, что действие использовано либо индикатор неактивен.

Цвет не гарантирует допустимость атаки или наличие цели.

Допустимость действий определяется серверной игровой логикой.

### Способности техники

На игровом поле текст способности техники не должен перегружать компактную карту.

Для техники со способностью предусматривается отдельный визуальный индикатор и способ просмотра описания.

Полный текст способности не размещается на квадратной карте поля.

Реализация этих элементов фиксируется в `PROGRESS.md` только после фактической проверки.

Для сенсорных устройств нельзя полагаться исключительно на наведение курсора: нужно предусмотреть подходящий способ просмотра дополнительной информации.

### Графические эффекты

Графика и анимации только отображают состояние и события, определённые серверной игровой логикой.

Они не меняют правила и не принимают игровые решения.

Для эффектов использовать существующие серверные события.

Не создавать отдельную клиентскую систему расчёта урона.

## Тестирование и проверка

Запускать тесты при изменении поведения, серверного контракта или игровой логики.

Не дублировать существующее покрытие без конкретной причины.

### Визуальные изменения

Визуальные изменения проверять в браузере.

Проверять:

- загрузку иллюстраций;
- загрузку рамок;
- прозрачность;
- совмещение слоёв;
- расположение динамических элементов;
- цветовую индикацию;
- изменение состояния после игровых действий;
- Turbo-обновления;
- отсутствие ошибок загрузки ресурсов.

Не считать успешную сборку ассетов подтверждением правильного отображения в браузере.

### Propshaft и CSS

Проект использует Rails 8 и Propshaft.

При добавлении новых CSS-компонентов необходимо:

1. Проверить существующую структуру стилей.
2. Создать файл по правильному пути.
3. Проверить способ подключения.
4. Проверить доступность файла для Propshaft.
5. Проверить результат в браузере.

При изменении ассетов и CSS при необходимости выполнять:

```bash
bin/rails assets:precompile
```

Если появляется `Propshaft::MissingAssetError`, сначала проверять:

- существование файла;
- правильность пути;
- подключение;
- пути загрузки ассетов;
- состояние предварительно собранных ресурсов.

Не считать `assets:precompile` универсальным исправлением ошибок.

Не создавать дополнительную систему сборки CSS без необходимости.

### Автоматические тесты

Не утверждать, что проверка прошла, если пользователь не сообщил результат или проверка фактически не выполнялась.

Исторические результаты тестов относятся только к соответствующим запускам:

```text
542 runs, 2024 assertions, 0 failures, 0 errors, 0 skips
548 runs, 2061 assertions, 0 failures, 0 errors, 0 skips
549 runs, 2082 assertions, 0 failures, 0 errors, 0 skips
553 runs, 2114 assertions, 0 failures, 0 errors, 0 skips
```

Экспериментальный результат:

```text
554 runs, 2125 assertions, 0 failures, 0 errors, 0 skips
```

относится к состоянию, изменения которого впоследствии были отменены.

Не использовать его как результат текущей версии.

После последующих графических изменений новый полный прогон тестов не подтверждён.
