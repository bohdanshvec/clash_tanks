Проведи полный аудит текущего проекта. Это НЕ задача на изменение кода — 
только анализ и отчёт. Ничего не редактируй, не создавай файлы, не 
предлагай патчи в виде diff — только текстовый отчёт с рекомендациями.

Проанализируй проект по следующим направлениям:

1. АРХИТЕКТУРА И СТРУКТУРА
   - Логична ли текущая структура папок/модулей для целей проекта
   - Есть ли нарушения разделения ответственности (слишком "жирные" 
     файлы/классы/функции, смешение слоёв — бизнес-логика вместе с UI, 
     доступ к БД в контроллерах и т.д.)
   - Есть ли циклические зависимости между модулями
   - Насколько легко будет добавлять новые фичи при текущей структуре

2. ДУБЛИРОВАНИЕ КОДА
   - Найди повторяющиеся куски логики (даже если они не 100% идентичны, 
     но решают одну задачу разными способами)
   - Найди похожие компоненты/функции, которые стоит объединить в общую 
     абстракцию
   - Укажи конкретные файлы и строки

3. МЁРТВЫЙ И НЕИСПОЛЬЗУЕМЫЙ КОД
   - Неиспользуемые функции, переменные, импорты, файлы
   - Закомментированный код, который давно пора удалить
   - Недостижимый код

4. НЕПОСЛЕДОВАТЕЛЬНОСТЬ И СОГЛАШЕНИЯ
   - Несогласованный стиль именования (разные конвенции в разных частях)
   - Смешение подходов к решению одной и той же задачи в разных местах 
     проекта (например, разные способы обработки ошибок, разные паттерны 
     работы с состоянием)
   - Отсутствие единообразия в обработке ошибок/логировании

5. ПОТЕНЦИАЛЬНЫЕ БАГИ И РИСКИ
   - Проблемные места: отсутствие валидации входных данных, гонки 
     состояний, утечки ресурсов, необработанные исключения
   - Хардкод значений, которые должны быть конфигурируемыми

6. ПРОИЗВОДИТЕЛЬНОСТЬ
   - Явные узкие места (N+1 запросы, лишние ре-рендеры, неэффективные 
     алгоритмы/структуры данных, избыточные вычисления)
   - Проблемы, которые сейчас незаметны на малом объёме данных, но 
     станут критичными при росте

7. ЗАВИСИМОСТИ
   - Неиспользуемые зависимости в package.json/requirements/аналогах
   - Устаревшие или потенциально проблемные версии библиотек
   - Дублирующиеся зависимости, решающие одну задачу

8. ТЕСТЫ И ПОКРЫТИЕ (если применимо)
   - Какие критичные части проекта не покрыты тестами
   - Есть ли "хрупкие" тесты, завязанные на детали реализации

ФОРМАТ ОТВЕТА:
Для каждой найденной проблемы укажи:
- Файл(ы) и, если возможно, строки
- В чём проблема и почему это важно (риск/эффект на тех. долг)
- Приоритет: критично / стоит исправить сейчас / можно отложить
- Краткая рекомендация, как исправить (без реализации)

В конце — сводка топ-5 проблем, которые стоит решить ПРЯМО СЕЙЧАС, 
пока проект на раннем этапе, чтобы не наращивать технический долг.
