## Stage 21 — AI в игровом процессе (ЗАВЕРШЁН)

### 1. База, модели и постоянный AI-игрок

- Режимы Game: `pvp`, `ai`; `Player#ai?`; частичный уникальный индекс для одного постоянного AI-игрока.
- `AiPlayers::Setup` идемпотентно находит или создаёт `ai@clash-tanks.local`.
- `AiPlayers::DecksSetup` готовит три постоянные AI-колоды на основе существующих карт.
- Игрок и колоды повторно используются между партиями; постоянные Deck не изменяются во время игры.

### 2. Подбор совместимой колоды

`Matchmaking::AiDeckSelector` выбирает полную AI-колоду в диапазоне ±10% веса, при нескольких совпадениях предпочитает ближайшую. Конкретные веса зависят от актуальных характеристик карт и состава колод.

### 3. AI-решение и безопасное выполнение Action

- `DecisionProviders::AI` получает разрешённый Context, проверяет ответ, нормализует ключи payload, допускает максимум три попытки некорректного решения.
- Источник решений подменяется в тестах; реальный API из тестов не вызывается.
- GameActionRunner под блокировкой сверяет `expected_state_digest`, вызывает Engine и сохраняет только успешный state. Устаревший или отклонённый Action не изменяет игру.
- Проверки покрывают успешное сохранение, отказ Engine, waiting, stale digest и актуальный digest.

### 4. Автоматический AI-цикл

`Games::RunAiTurns` (`app/services/games/run_ai_turns.rb`):

- максимум 20 AI-действий за запуск;
- PostgreSQL advisory lock предотвращает параллельные циклы одной игры, независимые игры не блокируются;
- максимум три stale-state retry;
- перед решением перечитывает игру и проверяет статус, активного игрока и лимит;
- прекращает цикл при смене хода, завершении игры, ошибке или лимите;
- сохраняет уже выполненные действия при последующей ошибке;
- принимает необязательный `on_action` и вызывает его с событиями каждого успешного действия после сохранения state.

### 5. GamesController и пошаговый Turbo

1. `GamesController#process_game_action` применяет человеческий Action, перечитывает игру и отправляет `broadcast_game_update(human_events)`.
2. Затем вызывает `run_ai_turns_if_needed(broadcast_each_action: true)`.
3. `Games::RunAiTurns` после каждого успешного AI Action вызывает `on_action(action_events)`.
4. Callback контроллера делает `@game.reload` и отправляет отдельный `broadcast_game_update(action_events)`.
5. Каждый broadcast формирует собственный VisibleState для каждого участника.
6. `GamesController#show` запускает AI, если открыта started-игра, в которой ход принадлежит AI.
7. Ошибка provider не отменяет уже сохранённое человеческое действие или выполненные действия AI.

Контроллерные тесты проверяли отдельные broadcasts и отсутствие передачи скрытой руки. Пользователь подтвердил последовательное отображение действий реального AI в полноценной браузерной партии.

### 6. Актуальный GroqAdapter

Основной адаптер — Groq, модель `openai/gpt-oss-20b`. Модель выбирает `action_index` из индексируемых `legal_actions`; адаптер проверяет индекс и возвращает исходное разрешённое действие. `available_actions` не дублируется в передаваемом состоянии.

Текущая конфигурация:

- Structured Outputs со строгой JSON-схемой `action_index`;
- `reasoning_effort=low`;
- `max_completion_tokens=512`;
- логирование token usage, `finish_reason` и HTTP/rate-limit диагностики;
- ограниченные повторы HTTP 429 при распознаваемой положительной задержке;
- ограниченная обработка временных сетевых ошибок;
- подменяемый HTTP transport для тестов;
- при единственном `legal_action` API-вызов пропускается.

Системная инструкция `INSTRUCTIONS` оставлена без сокращения по решению пользователя.

Исторически наблюдались HTTP 429 из-за TPM, HTTP 400 `json_validate_failed` в прежнем JSON-режиме и высокий расход completion tokens. В проверенной браузерной партии ответы успешно обрабатывались, но это не гарантирует отсутствия будущих HTTP 429 или timeout.

В Stage 22 диагностическое логирование было сокращено: убраны подробные данные руки AI, payload действий, тело HTTP-ошибок и сообщения исключений из ряда записей. Сохранены полезные метрики для диагностики.

## Архитектурные границы

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
browser session → current_player → GamePlayer → Action.player_id → GameEngine
```

GameEngine — единственный арбитр правил; Controller организует процесс и Turbo; AI выбирает Action; GameActionRunner безопасно применяет его; VisibleState ограничивает данные. AI не мутирует state и не получает скрытые данные противника.
