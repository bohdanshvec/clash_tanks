# Архитектурные ограничения

Основной принцип:

**Engine определяет результат, UI отображает его.**

Сохранять существующую архитектуру:

```text
Decision Provider
      ↓
    Action
      ↓
GameActionRunner
      ↓
  GameEngine
      ↓
  GameState
```

Основные ограничения:

- UI, Stimulus, Turbo и AI не изменяют `GameState` напрямую.
- Только `GameEngine` определяет результат игровых действий.
- Проверка допустимости действий остаётся ответственностью игрового движка.
- UI использует события и разрешённое состояние `VisibleState`.
- AI анализирует только разрешённую информацию из `VisibleState`.
- Симуляция гипотетических действий не изменяет реальное состояние партии.
- Для симуляции используется настоящий `GameEngine`.
- Симуляции не должны создавать реальные записи в БД, запускать callbacks, отправлять Turbo broadcast или изменять статистику.
- Скрытые карты противника и неизвестные карты колод не должны становиться доступными AI.

# Stage 25 — собственный стратегический движок AI-соперника

<badge color="success">Первоначальная разработка завершена</badge>

## Цель этапа

Заменить принятие решений внешней языковой моделью собственным алгоритмом, способным анализировать игровую ситуацию, оценивать стратегические цели, планировать последовательности действий и адаптироваться к фактическому результату каждого действия.

Собственный AI интегрирован в существующую игровую архитектуру и использует разрешённую информацию из `VisibleState`.

## Архитектура

Основной поток принятия решений:

```text
VisibleState
     ↓
ActionOptions
     ↓
TacticalPlanner
     ├── StateSimulator
     │        ↓
     │    GameEngine
     │        ↓
     │   VisibleState
     │
     └── StrategicEvaluator
              ↓
         Plan / Steps
              ↓
         ActionExecutor
              ↓
       Decision Provider
              ↓
            Action
              ↓
       GameActionRunner
              ↓
          GameEngine
              ↓
           GameState
```

### StateSimulator

Файл:

```text
app/services/decision_providers/opponent_engine/planning/state_simulator.rb
```

Реализована изолированная симуляция гипотетических действий.

Основные возможности:

- работа с `VisibleState`;
- восстановление изолированного состояния для `GameEngine`;
- замена скрытых карт заглушками;
- создание `GameEngine::Action`;
- вызов настоящего `GameEngine::Engine`;
- получение нового разрешённого состояния и событий;
- сохранение исходного `VisibleState` без изменений.

В ходе разработки исправлена проверка принадлежности техники в `GameEngine::Actions::Move`: учтено несовпадение типов идентификаторов игрока.

Добавлена регрессионная проверка несовпадения типов ID. Проверена симуляция перемещения через настоящий `GameEngine`.

### ActionOptions

Файл:

```text
app/services/decision_providers/action_options.rb
```

Сервис формирует варианты действий на основании `available_actions` из `VisibleState`.

Поддерживаются:

- перемещение техники;
- атака;
- розыгрыш карты;
- завершение хода (`end_turn`).

Для взводов учитываются доступные слоты, для техники — доступные позиции, для приказов — разрешённые цели и возможности соответствующего действия.

Варианты действий формируются заново для каждого симулированного состояния. Окончательная проверка допустимости действий остаётся ответственностью `GameEngine`.

### StrategicEvaluator

Файл:

```text
app/services/decision_providers/opponent_engine/planning/strategic_evaluator.rb
```

Реализована первоначальная система стратегической оценки.

Она учитывает:

- состояние штабов;
- HP, огневую мощь, дальность и топливо техники;
- характеристики и позиции взводов;
- доступные атаки и перемещения;
- возможности розыгрыша карт;
- ресурсы, свободные позиции и слоты;

- угрозы со стороны техники противника.

Для завершённой партии используются терминальные оценки:

```ruby
WIN_SCORE = 1_000_000
```

Реализованы механизмы оценки положения техники, свободных позиций для размещения новых подразделений, потенциальной совместной атаки и угроз со стороны противника.

Стратегическая оценка учитывает возможные перемещения техники, которые способны открыть атаку по вражеской технике или создать условия для совместной атаки.

Проведена первоначальная настройка весов и механизмов координации. Дальнейшая калибровка отложена до получения достаточного количества игровых наблюдений.

### TacticalPlanner

Файл:

```text
app/services/decision_providers/opponent_engine/planning/tactical_planner.rb
```

Реализован поиск последовательностей действий на основе Beam Search.

Параметры поиска:

```text
DEPTH = 5
WIDTH = 10
```

На каждом уровне поиска:

1. Формируются допустимые действия для текущего симулированного состояния.
2. Действия симулируются через `StateSimulator`.
3. Получается новое `VisibleState`.
4. Состояние оценивается через `StrategicEvaluator`.
5. Наиболее перспективные варианты сохраняются в пределах ширины поиска.
6. Поиск продолжается до заданной глубины или терминального действия.

План содержит последовательность действий, ожидаемое состояние после каждого шага и итоговую оценку.

Используется:

```ruby
Step = Data.define(:action, :expected_visible_state)
```

### ActionExecutor

Файл:

```text
app/services/decision_providers/opponent_engine/action_executor.rb
```

Реализовано получение и подготовка действия из рассчитанного плана.

Поддерживаются интерфейсы:

```ruby
ActionExecutor.call(plan:, context:)
```

```ruby
ActionExecutor.execute(plan:, context:, step_index: 0)
```

Результат `Execution` содержит действие, ожидаемое состояние и индекс следующего шага.

Перед выполнением проверяются индекс шага, наличие действий и шагов, их количество и соответствие действий в плане.

Для создания `GameEngine::Action` используется актуальный `context.state_digest`. Payload нормализуется из строковых ключей в символьные.

### Интеграция и выполнение плана

В `DecisionProviders::AI` добавлена поддержка:

```text
AI_PROVIDER=opponent_engine
```

Для собственного AI доступно получение решения вместе с планом через:

```ruby
call_with_plan
```

Результат `PlanDecision` содержит действие, план, ожидаемый `VisibleState` и индекс следующего шага.

В `Games::RunAiTurns` реализовано адаптивное выполнение плана.

Перед выполнением следующего шага проверяются:

- тот же ли игрок продолжает ход;
- существует ли ожидаемое состояние;
- не закончились ли шаги плана;
- соответствует ли фактический `VisibleState` ожидаемому;
- остаётся ли следующее действие допустимым согласно актуальному `ActionOptions`.

При сравнении состояний нормализуются поля времени:

```text
server_time
turn_started_at
remaining_time
```

Если состояние соответствует ожидаемому и действие остаётся допустимым, используется следующий шаг прежнего плана.

Если состояние изменилось или действие стало недопустимым, старый план очищается и выполняется новое планирование.

Все реальные действия проходят через `GameActionRunner`. Прямого изменения `GameState` со стороны AI нет.

План хранится в памяти текущего экземпляра сервиса. Отдельная таблица БД для хранения плана не добавлялась.

### Пауза между действиями

В `Games::RunAiTurns` реализована пауза между последовательными успешными действиями AI:

```ruby
ACTION_DELAY_SECONDS = 2.5
```

Пауза предназначена для отображения визуальных эффектов предыдущего действия до выполнения следующего.

Ожидание выполняется только между действиями, если AI продолжает ход, партия активна и лимит действий не достигнут.

Для тестов предусмотрена подмена `sleeper`.

Это временной механизм отображения, а не строгая синхронизация серверного выполнения с клиентской очередью анимаций.

### Интеграционная проверка повторного использования плана

Добавлен сценарий:

```text
native opponent engine reuses a plan to play two platoons
```

Проверено выполнение двух розыгрышей взводов из одного плана.

Результат тестового сценария:

```text
AI actions count: 4
Planner calls: 1
Events: platoon_played x2
```

AI выполнил два розыгрыша взводов, последующую атаку штаба и завершение хода, используя один рассчитанный план.

Браузерные партии показали, что собственный AI способен выполнять последовательности действий, перемещать технику и проводить атаки по штабу противника. В одной из проверенных партий давление на штаб привело к победе AI.

При этом наблюдались ситуации, в которых AI отправлял отдельную технику в атаку вместо подготовки группы. Также были выявлены возможности улучшить выбор момента совместной атаки и оценку резервных позиций.

Эти наблюдения зафиксированы как направления возможной будущей доработки, но не являются незавершёнными обязательными задачами текущего этапа.
