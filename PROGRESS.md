## Завершённые этапы

### Stage 16 — Players

`Player` одновременно account и игровая сущность. Реализованы регистрация, вход, выход, `has_secure_password`, `current_player`, session-based identity, header, публичные страницы, зарегистрированный `/statistics`, development command `bin/rails dev:create_game`. Отдельные `User`/Devise не используются.

### Stage 17 — Deck UI

Реализованы `Deck`, `DeckCard`, Deck Weight, Headquarters, `StarterDecks::Create`, стартовые колоды для зарегистрированных и гостей, каталог Cards, `/decks`, preview/editor, quantity, валидации, create/edit/destroy и browser UI. Гость просматривает starter Deck, но не управляет Deck.

### Stage 18 — Waiting / Started

Реализованы `/play`, выбор полной Deck, PvP UI, создание waiting Game и первого `GamePlayer`, `Matchmaking::FindOpponent`, безопасный `Join`, `StartGame`, cancel waiting, heartbeat, stale cleanup, guest lifecycle, VisibleState boundary и Turbo refresh. Проверен lifecycle Player/Guest → `/play` → waiting → Join → `StartGame` → started → first Action.

### Stage 19 — Human vs Human

Полный PvP lifecycle проверен пользователем в двух независимых браузерах. `Move`, `Attack`, `PlayCard`, `EndTurn`, `Surrender` проходят через Controller и Engine. `GameActionRunner` сохраняет только успешный результат. Turbo рассылает каждому игроку собственный `VisibleState`. Проверены причины завершения, пустые AvailableActions после окончания и защита скрытой информации.

### Stage 20 — Decision Provider

Реализованы `DecisionProviders::Base`, `Context`, `Human`, `AI`, `GameEngine::Action`, `GameActionRunner`, `VisibleState`, Groq adapter и OpenAI adapter. AI проверяет формат ответа, нормализует JSON payload и ограничивает попытки некорректного решения. Тесты адаптеров не требуют реальных API-запросов.

Текущая конфигурация: `AI_PROVIDER` по умолчанию `groq`, модель Groq по умолчанию `openai/gpt-oss-20b`; OpenAI adapter доступен как альтернатива. Ключи хранятся только в переменных окружения, не в Git.

## Stage 21 — AI в игровом процессе (НЕ завершён)

### 1. База, модели и постоянный AI-игрок

- `Game` поддерживает режимы `pvp` и `ai`.
- `Player` имеет признак `ai`; уникальный частичный индекс ограничивает количество постоянных AI-игроков одним.
- `AiPlayers::Setup` идемпотентно находит/создаёт игрока `ai@clash-tanks.local` с именем `ИИ`.
- `AiPlayers::DecksSetup` создаёт постоянные полные колоды из существующих карт:

| Колода | Нация | Вес |
|---|---|---:|
| `ИИ — США: лёгкая техника` | США | 13 |
| `ИИ — СССР: средняя техника` | СССР | 22 |
| `ИИ — Германия: тяжёлая техника` | Германия | 28 |

Колоды содержат по 10 карт с допустимым количеством копий. Настройка идемпотентна; игрок и колоды используются повторно между партиями.

### 2. Подбор совместимой колоды

`Matchmaking::AiDeckSelector` ищет полную AI-колоду с совместимым весом в диапазоне ±10%. Если подходит несколько колод, выбирает ближайшую по весу. Примерные целочисленные диапазоны: AI weight 13 → пользовательский вес 12–14; 22 → 20–24; 28 → 26–30.

### 3. AI-решение и безопасное выполнение Action

- `DecisionProviders::AI` получает контекст и возвращает `GameEngine::Action`; формат решения проверяется, ключи payload нормализуются. Для некорректного формата допускается максимум три попытки.
- Источник решения можно подменить в тестах; автоматические тесты не обращаются к реальному API.
- `GameActionRunner` выполняет действие под блокировкой игры, сравнивает `expected_state_digest` с актуальным состоянием и отклоняет устаревший Action. Состояние сохраняется только при успешном результате Engine.
- Существующие тесты `GameActionRunner` покрывают успешное сохранение, отказ Engine, waiting game, отказ устаревшего AI-действия без изменения state и принятие актуального digest.

### 4. Автоматический AI-цикл

`app/services/games/run_ai_turns.rb` (`Games::RunAiTurns`) реализован.

- Максимум 20 AI-действий за один запуск (`MAX_ACTIONS_PER_RUN`).
- Advisory lock на уровне PostgreSQL не позволяет одновременно выполнять несколько AI-циклов одной игры; независимые игры не блокируют друг друга.
- При устаревшем состоянии выполняются ограниченные повторы, максимум 3 (`MAX_STALE_STATE_RETRIES`).
- Перед каждым решением сервис перечитывает игру и проверяет статус, текущего игрока и лимит.
- Цикл завершается, когда игра больше не `started`, ход больше не принадлежит AI, достигнут лимит либо произошла ошибка.
- Возвращаются результат, события и число выполненных действий; события уже выполненных действий сохраняются в результате при последующей ошибке.
- Тесты покрывают конкурентный запуск, разные игры, освобождение lock, исключение provider, невалидное действие, частичный результат, лимит 0, retry stale state, исчерпание retries, завершение игры и переход хода человеку.

### 5. Подключение к GamesController и Turbo

- При открытии игры `GamesController#show` запускает AI, если игра активна и очередь принадлежит AI; после выполнения перечитывает игру.
- После успешного человеческого действия AI запускается, только если очередь перешла к AI и игра остаётся активной.
- События AI добавляются к событиям человеческого действия и передаются через существующий Turbo broadcast.
- Для каждого участника обновление строится через отдельный `GameEngine::VisibleState`; чужая рука и скрытая информация не раскрываются.
- Массив событий копируется перед объединением, чтобы не пытаться изменять замороженный массив.
- Controller tests покрывают безопасную реакцию на ошибку AI, повторный запуск после временной ошибки provider и broadcast события AI обоим игрокам.

## Архитектурные границы

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

```text
browser session → current_player → GamePlayer → Action.player_id → GameEngine
```

`GameEngine` — единственный арбитр правил. Controller организует процесс; AI выбирает действие; `GameActionRunner` безопасно применяет его; `VisibleState` ограничивает доступные данные. AI не изменяет state напрямую и не получает скрытые данные противника.
