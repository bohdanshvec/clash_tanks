# Архитектурные ограничения

Основной принцип:

**Engine определяет результат, UI отображает его.**

Сохранять существующую архитектуру:

```text
Decision Provider
      ↓
    Action
      ↓
GameActionRunner
      ↓
  GameEngine
      ↓
  GameState
```

Визуальные компоненты и эффекты не должны:

- изменять `GameState`;
- самостоятельно определять результат атаки;
- рассчитывать игровой урон;
- определять допустимость игровых действий;
- раскрывать скрытые данные противника.

UI использует события и разрешённое состояние (`VisibleState`).

Для собственного AI действуют дополнительные правила:

- AI работает только с разрешённой информацией из `VisibleState`.
- Планирование может симулировать гипотетические действия, но не изменять реальное игровое состояние.
- Для симуляции используется настоящий `GameEngine`.
- Реальное исполнение действий проходит через существующую игровую инфраструктуру.
- AI не должен обходить правила движка или самостоятельно разрешать запрещённые действия.
- Симуляции не должны создавать реальные записи в БД, запускать callbacks, отправлять Turbo broadcast или изменять статистику.
- Скрытые карты противника не должны становиться доступными для стратегического анализа или выбора действий.

# Stage 25 — собственный алгоритм AI-соперника

## Цель

Полностью заменить принятие решений внешними LLM/API собственным алгоритмом.

Новый AI должен:

- работать без внешних API и API-ключей;
- анализировать игровую ситуацию;
- оценивать стратегические цели;
- планировать последовательности действий;
- выполнять действия через существующую игровую архитектуру;
- адаптироваться к фактическому результату каждого действия;
- использовать только разрешённую информацию из `VisibleState`.

Качество стратегических решений проверяется не только автоматическими тестами, но и реальными партиями в браузере.

## 25.1. Архитектура

Основной поток:

```text
VisibleState
     ↓
ActionOptions
     ↓
TacticalPlanner
     ├── StateSimulator
     │        ↓
     │    GameEngine
     │        ↓
     │   VisibleState
     │
     └── StrategicEvaluator
              ↓
         Plan / Steps
              ↓
         ActionExecutor
              ↓
       Decision Provider
              ↓
            Action
              ↓
       GameActionRunner
              ↓
          GameEngine
              ↓
           GameState
```

Основные компоненты:

| Компонент | Назначение | Статус |
|---|---|---|
| `StateSimulator` | Изолированная симуляция через настоящий `GameEngine` | ВЫПОЛНЕНО |
| `ActionOptions` | Формирование допустимых вариантов действий из `VisibleState` | ВЫПОЛНЕНО |
| `StrategicEvaluator` | Оценка стратегической ценности состояния | РЕАЛИЗОВАН, ТРЕБУЕТ НАСТРОЙКИ |
| `TacticalPlanner` | Поиск последовательностей действий через Beam Search | ВЫПОЛНЕНО |
| `ActionExecutor` | Подготовка следующего действия плана | ВЫПОЛНЕНО |
| `Games::RunAiTurns` | Выполнение и повторное использование плана | ВЫПОЛНЕНО |

Подробное описание архитектуры и правил взаимодействия компонентов находится в `OPPONENT_ENGINE.md`.

## 25.2. StateSimulator — ВЫПОЛНЕНО

Файл:

```text
app/services/decision_providers/opponent_engine/planning/state_simulator.rb
```

Реализована изолированная симуляция гипотетических действий.

Основные обязанности:

- принимать `VisibleState`;
- проверять статус партии и текущего игрока;
- восстанавливать изолированное состояние для `GameEngine`;
- заменять скрытые карты заглушками;
- создавать `GameEngine::Action`;
- вызывать настоящий `GameEngine::Engine`;
- возвращать новое разрешённое состояние и события;
- не изменять исходный `VisibleState`.

Скрытые карты противника и неизвестные карты колод не становятся доступными для анализа AI.

### Исправление проверки принадлежности техники

В ходе проверки симуляции перемещения обнаружено несовпадение типов идентификаторов игрока: `player_id` техники мог быть строкой, а идентификатор действия — числом.

Исправлена проверка принадлежности техники в:

```text
GameEngine::Actions::Move
```

Сравнение идентификаторов учитывает их строковое представление.

Добавлена регрессионная проверка несовпадения типов ID. Также исправлены тестовые данные `StateSimulatorTest` и вызов `headquarters_participant` с использованием именованных аргументов.

Проверена симуляция перемещения через настоящий `GameEngine`.

Исправление не обходит игровые правила и не переносит проверку допустимости действий из движка в AI.

## 25.3. ActionOptions — ВЫПОЛНЕНО

Сервис формирует варианты действий на основании `available_actions` из `VisibleState`.

## 25.4. StrategicEvaluator — ПЕРВОНАЧАЛЬНАЯ РЕАЛИЗАЦИЯ

Файл:

```text
app/services/decision_providers/opponent_engine/planning/strategic_evaluator.rb
```

Реализована первоначальная система стратегической оценки.

Она учитывает:

- состояние штаба;
- HP, огневую мощь, дальность и топливо техники;
- характеристики взводов;
- позиции техники;
- доступные атаки и перемещения;
- возможности розыгрыша карт;
- ресурсы;
- доступные позиции и слоты;
- атакующий потенциал нескольких единиц техники;
- возможность открыть штабную атаку через перемещение техники;
- угрозу со стороны техники противника.

Для завершённой партии используются терминальные оценки:

```ruby
WIN_SCORE = 1_000_000
```

Оценка использует только разрешённую информацию из `VisibleState`. Скрытые карты противника не анализируются.

### Уже реализованные стратегические механизмы

- Оценка положения техники относительно штабов.
- Оценка свободных позиций рядом со своим штабом для размещения новой техники.
- Оценка потенциальной совместной атаки нескольких единиц техники по одной цели.
- Прогнозирование атакующих с учётом возможного перемещения.
- Оценка возможности перемещения разведчика для открытия атаки штаба по технике.
- Оценка угрозы от техники противника с моделированием возможного боя.

### Текущая проблема

Первоначальная модель оценки позиции и атакующего потенциала пока не обеспечивает желаемого стратегического поведения.

Браузерное тестирование выявило, что AI может преждевременно отправлять отдельную технику в атаку вместо сохранения сил и подготовки совместного наступления.

Также требуется проверить влияние оценки резервных позиций на выбор перемещений.

Свободная клетка рядом со штабом уже учитывается через `deployment_capacity_score`. При дальнейшей настройке нельзя повторно начислять бонус за освобождение той же клетки.

**Следующая работа над `StrategicEvaluator` должна сначала улучшить оценку позиции и накопления техники. Изменения планировщика не следует выполнять заранее, пока не проверено влияние новой оценки на выбор планов.**

## 25.5. TacticalPlanner — ВЫПОЛНЕНО

Файл:

```text
app/services/decision_providers/opponent_engine/planning/tactical_planner.rb
```

Реализован поиск последовательностей действий на основе Beam Search.

Начальные параметры:

```text
DEPTH = 5
WIDTH = 10
```

На каждом уровне поиска:

1. Получаются допустимые действия для текущего симулированного состояния.
2. Подходящие действия симулируются через `StateSimulator`.
3. Формируется новое `VisibleState`.
4. Состояние оценивается через `StrategicEvaluator`.
5. Наиболее перспективные варианты сохраняются в пределах ширины поиска.
6. Поиск продолжается до заданной глубины или терминального действия.

План сохраняет последовательность действий и ожидаемое состояние после каждого шага.

Используется:

```ruby
Step = Data.define(:action, :expected_visible_state)
```

Результат содержит:

- `actions`;
- `steps`;
- `score`;
- `expanded_nodes`.

`end_turn`, завершение партии или переход хода являются терминальными условиями поиска. Планировщик не моделирует действия противника после завершения хода AI.

Параметры глубины и ширины поиска могут быть пересмотрены после настройки стратегической оценки и проверки производительности.

## 25.8. Адаптивное выполнение плана — ВЫПОЛНЕНО

Файл:

```text
app/services/games/run_ai_turns.rb
```

Реализовано хранение и повторное использование плана в течение хода AI.

Перед выполнением следующего шага проверяются:

1. Тот же ли игрок продолжает ход.
2. Существует ли ожидаемое состояние.
3. Не закончились ли шаги плана.
4. Соответствует ли фактический `VisibleState` ожидаемому.
5. Остаётся ли следующее действие допустимым согласно актуальному `ActionOptions`.

При сравнении состояний нормализуются поля времени:

```text
server_time
turn_started_at
remaining_time
```

Если состояние соответствует ожидаемому и действие остаётся допустимым, используется следующий шаг прежнего плана.

Если состояние изменилось или действие стало недопустимым, старый план очищается и выполняется новое планирование.

Все реальные действия проходят через:

```text
GameActionRunner
```

`Games::RunAiTurns` не изменяет `GameState` напрямую.

План хранится в памяти текущего экземпляра сервиса. Отдельная таблица БД для хранения плана не добавлялась.

### Интеграционная проверка

Добавлен сценарий:

```text
native opponent engine reuses a plan to play two platoons
```

Тест проверяет два последовательных розыгрыша взводов из одного плана.

Фактический результат:

```text
AI actions count: 4
Planner calls: 1
Events: platoon_played x2
```

В рамках одного плана AI выполнил два розыгрыша взводов, последующую атаку штаба и завершение хода.

Это подтверждает повторное использование плана при совпадении ожидаемого и фактического состояния.

## 25.9. Пауза между действиями AI — ВЫПОЛНЕНО

В `Games::RunAiTurns` реализована пауза между последовательными успешными действиями AI.

Текущая величина:

```ruby
ACTION_DELAY_SECONDS = 2.5
```

Пауза нужна для отображения визуальных эффектов предыдущего действия до выполнения следующего.

Ожидание выполняется только между действиями, если AI продолжает ход, партия активна и лимит действий не достигнут.

Для тестов предусмотрена подмена `sleeper`.

Пауза не гарантирует завершение длинной клиентской очереди анимаций. Она является временным компромиссом, а не строгим механизмом синхронизации клиента и сервера.

Ожидание занимает время серверного запроса и удерживает используемые ресурсы, включая соединение с БД и advisory lock. При дальнейшей оптимизации можно рассмотреть фоновое выполнение без добавления Redis.

## 25.10. Браузерная проверка и стратегические недостатки

Браузерное тестирование подтвердило:

- собственный AI способен перемещать технику;
- AI выполняет атаки по штабу противника;
- в одной из проверенных партий давление на штаб привело к победе AI.

При этом выявлены следующие проблемы:

1. AI не накапливает технику достаточно эффективно. Вместо подготовки группы каждый ход может отправлять одну единицу техники в атаку.
2. AI недостаточно хорошо координирует несколько танков.
3. AI может атаковать штабом штаб противника, не используя возможность сначала атаковать опасную технику.
4. AI не всегда учитывает, что перемещение собственной техники может обеспечить разведку и открыть штабную атаку по технике противника.
5. Оценка резервных позиций может провоцировать неоправданное отступление с передовых позиций.
6. Требуется улучшить оценку освобождения клеток рядом со штабом для размещения новой техники.

Для совместной атаки уже реализовано прогнозирование потенциальных атакующих: учитываются не только техники, способные атаковать цель из текущей позиции, но и техники, которые могут переместиться на подходящую позицию.

Также реализована оценка возможности перемещения техники для открытия штабной атаки по вражеской технике.

Эти изменения расширяют анализ потенциальных атак, но пока не гарантируют правильного накопления сил и выбора момента для совместного наступления.

### Приоритет стратегического поведения

Главный приоритет:

**Сначала накопление техники и формирование боеспособной группы, затем совместная атака техники и штаба.**

При этом:

- не отправлять каждый танк в одиночную атаку без явной выгоды;
- учитывать сохранение атакующей техники;
- оценивать возможность поддержки другими танками;
- грамотно освобождать клетки рядом со штабом для новой техники;
- оценивать позицию перемещаемого танка с учётом продвижения, поддержки и подготовки будущей группировки;
- не давать резервной позиции самостоятельный бонус, провоцирующий отступление;
- не учитывать ценность освобождённой клетки дважды;
- не добавлять отдельный бонус за карту в руке до проверки базовой модели;
- сохранять возможность одиночной атаки, если она позволяет уничтожить опасную цель или даёт явное преимущество;
- не повышать искусственно вес совместной атаки до проверки поведения накопления техники.

Свободная клетка рядом со штабом является постоянным стратегическим ресурсом. Её ценность не должна зависеть исключительно от наличия карты техники в руке.

Доступная для розыгрыша техника может повышать срочность освобождения клетки, но не должна определять базовую ценность самой клетки.
