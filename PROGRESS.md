# Архитектурные ограничения

Основной принцип:

**Engine определяет результат, UI отображает его.**

Сохранять существующую архитектуру:

```text
Decision Provider
      ↓
    Action
      ↓
GameActionRunner
      ↓
  GameEngine
      ↓
  GameState
```

Основные ограничения:

- UI, Stimulus, Turbo и AI не изменяют `GameState` напрямую.
- Только `GameEngine` определяет результат игровых действий.
- Проверка допустимости действий остаётся ответственностью игрового движка.
- UI использует события и разрешённое состояние `VisibleState`.
- AI анализирует только разрешённую информацию из `VisibleState`.
- Симуляция гипотетических действий не изменяет реальное состояние партии.
- Для симуляции используется настоящий `GameEngine`.
- Симуляции не должны создавать реальные записи в БД, запускать callbacks, отправлять Turbo broadcast или изменять статистику.
- Скрытые карты противника и неизвестные карты колод не должны становиться доступными AI.

### Эффект добора карт

Реализован отдельный Stimulus-контроллер:

```text
card_draw_effect_controller.js
```

После события `card_drawn` новые карты в руке игрока подсвечиваются двумя последовательными вспышками контура.

Поддерживаются:

- добор карт в начале хода;
- добор приказом «Взять 2 карты»;
- обработка нескольких карт за одно действие;
- определение количества подсвечиваемых карт по количеству событий `card_drawn`.

Подсвечиваются последние N карт в руке игрока, где N соответствует количеству полученных событий.

Эффект работает до обновления руки через Turbo Stream и не изменяет игровое состояние.

Повторное воспроизведение эффекта для уже обработанных событий не допускается.

### ActionOptions

Реализована система стратегической оценки, учитывающая:

Для завершённой партии используются терминальные оценки:

```ruby
WIN_SCORE = 1_000_000
```

#### Наступательная группировка

Реализована оценка взаимодействия нескольких единиц техники.

В расчёт входят:

- взаимная дистанция между подразделениями;
- огневая мощь;
- продвижение поддерживающей техники к авангарду;
- положение относительно штабов;
- текущее состояние HP.

Критически повреждённая техника больше не исключается из наступательной группировки по жёсткому порогу HP.

Вместо этого используется пропорциональное снижение её вклада:

| HP техники | Доля вклада в оценку |
|---:|---:|
| 4 и более | 100% |
| 3 | 75% |
| 2 | 50% |
| 1 | 25% |
| 0 | 0% |

Таким образом, повреждённая, но ещё действующая техника сохраняет часть стратегической ценности. При уничтожении её вклад обнуляется.

#### Другие стратегические оценки

Реализованы:

- оценка наступательной линии;
- оценка возможности размещения новых подразделений;
- оценка штабной атаки;
- оценка потенциальной совместной атаки;
- оценка будущих возможностей координации;
- оценка угроз противника с учётом результатов симуляции атак.

Проведена первоначальная настройка весов и механизмов координации. В частности, уменьшена избыточная мотивация освобождать позиции рядом со штабом: наличие хотя бы одной свободной позиции учитывается как возможность размещения, без накопления прежнего бонуса за каждую свободную клетку.

Для отдельных типов техники предусмотрены дополнительные ролевые оценки, учитывающие специализацию против танков и артиллерийские возможности.

#### Координация штабной атаки и техники

Проверена последовательность, в которой штаб атакует первым, принимает контратаку, а затем собственная техника уничтожает ослабленную цель.

Для этого используется симуляция последствий атак через настоящий `GameEngine::Attacks::CombatExecutor`.

Безусловный приоритет атаки штабом не вводился. Оценка должна учитывать результат последовательности действий и риск ответного огня.

Регрессионный сценарий подтвердил преимущество последовательности HQ → техника в проверенной ситуации, где атака техникой первой приводила к её уничтожению от контратаки.

### TacticalPlanner

```text

Последние известные параметры поиска:

```

На каждом уровне поиска:

1. Формируются допустимые действия для текущего симулированного состояния.
2. Действия симулируются через `StateSimulator`.
3. Получается новое `VisibleState`.
4. Состояние оценивается через `StrategicEvaluator`.
5. Наиболее перспективные варианты сохраняются в пределах ширины поиска.
6. Поиск продолжается до заданной глубины или терминального действия.

План содержит последовательность действий, ожидаемое состояние после каждого шага и итоговую оценку.

Используется:

```ruby
Step = Data.define(:action, :expected_visible_state)
```

### ActionExecutor

Файл:

```text
app/services/decision_providers/opponent_engine/action_executor.rb
```

Реализовано получение и подготовка действия из рассчитанного плана.

Поддерживаются интерфейсы:

```ruby
ActionExecutor.call(plan:, context:)
```

```ruby
ActionExecutor.execute(plan:, context:, step_index: 0)
```

Результат `Execution` содержит действие, ожидаемое состояние и индекс следующего шага.

Перед выполнением проверяются индекс шага, наличие действий и шагов, их количество и соответствие действий в плане.

Для создания `GameEngine::Action` используется актуальный `context.state_digest`. Payload нормализуется из строковых ключей в символьные.

### Интеграция и адаптивное выполнение плана

`DecisionProviders::AI` использует собственный `OpponentEngine`.

Получение решения вместе с планом выполняется через:

```ruby
call_with_plan
```

Метод вызывает `TacticalPlanner`, передаёт построенный план в `ActionExecutor` и возвращает `PlanDecision`.

Результат `PlanDecision` содержит:

- действие;
- план;
- ожидаемый `VisibleState`;
- индекс следующего шага.

`Games::RunAiTurns` поддерживает адаптивное выполнение плана.

Перед выполнением следующего шага проверяются:

- тот же ли игрок продолжает ход;
- существует ли ожидаемое состояние;
- не закончились ли шаги плана;
- соответствует ли фактический `VisibleState` ожидаемому;
- остаётся ли следующее действие допустимым согласно актуальному `ActionOptions`.

При сравнении состояний нормализуются поля времени:

```text
server_time
turn_started_at
remaining_time
```

Если состояние соответствует ожидаемому и действие остаётся допустимым, используется следующий шаг прежнего плана.

Если состояние изменилось или действие стало недопустимым, старый план очищается и выполняется новое планирование.

Все реальные действия проходят через `GameActionRunner`. Прямого изменения `GameState` со стороны AI нет.

План хранится в памяти текущего экземпляра сервиса. Отдельная таблица БД для хранения плана не добавлялась.

### Пауза между действиями

В `Games::RunAiTurns` реализована пауза между последовательными успешными действиями AI:

```ruby
ACTION_DELAY_SECONDS = 2.5
```

Пауза предназначена для отображения визуальных эффектов предыдущего действия до выполнения следующего.

Ожидание выполняется только между действиями, если AI продолжает ход, партия активна и лимит действий не достигнут.

Для тестов предусмотрена подмена `sleeper`.

Это временной механизм отображения, а не строгая синхронизация серверного выполнения с клиентской очередью анимаций.

### Интеграционная проверка повторного использования плана

Добавлен сценарий:

```text
native opponent engine reuses a plan to play two platoons
```

Проверено выполнение двух розыгрышей взводов из одного плана.

Результат тестового сценария:

```text
AI actions count: 4
Planner calls: 1
Events: platoon_played x2
```

AI выполнил два розыгрыша взводов, последующую атаку штаба и завершение хода, используя один рассчитанный план.

### Выявленная проблема: неоправданное отступление повреждённой техники

В реальных партиях наблюдались ситуации, когда повреждённая техника отступала вместо продолжения наступления или участия в совместной атаке.

В `StrategicEvaluator` уже выполнена коррекция: вклад повреждённой техники в наступательную группировку теперь уменьшается пропорционально HP, а не обнуляется при достижении фиксированного порога.

Однако пока нельзя утверждать, что эта коррекция полностью устраняет отступления.

Возможные причины требуют проверки на фактических игровых ситуациях:

- оценка угрозы со стороны противника;
- соотношение риска и стратегической ценности позиции;
- оценки перемещения и продолжения атаки;
- влияние состояния HP на итоговую оценку последовательности действий;
- результаты симуляции альтернативных планов.

Для дальнейшего анализа предусмотрено диагностическое логирование в:

```text
app/services/decision_providers/opponent_engine/planning/tactical_planner.rb
app/services/decision_providers/opponent_engine/planning/strategic_evaluator.rb
```

Логирование должно позволить сопоставлять исходные позиции, рассматриваемые действия, результаты симуляций, составляющие стратегической оценки и выбранный план.

Диагностика не должна менять поведение AI, раскрывать скрытые данные противника или изменять игровое состояние.

Причины отступления считаются установленными только после анализа соответствующих логов.
