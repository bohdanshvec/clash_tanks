# DEVELOPMENT.md

## Порядок работы

Перед изменением кода прочитать `AGENTS.md` и этот файл; затем — документы по задаче из таблицы в `AGENTS.md`.

Существенные изменения предварительно обсуждать с пользователем.

Вносить только необходимые изменения. Не выполнять рефакторинг без конкретной причины.

Добавлять или обновлять тесты, если изменяемое поведение ещё не покрыто существующими проверками.

После завершения существенного этапа, затрагивающего игровую логику или серверное поведение, запускать:

```bash
bin/rails test
```

Для UI работать маленькими шагами и после существенных UI-изменений проверять результат непосредственно в браузере.

Для визуальных эффектов проверять не только внешний вид, но и последовательность событий, блокировку повторных действий и корректность обновления интерфейса.

После значимого этапа делать Git commit.

Без явной команды пользователя не изменять файлы проекта.

Результат проверки относится к конкретному состоянию локальной базы данных.

## Обязательные технические запреты

- Не переносить игровую логику в Controllers, ActiveRecord, UI, Stimulus/JavaScript, Turbo/Action Cable или AI.
- Не мутировать исходный `GameState`, не хранить его в session/cookies и не сохранять каждое промежуточное изменение.
- Не изменять persistent `Deck` во время партии, не хранить runtime `Platoon` в field и не уплотнять `Platoon` slots.
- Не создавать `TechniqueAbility`, `HeadquartersAbility`, отдельный HQ level, отдельную систему spotting для HQ, Draw Action, отдельную систему победы или surrender.
- Не раскрывать hidden information через `VisibleState`; не вычислять `AvailableActions` в Stimulus; CSS и JavaScript не являются механизмами безопасности.
- Не использовать `?player_id=` или dev-player ID для пользовательской идентификации.
- Не считать координаты постоянным ID `Technique`, визуальный порядок клеток — логическими координатами, либо `movement_count` — counterattack.
- Не передавать `Platoon` slot из UI в `play_card`; Drag & Drop не является отдельной системой правил.
- Не менять логические координаты ради перспективы, не использовать `transform: rotate(180deg)` и не дублировать перспективу в Stimulus.
- Не создавать AI-соперника автоматически в PvP; не превращать список waiting players в ручной выбор комнаты.
- Не хранить matchmaking metadata в `GameState`, не считать `Game.last_seen_at` игровой механикой, не удалять started/finished games waiting-cleanup.
- Не создавать отдельный Engine или отдельную игровую систему для гостей.

Игровые запреты и точные правила дополнительно определяются `GAME_RULES.md`; архитектурная мотивация — `ARCHITECTURE.md`.

## Диагностика собственного AI

Текущий AI использует собственный `OpponentEngine`. Внешний LLM-провайдер не участвует в обычном принятии решений.

Основные компоненты:

- `DecisionProviders::AI` — точка входа;
- `DecisionProviders::Context` — подготовка доступного состояния;
- `DecisionProviders::ActionOptions` — получение допустимых действий;
- `OpponentEngine::Planning::TacticalPlanner` — построение плана;
- `OpponentEngine::ActionExecutor` — выбор и исполнение следующего шага;
- `Games::RunAiTurns` — управление циклом действий AI.

При диагностике:

1. Проверять, какие допустимые действия переданы AI.
2. Проверять построенный план и выбранный шаг.
3. Проверять результат симуляции действий.
4. Проверять соответствие ожидаемого и фактического `VisibleState`.
5. Проверять, что действие проходит через `GameActionRunner`.
6. Проверять журналы `Games::RunAiTurns` и компонентов `OpponentEngine`.

Не переносить применение игровых действий в `OpponentEngine`: он формирует решения, а применение выполняется общим игровым механизмом.

Тесты AI должны использовать контролируемые состояния и не зависеть от внешних API.

## Графические ресурсы карт

Основной документ художественного оформления:

```text
ART_STYLE.md
```

Перед изменением изображений, рамок, обозначений или визуальных эффектов необходимо сверяться с ним.

### Утверждённые форматы

Для графических ресурсов карт используются два исходных формата.

| Формат | Размер | Назначение |
|---|---|---|
| `field` | 1024 × 1024 px | Штабы, техника и взводы на игровом поле |
| `card` | 848 × 1264 px | Каталог, колоды, редактор и рука игрока |

Приказы используют только вертикальный формат.

Размеры относятся к исходным ресурсам.

Фактический размер отображения определяется HTML/CSS.

Не создавать отдельные PNG для разных CSS-размеров одного изображения.

### Структура каталогов

Утверждённая структура:

```text
app/assets/images/cards/
├── germany/
│   ├── headquarters/
│   ├── technique/
│   ├── order/
│   └── platoon/
├── usa/
│   ├── headquarters/
│   ├── technique/
│   ├── order/
│   └── platoon/
└── ussr/
    ├── headquarters/
    ├── technique/
    ├── order/
    └── platoon/
```

Не создавать параллельные каталоги для тех же ресурсов без необходимости.

### Именование иллюстраций

Использовать схему:

```text
{nation}_{display}_{type}_{card_code_without_nation_and_type_prefix}.png
```

Где:

- `nation` — код нации;
- `display` — `field` или `card`;
- `type` — тип карты;
- последняя часть — код карты без префиксов нации и типа.

Примеры:

```text
usa_field_headquarters_second_front.png
usa_card_headquarters_second_front.png
usa_field_technique_m3_lee_grant.png
usa_card_technique_m3_lee_grant.png
usa_card_order_lend_liz.png
germany_field_headquarters_operation_weiß.png
```

### Именование рамок

Основная схема:

```text
{nation}_{display}_{type}_border.png
```

Для рамок с вариантами:

```text
{nation}_{display}_{type}_{variant}_border.png
```

Варианты рамок зависят от типа карты:

- `Headquarters` — обычная рамка и вариант `ability`.
- `Technique` — обычная рамка и вариант `ability`.
- `Order` — обычная рамка.
- `Platoon` — варианты `attack` и `defense`.

Вариант выбирается по актуальным данным карты.

Не выбирать вариант по произвольному условию интерфейса.

### Универсальные helpers изображений

Для формирования путей используются:

```ruby
card_image_path(
  nation:,
  display:,
  type:,
  code:
)

card_border_path(
  nation:,
  display:,
  type:,
  variant: nil
)
```

Helpers должны соответствовать утверждённой структуре каталогов.

Не дублировать формирование путей непосредственно в каждом ERB-шаблоне.

Перед изменением helper необходимо проверить его существующий контракт и места использования.

### Unicode в кодах карт

Коды карт могут содержать Unicode-символы.

Подтверждённый пример:

```text
germany_headquarters_operation_weiß
```

Соответствующий путь:

```text
cards/germany/headquarters/germany_field_headquarters_operation_weiß.png
```

Нельзя ограничивать допустимые символы только ASCII, если это исключает корректные коды карт.

Для проверки буквенно-цифровых кодов с подчёркиваниями допускается Unicode-aware выражение:

```ruby
/\A[\p{L}\p{N}_]+\z/u
```

Не выполнять произвольную транслитерацию кодов.

Не заменять `ß` на `ss` при формировании имени файла.

### Многослойное отображение карт

Основная схема:

1. Иллюстрация.
2. Прозрачная рамка.
3. Условные обозначения.
4. Динамические характеристики.
5. Индикаторы и визуальные эффекты.

Фактический набор слоёв зависит от типа карты.

### Источники данных

Иллюстрация и рамка определяются по данным карты.

Динамические характеристики определяются по актуальному разрешённому состоянию игры.

Не использовать PNG как источник текущих игровых значений.

Не переносить вычисление допустимых действий в CSS или JavaScript.

### Определение изображения по `card_id`

Для игровых объектов, содержащих `card_id`, необходимо использовать соответствующий код карты.

Не выбирать иллюстрацию только по нации, если внутри одной нации существует несколько карт соответствующего типа.

При необходимости коды карт могут быть подготовлены на сервере для представления.

Не добавлять в клиентское состояние скрытые данные противника ради отображения иллюстраций.

### Динамические характеристики

Для штабов и техники используются предусмотренные рамкой характеристики:

- огневая мощь;
- HP;
- топливо.

Значения берутся из актуального состояния.

Утверждённое правило:

- `0` — характеристика существует и равна нулю;
- `–` — характеристика неприменима.

Не заменять числовой ноль прочерком.

Не добавлять в интерфейс характеристики, которых нет в данных карты или игровом состоянии.

### Индикаторы и визуальные правила

Правила отображения огневой мощи, движения, способностей, классов техники и взводов определены в `ART_STYLE.md`.

Не дублировать в этом документе подробные визуальные спецификации. При изменении этих элементов проверять актуальные решения и согласованность с `ART_STYLE.md`.

## Боевые события и визуальные эффекты

Визуальные эффекты игрового поля должны отображать уже произошедшие игровые события.

Они не определяют правила, не рассчитывают урон и не изменяют `GameState`.

### Архитектура обработки

Основной принцип:

```text
GameEngine
    ↓
Боевые события
    ↓
Серверное представление событий
    ↓
UI / Stimulus
    ↓
Очередь визуальных эффектов
    ↓
DOM-анимации
```

`GameEngine` остаётся единственным источником игровых решений.

UI получает события и воспроизводит соответствующие визуальные эффекты.

Не переносить обработку боевых правил в контроллер визуальных эффектов.

Не определять результат атаки, контратаки или повреждения на стороне браузера.

### Контракт событий

В Stage 24 используются следующие типы боевых событий:

- `shot_fired`;
- `counterattack_fired`;
- `damage_applied`;
- `technique_destroyed`;
- `platoon_damaged`;
- `platoon_destroyed`;
- `empty_deck_draw_attempt`.

Также сохраняются необходимые legacy-события.

Не удалять и не переименовывать существующие события без проверки всех потребителей и согласования изменения контракта.

События должны содержать данные, необходимые для отображения соответствующего эффекта, но не должны раскрывать скрытую информацию противника.

### Источник и последствия урона

При отображении урона учитывать источник события.

Для урона от попытки взять карту из пустой колоды используется источник:

```ruby
{ type: "empty_deck_draw" }
```

Не определять источник урона по косвенным признакам интерфейса.

Не смешивать урон от атаки, контратаки и пустой колоды.

Контракт события `damage_applied` и связанные события должны оставаться согласованными с фактическим результатом `GameEngine`.

### Очередь визуальных эффектов

Визуальные эффекты должны обрабатываться последовательно через очередь.

При работе с очередью:

- не запускать параллельную обработку одной очереди;
- не воспроизводить одно событие повторно без предусмотренной причины;
- сохранять порядок поступивших событий;
- корректно завершать обработку текущего эффекта перед переходом к следующему;
- учитывать блокировку повторных пользовательских действий во время критической последовательности;
- освобождать блокировку после завершения обработки;
- учитывать отсутствие DOM-элемента, необходимого для конкретного эффекта;
- не допускать бесконечного ожидания незавершённой анимации.

Очередь отвечает только за последовательность отображения.

Она не является механизмом синхронизации или сохранения игрового состояния.

При изменении очереди сначала изучить существующую реализацию контроллера и контракт событий. Не заменять её новой системой без конкретной причины.

Основной контроллер визуальных боевых эффектов:

```text
game_combat_effects_controller.js
```

Перед изменением проверять актуальные методы, DOM-якоря и места подключения контроллера.

### Эффект добора карт

Для визуального отображения новых карт используется отдельный контроллер:

```text
card_draw_effect_controller.js
```

Он обнаруживает события `card_drawn` перед Turbo Stream обновлением и выделяет новые карты в руке текущего игрока.

Подсветка выполняется CSS-анимацией с двумя вспышками контура, визуально согласованными с эффектом выбранной карты.

Количество выделяемых карт определяется количеством соответствующих событий добора.

Ограничения:

- не изменять `GameEngine` ради визуального эффекта;
- не изменять контракт боевых событий ради добора;
- не вмешиваться в `game_events_controller.js`;
- не изменять содержимое игровой руки;
- не воспроизводить эффект для карт противника;
- не допускать повторного запуска анимации для уже полученных карт.

При изменении механизма добора проверять корректность определения игрока, количества карт и поведения после Turbo Stream обновления.

### Отображение перемещения техники

Событие перемещения техники должно визуально отображаться обоим игрокам.

Направление эффекта определяется фактическим перемещением объекта.

Не изменять логические координаты ради визуального направления.

Не использовать поворот всего игрового поля для имитации перспективы.

### Проверка боевых эффектов

Для каждого нового или изменённого эффекта проверять:

1. Правильность типа события.
2. Правильность источника и цели.
3. Соответствие визуального эффекта фактическому результату.
4. Последовательность воспроизведения.
5. Отсутствие повторного запуска одного эффекта.
6. Отсутствие одновременной обработки очереди.
7. Корректное завершение анимации.
8. Снятие блокировки интерфейса.
9. Поведение при отсутствии целевого DOM-элемента.
10. Отображение результата обоим игрокам, если событие должно быть им доступно.

Если меняется контракт события или серверная логика, дополнительно запускать соответствующие автоматические тесты.

Не считать успешное воспроизведение анимации подтверждением правильности игровой логики.

## CSS и Propshaft

Проект использует Rails 8 и Propshaft.

Перед изменением системы стилей необходимо изучить существующие файлы и способ их подключения.

Не создавать дополнительную систему сборки CSS без необходимости.

### Компоненты

CSS-компоненты размещаются в:

```text
app/assets/stylesheets/components/
```

Для отображения штабов используется:

```text
app/assets/stylesheets/components/headquarters-field.css
```

Для отображения техники используется:

```text
app/assets/stylesheets/components/technique-field.css
```

Подключение компонентов должно соответствовать существующей структуре `application.css`.

### Добавление нового CSS-файла

Перед подключением нового компонента:

1. Создать файл.
2. Проверить правильность имени.
3. Проверить расположение.
4. Проверить способ подключения.
5. Проверить доступность для Propshaft.
6. Проверить загрузку в браузере.

Не добавлять импорт несуществующего файла.

### Ошибка MissingAssetError

В ходе Stage 24 наблюдалась ошибка:

```text
Propshaft::MissingAssetError:
The asset 'components/technique-field.css'
was not found in the load path.
```

После выполнения:

```bash
bin/rails assets:precompile
```

пользователь подтвердил запуск игры.

Это подтверждает успешный запуск после сборки, но не устанавливает окончательную причину первоначальной ошибки.

Не считать `assets:precompile` универсальным решением ошибок подключения CSS.

При повторном возникновении ошибки необходимо проверить:

1. Существует ли файл.
2. Правильно ли указан путь.
3. Подключён ли каталог к системе ассетов.
4. Как обрабатываются CSS-импорты.
5. Не используются ли устаревшие предварительно собранные ресурсы.

### Development и production

В development необходимо проверить корректную загрузку новых ресурсов.

В production сборка ассетов должна выполняться в процессе развёртывания приложения.

После обновления приложения необходимо убедиться, что:

- новые CSS-файлы доступны;
- изображения доступны;
- пути соответствуют fingerprinted assets;
- браузер не использует устаревшие ресурсы;
- отсутствуют ошибки загрузки.

Не переносить вручную файлы из `public/assets` как замену корректной конфигурации сборки.

## Полноэкранный режим

Для полноэкранного режима используется Stimulus-контроллер:

```text
site_fullscreen_controller.js
```

Контроллер отвечает за переключение fullscreen и отображение актуального текста кнопок.

После Turbo-обновлений необходимо синхронизировать состояние всех доступных кнопок, поскольку Turbo может заменить часть DOM и вернуть серверный текст кнопки по умолчанию.

Ограничения:

- не связывать полноэкранный режим с игровым состоянием;
- не изменять разметку игровых объектов ради fullscreen;
- корректно обновлять текст и `aria-pressed`;
- учитывать повторное подключение DOM-элементов после Turbo-обновлений.

При изменении контроллера проверять вход и выход из fullscreen, а также обновление текста кнопки после Turbo Stream и Turbo render.

## Проверка визуальных компонентов

После изменения изображений, рамок или CSS:

1. Проверить отсутствие ошибок Rails.
2. Проверить загрузку ресурсов.
3. Проверить правильность слоёв.
4. Проверить прозрачность.
5. Проверить расположение характеристик.
6. Проверить отображение нулевых значений.
7. Проверить цветовые индикаторы.
8. Проверить игровые действия.
9. Проверить Turbo-обновления.
10. Проверить отображение на разных размерах экрана.

### Проверка техники

Для квадратных карт техники дополнительно проверять:

- название;
- национальную рамку;
- иллюстрацию;
- обозначение класса;
- индикаторы движения;
- огневую мощь;
- HP;
- топливо;
- индикатор способности;
- обновление состояния после перемещения;
- обновление состояния после атаки;
- обновление состояния после контратаки.

При проверке учитывать собственную и вражескую технику, все три нации и поддерживаемые классы техники.

### Проверка взводов

Для квадратных карт взводов дополнительно проверять:

- четыре слота;
- правильный вариант рамки `attack` или `defense`;
- символ типа взвода;
- отображение огневой мощи или брони;
- корректность характеристик;
- визуальные эффекты при размещении;
- визуальные эффекты при повреждении;
- визуальные эффекты при уничтожении;
- расположение элементов для обоих игроков.

Не изменять правила размещения взводов ради визуального оформления.
