# DEVELOPMENT.md

## Порядок работы

Перед изменением кода прочитать `AGENTS.md` и этот файл; затем — документы по задаче из таблицы в `AGENTS.md`.

Существенные изменения предварительно обсуждать с пользователем.

Вносить только необходимые изменения. Не выполнять рефакторинг без конкретной причины.

Добавлять или обновлять тесты, если изменяемое поведение ещё не покрыто существующими проверками.

После завершения существенного этапа, затрагивающего игровую логику или серверное поведение, запускать:

```bash
bin/rails test
```

Для UI работать маленькими шагами и после существенных UI-изменений проверять результат непосредственно в браузере.

После значимого этапа делать Git commit.

Без явной команды пользователя не изменять файлы проекта.

GitHub используется исключительно для чтения.

Не выполнять через подключённый GitHub:

- создание коммитов;
- создание веток;
- создание pull request;

Актуальные локальные файлы пользователя имеют приоритет перед удалённой версией, если пользователь сообщает о расхождении.

## Обязательные технические запреты

- Не переносить игровую логику в Controllers, ActiveRecord, UI, Stimulus/JavaScript, Turbo/Action Cable или AI.
- Не мутировать исходный GameState, не хранить его в session/cookies и не сохранять каждое промежуточное изменение.
- Не изменять persistent Deck во время партии, не хранить runtime Platoon в field и не уплотнять Platoon slots.
- Не создавать TechniqueAbility, HeadquartersAbility, отдельный HQ level, отдельную систему spotting для HQ, Draw Action, отдельную систему победы или surrender.
- Не раскрывать hidden information через VisibleState; не вычислять AvailableActions в Stimulus; CSS и JavaScript не являются механизмами безопасности.
- Не использовать `?player_id=` или dev-player ID для пользовательской идентификации.
- Не считать координаты постоянным ID Technique, визуальный порядок клеток — логическими координатами, либо movement_count — counterattack.
- Не передавать Platoon slot из UI в play_card; Drag & Drop не является отдельной системой правил.
- Не менять логические координаты ради перспективы, не использовать `transform: rotate(180deg)` и не дублировать перспективу в Stimulus.
- Не создавать AI-соперника автоматически в PvP; не превращать список waiting players в ручной выбор комнаты.
- Не хранить matchmaking metadata в GameState, не считать Game.last_seen_at игровой механикой, не удалять started/finished games waiting-cleanup.
- Не создавать отдельный Engine или отдельную игровую систему для гостей.

Игровые запреты и точные правила дополнительно определяются `GAME_RULES.md`; архитектурная мотивация — `ARCHITECTURE.md`.

## Диагностика AI-провайдера Groq

Основной провайдер выбирается через `AI_PROVIDER`; текущая настройка по умолчанию — `groq`.

Модель по умолчанию:

```text
openai/gpt-oss-20b
```

API-ключ хранится в `GROQ_API_KEY` в локальном окружении.

Не добавлять ключи, содержимое `.env` или секреты в Git, логи, тестовые фикстуры и сообщения об ошибках.

Для тестирования GroqAdapter использовать fake HTTP transport.

Автоматические тесты не должны обращаться к реальному API.

Перед исправлением ошибки:

1. Запустить целевой тест:

   ```bash
   bin/rails test test/services/decision_providers/groq_adapter_test.rb
   ```

2. Записать фактический результат теста.
3. Изучить HTTP-статус, код ошибки, доступные rate-limit headers и сообщение API.
4. Проверить, не изменился ли контракт Groq для выбранной модели.
5. Исправлять только подтверждённую проблему.

Различать следующие случаи:

- **HTTP 429** — ограничение частоты запросов или токенов. Проверять заголовки и информацию о задержке; не выполнять бесконечные повторы.
- **HTTP 400 `json_validate_failed`** — ошибка проверки запроса или JSON-режима. Не считать её превышением TPM без подтверждающих данных.
- **HTTP 5xx** — ошибка сервера API; обрабатывать согласно контракту адаптера, не превращая её в бесконечный цикл повторов.
- **Timeout/network error** — ошибка соединения или ожидания ответа.

GroqAdapter логирует token usage успешных ответов и диагностические данные HTTP-ошибок.

Не записывать в логи API-ключи или секреты.

Если completion tokens неожиданно велики, сначала проверить фактическое использование и поддерживаемые моделью параметры API.

Не добавлять `max_completion_tokens` или `max_tokens` без проверки совместимости.

Не объявлять проблему исправленной только по изменению кода.

Требуются соответствующие автоматические тесты; если проверяется поведение реального API, отдельно записать результат ручной проверки.

## Графические ресурсы карт

Основной документ художественного оформления:

`ART_STYLE.md`

Перед изменением изображений, рамок, обозначений или визуальных эффектов необходимо сверяться с ним.

### Утверждённые форматы

Для графических ресурсов карт используются два исходных формата.

| Формат | Размер | Назначение |
|---|---|---|
| `field` | 1024 × 1024 px | Штабы, техника и взводы на игровом поле |
| `card` | 848 × 1264 px | Каталог, колоды, редактор и рука игрока |

Приказы используют только вертикальный формат.

Размеры относятся к исходным ресурсам.

Фактический размер отображения определяется HTML/CSS.

Не создавать отдельные PNG для разных CSS-размеров одного изображения.

### Структура каталогов

Утверждённая структура:

```text
app/assets/images/cards/
├── germany/
│   ├── headquarters/
│   ├── technique/
│   ├── order/
│   └── platoon/
├── usa/
│   ├── headquarters/
│   ├── technique/
│   ├── order/
│   └── platoon/
└── ussr/
    ├── headquarters/
    ├── technique/
    ├── order/
    └── platoon/
```

Не создавать параллельные каталоги для тех же ресурсов без необходимости.

### Именование иллюстраций

Использовать схему:

```text
{nation}_{display}_{type}_{card_code_without_nation_and_type_prefix}.png
```

Где:

- `nation` — код нации;
- `display` — `field` или `card`;
- `type` — тип карты;
- последняя часть — код карты без префиксов нации и типа.

Примеры:

```text
usa_field_headquarters_second_front.png
usa_card_headquarters_second_front.png
usa_field_technique_m3_lee_grant.png
usa_card_technique_m3_lee_grant.png
usa_card_order_lend_liz.png
germany_field_headquarters_operation_weiß.png
```

### Именование рамок

Основная схема:

```text
{nation}_{display}_{type}_border.png
```

Для рамок с вариантами:

```text
{nation}_{display}_{type}_{variant}_border.png
```

Варианты рамок зависят от типа карты:

- Headquarters — обычная рамка и вариант `ability`.
- Technique — обычная рамка и вариант `ability`.
- Order — обычная рамка.
- Platoon — варианты `attack` и `defense`.

Вариант выбирается по актуальным данным карты.

Не выбирать вариант по произвольному условию интерфейса.

### Unicode в кодах карт

Коды карт могут содержать Unicode-символы.

Подтверждённый пример:

```text
germany_headquarters_operation_weiß
```

Соответствующий путь:

```text
cards/germany/headquarters/germany_field_headquarters_operation_weiß.png
```

Нельзя ограничивать допустимые символы только ASCII, если это исключает корректные коды карт.

Для проверки буквенно-цифровых кодов с подчёркиваниями допускается Unicode-aware выражение:

```ruby
/\A[\p{L}\p{N}_]+\z/u
```

Не выполнять произвольную транслитерацию кодов.

Не заменять `ß` на `ss` при формировании имени файла.

## Многослойное отображение карт

Основная схема:

1. Иллюстрация.
2. Прозрачная рамка.
3. Условные обозначения.
4. Динамические характеристики.
5. Индикаторы и визуальные эффекты.

Фактический набор слоёв зависит от типа карты.

### Источники данных

Иллюстрация и рамка определяются по данным карты.

Динамические характеристики определяются по актуальному разрешённому состоянию игры.

Не использовать PNG как источник текущих игровых значений.

Не переносить вычисление допустимых действий в CSS или JavaScript.

### Определение изображения по card_id

Для игровых объектов, содержащих `card_id`, необходимо использовать соответствующий код карты.

Не выбирать иллюстрацию только по нации, если внутри одной нации существует несколько карт соответствующего типа.

При необходимости коды карт могут быть подготовлены на сервере для представления.

Не добавлять в клиентское состояние скрытые данные противника ради отображения иллюстраций.

### Динамические характеристики

Для штабов и техники используются предусмотренные рамкой характеристики:

- огневая мощь;
- HP;
- топливо.

Значения берутся из актуального состояния.

Утверждённое правило:

- `0` — характеристика существует и равна нулю;
- `–` — характеристика неприменима.

Не заменять числовой ноль прочерком.

Не добавлять в интерфейс характеристики, которых нет в данных карты или игровом состоянии.

### Цвет огневой мощи

Для отображения состояния атаки и контратаки используются:

- `has_attacked`;
- `has_counterattacked`.

Красный цвет означает, что соответствующее действие ещё не использовано.

Стандартный цвет означает, что действие использовано либо индикатор неактивен.

При отображении учитывать текущего игрока и владельца объекта.

Красный цвет не гарантирует допустимость атаки или наличие цели.

### Обозначения классов техники

Утверждены следующие обозначения:

| Класс | Код | Символ |
|---|---|---|
| Лёгкий танк | `light_tank` | Ромб |
| Средний танк | `medium_tank` | Горизонтальный прямоугольник |
| Тяжёлый танк | `heavy_tank` | Квадрат |
| ПТ-САУ | `tank_destroyer` | Треугольник |
| САУ | `artillery` | Вертикальный прямоугольник |

Обозначения размещаются в верхнем правом элементе рамки техники.

Текущий утверждённый цвет — красный.

Использовать CSS или SVG.

Не встраивать динамические обозначения в PNG.

### Индикаторы движения

Для техники используются индикаторы в виде колёс.

Количество определяется:

```ruby
movement_limit
```

Использованные перемещения определяются:

```ruby
movement_count
```

Количество оставшихся перемещений:

```ruby
[movement_limit - movement_count, 0].max
```

Красный цвет означает неиспользованное перемещение.

Стандартный цвет означает использованное перемещение.

При определении состояния учитывать текущего игрока и владельца техники.

Индикатор не гарантирует наличие допустимого маршрута.

Не вычислять допустимость перемещения на клиенте.

### Индикатор способности

Для техники со способностью предусматривается компактный индикатор.

Полный текст способности не размещается на квадратной карте игрового поля.

Описание должно быть доступно через интерфейс.

На сенсорных устройствах нельзя полагаться исключительно на `hover`.

Реализация индикатора способности остаётся отдельной задачей Stage 24.

### Проверка прозрачности

**Наличие альфа-канала не гарантирует прозрачность.**

PNG в режиме RGBA может содержать только непрозрачные пиксели.

Для проверки можно использовать ImageMagick:

```bash
identify -format '%f: %[channels], alpha min=%[fx:minima.a], alpha max=%[fx:maxima.a]\n' \
  app/assets/images/cards/germany/technique/germany_field_technique_border.png
```

В этом выражении значения альфа-канала нормализованы в диапазоне от `0` до `1`.

- `0` — полностью прозрачный пиксель.
- `1` — полностью непрозрачный пиксель.

Для корректной рамки с прозрачной областью минимальное значение должно быть `0`.

Однако этого недостаточно для подтверждения правильного расположения прозрачных областей.

Необходимо дополнительно проверить рамку визуально.

4. Проверить способ подключения.
5. Проверить доступность для Propshaft.
6. Проверить загрузку в браузере.

Не добавлять импорт несуществующего файла.

### Ошибка MissingAssetError

В ходе Stage 24 наблюдалась ошибка:

```text
Propshaft::MissingAssetError:
The asset 'components/technique-field.css'
was not found in the load path.
```

После выполнения:

```bash
bin/rails assets:precompile
```

пользователь подтвердил запуск игры.

Это подтверждает успешный запуск после сборки, но не устанавливает окончательную причину первоначальной ошибки.

Не считать `assets:precompile` универсальным решением ошибок подключения CSS.

При повторном возникновении ошибки необходимо проверить:

1. Существует ли файл.
2. Правильно ли указан путь.
3. Подключён ли каталог к системе ассетов.
4. Как обрабатываются CSS-импорты.
5. Не используются ли устаревшие предварительно собранные ресурсы.

### Development и production

В development необходимо проверить корректную загрузку новых ресурсов.

В production сборка ассетов должна выполняться в процессе развёртывания приложения.

После обновления приложения необходимо убедиться, что:

- новые CSS-файлы доступны;
- изображения доступны;
- пути соответствуют fingerprinted assets;
- браузер не использует устаревшие ресурсы;
- отсутствуют ошибки загрузки.

Не переносить вручную файлы из `public/assets` как замену корректной конфигурации сборки.

## Проверка визуальных компонентов

После изменения изображений, рамок или CSS:

1. Проверить отсутствие ошибок Rails.
2. Проверить загрузку ресурсов.
3. Проверить правильность слоёв.
4. Проверить прозрачность.
5. Проверить расположение характеристик.
6. Проверить отображение нулевых значений.
7. Проверить цветовые индикаторы.
8. Проверить игровые действия.
9. Проверить Turbo-обновления.
10. Проверить отображение на разных размерах экрана.

### Проверка техники

Для квадратных карт техники дополнительно проверять:

- название;
- национальную рамку;
- иллюстрацию;
- обозначение класса;
- индикаторы движения;
- огневую мощь;
- HP;
- топливо;
- обновление состояния после перемещения;
- обновление состояния после атаки;
- обновление состояния после контратаки.

### Автоматические тесты

Для чисто визуальных изменений достаточно соответствующей браузерной проверки, если серверное поведение и игровой контракт не изменялись.

При изменении игровой логики или серверных контрактов запускать соответствующие тесты.

Не добавлять дублирующие тесты без конкретной причины.

### Фиксация результата

После проверки необходимо зафиксировать:

- какие файлы изменены;
- что было реализовано;
- какие проверки выполнены;
- какие результаты подтверждены;
- какие проблемы остались;
- какие задачи следуют дальше.

Подтверждённые результаты записывать в `PROGRESS.md`.

Незавершённые задачи и критерии завершения — в `ROADMAP.md`.

Художественные требования — в `ART_STYLE.md`.

**Главный принцип: GameEngine определяет результат, UI отображает его.**
