# OPPONENT_ENGINE.md

# Собственный стратегический движок AI-соперника

## 1. Назначение документа

Документ определяет архитектуру, принципы работы, этапы разработки и критерии завершения собственного алгоритма AI-соперника Clash Tanks.

Цель Stage 25 — заменить принятие решений внешней языковой моделью собственным стратегическим движком, который анализирует игровую ситуацию, строит последовательность действий, оценивает последствия и адаптирует план по мере изменения состояния партии.

AI должен действовать как полноценный стратегический соперник, а не как механизм выбора одного случайного или локально выгодного действия.

Документ является основным планом разработки и журналом принятых архитектурных решений по Stage 25.

В нём необходимо фиксировать:

- утверждённую архитектуру;
- контракты компонентов;
- алгоритмы оценки и планирования;
- ограничения реализации;
- результаты разработки;
- обнаруженные проблемы и принятые решения;
- критерии завершения этапа.

Запланированные возможности не считаются реализованными до фактической реализации и проверки.

---

## 2. Основные цели

Собственный AI должен:

1. Анализировать всю доступную ему игровую ситуацию.
2. Определять стратегические цели на основании текущего состояния партии.
3. Планировать несколько последовательных действий в рамках одного хода.
4. Оценивать альтернативные последовательности действий.
5. Учитывать последствия атак, контратак, перемещений, размещения карт и использования приказов.
6. Учитывать защиту собственного штаба и угрозу штабу противника.
7. Развивать армию с учётом ресурсов, топлива и доступных карт.
8. Создавать выгодные позиции для последующих действий.
9. Пересматривать план после фактического выполнения действий.
10. Выбирать только действия, разрешённые серверной игровой логикой.
11. Не получать скрытую информацию противника.
12. Не изменять игровые правила и состояние игры самостоятельно.
13. Работать без внешних LLM, API-ключей и сетевых AI-провайдеров.
14. Обеспечивать последовательное отображение действий и визуальных эффектов на игровом поле.

Главный принцип:

**AI должен оценивать не только непосредственную выгоду действия, но и то, к какому состоянию партии приведёт последовательность его действий.**

## 3. Архитектурные ограничения

Обязательный архитектурный инвариант проекта:

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

Собственный AI встраивается в существующую архитектуру и не создаёт параллельную игровую систему.

### 3.1. GameEngine

`GameEngine` остаётся единственным арбитром игровых правил.

AI:

- не рассчитывает окончательный результат атаки;
- не применяет урон самостоятельно;
- не определяет допустимость перемещения самостоятельно;
- не меняет характеристики игровых объектов;
- не создаёт произвольные игровые действия;
- не изменяет `GameState` напрямую.

Все реальные действия выполняются через существующие механизмы:

```text
Action → GameActionRunner → GameEngine
```

Для гипотетического моделирования допускается непосредственное использование `GameEngine::Engine` на изолированной копии состояния. Такая симуляция не является реальным исполнением действия и не должна иметь побочных эффектов.

### 3.2. VisibleState

AI использует только разрешённую информацию.

Основная граница доступных данных:

```text
GameEngine::VisibleState
```

Нельзя передавать AI полный скрытый `GameState`.

В частности, AI не должен получать:

- карты в руке противника;
- скрытые карты колоды противника;
- другие данные, которые по правилам игры недоступны игроку.

AI может использовать доступные сведения о противнике:

- расположение его объектов;
- характеристики видимых объектов;
- состояние его штаба;
- доступные публичные показатели;
- результаты уже произошедших действий.

### 3.3. AvailableActions

Допустимые действия определяются существующей серверной логикой:

```text
GameEngine::AvailableActions
```

AI не должен самостоятельно формировать список разрешённых действий.

Планировщик может оценивать только действия, предоставленные сервером для соответствующего состояния.

После каждого гипотетического действия список допустимых действий должен вычисляться заново для нового состояния.

### 3.4. Запрет дублирования игровой логики

Не создавать второй GameEngine.

Не копировать правила атак, контратак, перемещений, размещения карт и других игровых действий в отдельную систему.

При моделировании последствий необходимо повторно использовать существующие правила GameEngine.

StateSimulator должен быть оболочкой безопасного моделирования, а не отдельной реализацией игровых правил.

## 4. Общая архитектура принятия решений

AI состоит из трёх логических уровней.

```text
StrategicEvaluator
        ↓
TacticalPlanner
        ↓
ActionExecutor
        ↓
GameActionRunner
        ↓
GameEngine
```

### 4.1. StrategicEvaluator

Стратегический анализатор оценивает общую ситуацию на поле и определяет приоритетные цели.

Он отвечает на вопросы:

- Насколько безопасен собственный штаб?
- Насколько опасно положение штаба противника?
- Какие объекты противника представляют наибольшую угрозу?
- Достаточно ли сильна собственная армия?
- Есть ли преимущество в контроле поля?
- Хватает ли ресурсов для развития армии?
- Какие позиции следует занять?
- Какие возможности необходимо подготовить на следующие ходы?

Стратегический анализ должен учитывать не только отдельные характеристики, но и их взаимное влияние.

Основные стратегические направления:

| Направление | Назначение |
|---|---|
| HQ Safety | Сохранение собственного штаба |
| Enemy HQ Threat | Создание угрозы штабу противника |
| Army Strength | Оценка силы собственной армии |
| Enemy Strength | Оценка доступной информации о силах противника |
| Battlefield Control | Контроль игровых позиций |
| Resource Position | Оценка доступных ресурсов |
| Fuel Position | Оценка топливных возможностей |
| Tactical Advantage | Текущее тактическое преимущество |
| Development Potential | Возможности дальнейшего развития армии |

Вес стратегических направлений должен зависеть от ситуации.

Например, при непосредственной угрозе уничтожения собственного штаба приоритет защиты должен значительно возрастать.

Нельзя использовать неизменную последовательность приоритетов для всех игровых ситуаций.

### 4.2. TacticalPlanner

Тактический планировщик строит последовательность действий, позволяющую реализовать стратегические цели.

Он отвечает за:

- получение допустимых действий;
- анализ альтернатив;
- моделирование последствий;
- сравнение последовательностей действий;
- выбор наиболее перспективного плана;
- определение первого действия для реального исполнения.

Планировщик должен учитывать взаимосвязь действий.

Например:

```text
Переместить танк
    ↓
Освободить позицию
    ↓
Разместить взвод
    ↓
Получить возможность атаки
    ↓
Создать угрозу штабу противника
```

Отдельное действие может быть невыгодным само по себе, но становиться полезным как часть более длинной последовательности.

### 4.3. ActionExecutor

Исполнитель отвечает за фактическое выполнение выбранного действия.

Он:

1. Получает первое действие лучшего плана.
2. Передаёт его существующему механизму исполнения.
3. Ожидает результат GameEngine.
4. Проверяет фактическое изменение состояния.
5. Определяет, остаётся ли оставшаяся часть плана актуальной.
6. Продолжает выполнение либо инициирует новое планирование.

Исполнитель не применяет игровые правила самостоятельно.

Он не должен считать гипотетический результат симуляции фактически произошедшим событием.

## 5. Стратегические цели

Стратегический движок должен учитывать иерархию целей.

Основные направления:

1. Сохранить собственный штаб.
2. Реализовать возможность немедленной победы.
3. Устранить непосредственные угрозы собственному штабу.
4. Уничтожить наиболее опасные объекты противника.
5. Создать боевое преимущество.
6. Сформировать наступательную группировку.
7. Развить армию.
8. Улучшить расположение объектов.
9. Подготовить возможности для следующих ходов.
10. Выполнить второстепенные действия, если они не мешают более важным целям.

Этот порядок является стратегическим ориентиром, а не жёстким списком действий.

Оценка должна учитывать реальные последствия.

Например, не всегда необходимо атаковать противника, если перемещение или размещение защитного взвода позволяет предотвратить уничтожение собственного штаба.

### 5.1. Долгосрочные цели

AI должен учитывать конечную цель партии — уничтожение штаба противника.

Для её достижения могут формироваться промежуточные цели:

- создать наступательную группировку;
- вывести технику на выгодные позиции;
- обеспечить необходимое топливо;
- устранить защитные объекты противника;
- подготовить возможность атаки штаба.

### 5.2. Среднесрочные цели

Среднесрочные цели связаны с развитием ситуации на поле:

- сформировать сильную линию техники;
- усилить защиту штаба;
- обеспечить поддержку техники взводами;
- занять позиции для будущих атак;
- подготовить несколько взаимосвязанных действий.

### 5.3. Краткосрочные цели

Краткосрочные цели реализуются в текущем ходе:

- атаковать;
- выполнить контратаку, если она предусмотрена допустимым действием;
- переместить технику;
- разместить карту;
- использовать приказ;
- устранить непосредственную угрозу;
- подготовить позицию для следующего действия.

## 6. Планирование последовательности действий

### 6.1. Основной принцип

AI должен планировать несколько действий вперёд, а не принимать каждое решение изолированно.

После выбора первого действия необходимо учитывать возможные последствия следующих действий.

План представляет собой последовательность гипотетических действий и состояний.

### 6.2. Beam Search

В качестве основного начального алгоритма ограниченного поиска рассматривается Beam Search.

Полный перебор всех комбинаций действий нецелесообразен из-за большого количества вариантов.

Например, при 20 допустимых действиях и глубине 5 полный перебор может дать до 3 200 000 последовательностей.

Beam Search позволяет сохранять только наиболее перспективные варианты на каждом уровне поиска.

Принцип работы:

1. Получить исходное доступное состояние.
2. Получить допустимые действия.
3. Создать варианты первого действия.
4. Смоделировать последствия каждого варианта.
5. Оценить полученные состояния.
6. Оставить ограниченное количество лучших вариантов.
7. Для каждого сохранённого варианта получить новые допустимые действия.
8. Повторять процесс до достижения заданной глубины.
9. Сравнить итоговые планы.
10. Выбрать первый шаг лучшего плана.

### 6.3. Начальные параметры поиска

Предварительные ориентиры:

| Параметр | Начальное значение |
|---|---:|
| Максимальная глубина | 5 действий |
| Ширина поиска | 10 вариантов |
| Максимальное количество реальных действий за запуск | 20 |
| Максимальное количество повторных попыток при устаревшем состоянии | 3 |

Это начальные значения для реализации и профилирования, а не окончательные ограничения алгоритма.

Их можно изменять после измерения производительности и анализа качества решений.

Ограничение в 20 реальных действий относится к существующему механизму выполнения AI-хода и не должно незаметно изменяться при разработке планировщика.

### 6.4. Оценка планов

Оцениваться должно итоговое состояние после последовательности действий.

Нельзя выбирать действие только по его локальной оценке.

Например:

- атака может нанести урон, но открыть собственный штаб для уничтожения;
- перемещение может не дать немедленной выгоды, но создать возможность атаки;
- размещение защитного взвода может быть полезнее немедленной атаки;
- приказ может быть ценен благодаря последствиям нескольких последующих действий.

Оценка должна учитывать:

- безопасность собственного штаба;
- угрозу штабу противника;
- уничтожение опасных объектов;
- сохранность собственной техники;
- состояние взводов;
- занятые позиции;
- доступные ресурсы;
- топливо;
- возможности дальнейших действий;
- стратегическую цель.

Не фиксировать окончательные числовые коэффициенты до реализации базовой системы оценки и проверки её поведения.

### 6.5. Отказ от бесполезных действий

AI должен избегать действий, которые не улучшают ситуацию и не помогают реализации стратегической цели.

При этом нельзя отбрасывать действие только потому, что его непосредственный результат выглядит невыгодным.

Необходимо оценивать его влияние на последующую последовательность действий.

## 7. Симуляция игровых действий

### 7.1. Назначение

Для планирования нескольких действий необходимо моделировать гипотетические состояния.

Симуляция нужна только для оценки вариантов.

Она не должна изменять реальную партию.

### 7.2. StateSimulator

Реализован компонент:

```text
DecisionProviders::OpponentEngine::Planning::StateSimulator
```

Файл:

```text
app/services/decision_providers/opponent_engine/planning/state_simulator.rb
```

Его задача — получить гипотетическое состояние после применения выбранного действия к изолированной копии игрового состояния.

Основной интерфейс:

```ruby
StateSimulator.call(
  visible_state:,
  player_id:,
  action:,
  current_time:
)
```

Компонент:

1. Принимает разрешённый `VisibleState`, идентификатор игрока, действие и фиксированное время.
2. Проверяет, что игра началась.
3. Проверяет существование игрока.
4. Проверяет, что сейчас ход указанного AI-игрока.
5. Строит минимальное симуляционное состояние на основании разрешённого `VisibleState`.
6. Создаёт `GameEngine::Action`.
7. Выполняет гипотетическое действие через настоящий `GameEngine::Engine`.
8. При успешном результате получает новый `VisibleState`.
9. Возвращает новый `VisibleState` и события Engine.

Результат симуляции не должен раскрывать полный `GameState`.

### 7.3. Безопасное построение состояния

StateSimulator не получает и не использует полный исходный `Game.state`.

Симуляционное состояние строится из разрешённых данных `VisibleState`.

При построении состояния:

- собственная рука AI сохраняется с известными картами;
- рука противника представляется неизвестными заглушками в количестве, соответствующем публичному показателю;
- колоды обоих игроков представляются неизвестными заглушками;
- кладбища представляются неизвестными заглушками;
- поле копируется из `VisibleState`;
- видимые характеристики объектов сохраняются;
- доступные ресурсы и таймеры сохраняются;
- остальные необходимые для Engine публичные параметры переносятся из `VisibleState`.

Неизвестные карты не должны становиться доступными для розыгрыша.

Заглушки скрытых карт используют:

```ruby
{
  "card_id" => "...",
  "card_type" => "unknown"
}
```

Идентификаторы заглушек должны быть уникальными внутри соответствующего симуляционного состояния.

### 7.4. Повторное использование GameEngine

Для гипотетического исполнения используется:

```ruby
GameEngine::Engine.new(
  state,
  current_time: current_time
).call(action)
```

Используется существующая реализация игровых правил.

Не создаётся второй движок и не дублируются правила атак, контратак, перемещений, размещения карт и других действий.

StateSimulator не должен вызывать:

- GameActionRunner;
- сохранение реальной игры;
- ActiveRecord callbacks;
- Turbo broadcast;
- механизмы реального исполнения действий.

Симуляция должна оставаться изолированной от реальной партии.

### 7.5. Фиксированное время симуляции

Внутри одной цепочки гипотетических действий необходимо использовать единое значение `current_time`.

Это исключает изменение результатов симуляции только из-за прохождения реального времени между последовательными вызовами Engine.

При построении плана все гипотетические действия должны рассчитываться относительно одного зафиксированного времени поиска.

### 7.6. Типы идентификаторов игроков

При симуляции необходимо сохранять исходный тип `current_player_id`.

В `VisibleState` идентификаторы игроков в ключах `players` могут использоваться в строковом представлении, однако объекты на игровом поле сохраняют исходный тип `player_id`.

В `GameEngine::Actions::Move` принадлежность техники проверяется строгим сравнением:

```ruby
technique["player_id"] == @action.player_id
```

Поэтому передача строкового идентификатора вместо исходного значения может привести к ошибке:

```text
Technique does not belong to player
```

Принятое решение:

- строковый `@player_id` используется для обращения к ключам `players`;
- в `GameEngine::Action` передаётся исходный тип:

```ruby
player_id: @visible_state["current_player_id"]
```

Не изменять строгие проверки GameEngine ради исправления этой проблемы: нормализация должна выполняться на границе StateSimulator.

### 7.7. Результат и обработка ошибок

StateSimulator возвращает структурированный результат:

- признак успешной симуляции;
- ошибку при неудаче;
- новый `VisibleState` при успехе;
- события Engine при успехе.

При ошибке симуляции не должно происходить изменения исходного состояния.

Симулятор не должен скрывать ошибки и выдавать неуспешное действие за успешное.

### 7.8. Проверка StateSimulator

```text

```

Проверяется:

Обнаруженная при тестировании проблема несовпадения типов `player_id` исправлена на границе StateSimulator.

**Статус: реализован и проверен полным набором тестов.**

## 8. Жизненный цикл плана

План должен быть адаптивным.

Он не должен становиться жёсткой последовательностью действий, которая продолжает выполняться после изменения исходных условий.

### 8.1. Создание плана

При необходимости планировщик:

1. Анализирует актуальный VisibleState.
2. Определяет стратегические цели.
3. Получает допустимые действия.
4. Строит альтернативные планы.
5. Выбирает лучший план.
6. Передаёт первое действие исполнителю.

### 8.2. Проверка после действия

После реального выполнения действия:

1. Получить фактический результат GameEngine.
2. Получить актуальное состояние игры.
3. Проверить соответствие ожидаемому состоянию.
4. Проверить допустимость следующего запланированного действия.
5. Оценить, не изменились ли стратегические приоритеты.

Если план остаётся актуальным, можно продолжить его выполнение.

Если состояние существенно отличается от ожидаемого или следующее действие больше не разрешено, план необходимо перестроить.

### 8.3. Хранение плана

На начальном этапе не создавать отдельную постоянную систему хранения стратегических планов в базе данных.

Сначала проверить, можно ли хранить текущий план в памяти одного запуска:

```text
Games::RunAiTurns
```

Если существующий цикл выполняет несколько действий последовательно в рамках одного запуска, предпочтительно использовать этот жизненный цикл.

Persistent storage для планов допускается рассматривать только при доказанной необходимости.

### 8.4. Стратегическая память

Не сохранять полную историю боя ради планирования.

Основной источник информации — актуальный VisibleState.

Постоянную стратегическую память вводить только в том случае, если будет выявлена конкретная важная информация, которую невозможно восстановить из текущего разрешённого состояния.

## 11. Последовательность исполнения действий и визуальные эффекты

### 11.1. Проблема

Во время игры AI может очень быстро выполнить несколько действий подряд.

В результате серверные действия уже завершены, а визуальные эффекты предыдущего действия ещё не успели полностью отработать в браузере.

Это ухудшает восприятие партии: игрок не успевает увидеть последовательность атаки, контратаки, повреждения, уничтожения или перемещения.

### 11.2. Требуемое поведение

Между реальными действиями AI должна быть пауза:

**от 2 до 3 секунд.**

Начальное рекомендуемое значение:

```text
2.5 секунды
```

Пауза должна применяться между успешно выполненными реальными действиями AI.

Не требуется задержка:

- перед первым действием хода;
- после последнего действия;
- после действия, которое завершило партию;
- после ошибки, если дальнейшее выполнение прекращается.

### 11.3. Место реализации

Задержка относится к слою исполнения, а не к стратегическому планированию.

Реализация находится в существующем цикле:

```text
Games::RunAiTurns
```

Не добавлять задержки в:

- StrategicEvaluator;
- TacticalPlanner;
- BeamSearch;
- StateSimulator;
- ActionScorer.

Планирование и гипотетическая симуляция должны оставаться быстрыми.

### 11.4. Последовательность реального выполнения

Ожидаемый процесс:

```text
AI выбирает действие
        ↓
GameActionRunner
        ↓
GameEngine
        ↓
Сохранение успешного результата
        ↓
Turbo broadcast / обновление интерфейса
        ↓
Воспроизведение визуальных эффектов
        ↓
Пауза 2–3 секунды
        ↓
Следующее действие AI
```

Нужно учитывать существующую очередь последовательного воспроизведения визуальных эффектов.

Новая пауза не должна заменять или ломать текущую очередь анимаций.

### 11.5. Реализация задержки

В `Games::RunAiTurns` реализована централизованная задержка:

```text
2.5 секунды
```

Она применяется между успешно выполненными действиями, когда тот же AI-игрок продолжает ход.

Для тестирования предусмотрена возможность подменить механизм ожидания, чтобы тесты не зависели от реального времени.

Задержка не должна применяться после последнего действия, завершения игры или при прекращении выполнения.

**Результат проверки:** полный набор тестов после реализации задержки и последующих изменений StateSimulator прошёл успешно.

Ограничение текущего решения: пауза фиксированной продолжительности не гарантирует, что браузер закончил воспроизведение всех анимаций. Для строгой синхронизации в будущем можно рассмотреть механизм подтверждения завершения анимаций клиентом.

Также необходимо учитывать, что ожидание внутри текущего синхронного цикла увеличивает продолжительность выполнения AI-хода. До изменения механизма исполнения не вводить Redis или другую дополнительную инфраструктуру без отдельного согласования.

- устаревшие инструкции в документации;
- неиспользуемые зависимости.

Общую инфраструктуру `DecisionProviders`, `Context`, `ActionOptions` и существующие механизмы исполнения не удалять, если они нужны собственному AI.

Критерий завершения:

**AI-соперник полностью работает без Groq, OpenAI и внешних API-ключей.**

## 16. Принятые решения и ограничения

На текущий момент согласованы следующие решения:

1. Используется собственный алгоритм AI без внешней языковой модели.
2. Groq и OpenAI полностью исключаются из рабочего механизма AI.
3. Основой принятия решений являются VisibleState и ActionOptions.
4. GameEngine остаётся единственным арбитром игровых правил.
5. AI должен планировать несколько последовательных действий.
6. Для ограниченного поиска используется подход Beam Search.
7. Гипотетическая симуляция не должна изменять реальную игру.
8. Для симуляции повторно используется настоящий `GameEngine::Engine`.
9. StateSimulator строит состояние только из разрешённого VisibleState.
10. Скрытые карты противника заменяются неизвестными заглушками.
11. Результат симуляции содержит новый VisibleState и события, но не полный GameState.
12. После реального действия план проверяется и при необходимости перестраивается.
13. Долгосрочная стратегическая память не вводится без доказанной необходимости.
14. Качество игровых решений проверяется пользователем вручную.
15. Автоматические тесты проверяют программную корректность компонентов.
16. Между реальными действиями AI предусматривается пауза 2–3 секунды; реализованное начальное значение — 2,5 секунды.
17. Пауза реализуется в механизме исполнения, а не в планировщике.
18. Существующие визуальные эффекты и очередь их воспроизведения сохраняются.
19. Не изменять игровые правила и ограничения времени без отдельного согласования.
20. Для одной цепочки гипотетических действий используется фиксированное значение current_time.
21. Исходный тип current_player_id сохраняется при создании GameEngine::Action, чтобы не нарушать строгие проверки принадлежности игровых объектов.
