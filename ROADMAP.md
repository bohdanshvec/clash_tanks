### Главный стратегический приоритет

**Сначала накопление техники и подготовка выгодных позиций, затем совместная атака.**

AI не должен отправлять каждый новый танк в одиночную атаку только потому, что она доступна в текущем состоянии.

Необходимо учитывать:

- сохранение уже выставленной техники;
- возможность сформировать группу для совместной атаки;
- взаимную поддержку танков;
- ценность позиции каждого танка для последующих действий;
- возможность освободить клетку возле штаба для развёртывания новой техники;
- риск ожидания и вероятность потерять возможность атаки;
- необходимость сохранять давление на штаб противника.

Одиночная атака остаётся оправданной, если позволяет уничтожить опасную цель или получить явное стратегическое преимущество.

Свободные клетки рядом со штабом уже оцениваются компонентом `deployment_capacity_score`. Новая позиционная оценка не должна повторно начислять бонус за освобождение той же клетки.

Доступная для розыгрыша техника может повышать срочность освобождения клетки, но сама ценность свободной клетки не должна зависеть исключительно от наличия карты в руке.

Резервная позиция сама по себе не должна давать бонус, провоцирующий отступление. Перемещение назад оправдано только тогда, когда оно создаёт конкретную стратегическую пользу.

**Накопление сил и координация танков не считаются реализованными только потому, что AI выполняет несколько действий подряд или иногда перемещает технику в сторону общей цели. Необходимо подтвердить устойчивое целенаправленное поведение в нескольких партиях.**

## Обязательные архитектурные границы

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

- `GameEngine` — единственный арбитр игровых правил.
- AI выбирает допустимое действие, но не изменяет `GameState` напрямую.
- `GameActionRunner` сохраняет только успешно выполненные действия.
- AI получает только разрешённое состояние.
- `VisibleState` — граница доступа AI к игровым данным.
- Гипотетические действия выполняются только на изолированном состоянии.
- Turbo, Stimulus и UI не изменяют `GameState`.
- Боевые события описывают результат Engine.
- Автотесты не вызывают реальные API.
- Не вводить Redis.
- Не менять PostgreSQL 12/14.
- Не менять игровую механику без согласования.
- Язык интерфейса — украинский.
- CSS и графика не должны влиять на игровые правила.
- Не изменять работающий код на основании неподтверждённых гипотез.
- Не сокращать и не изменять существующие анимации без отдельного согласования.

# Stage 25 — собственный алгоритм AI-соперника (В РАБОТЕ)

## Цель

Заменить внешнюю LLM-модель собственным алгоритмом принятия решений.

Новый AI должен:

- работать без внешних LLM и AI API;
- не требовать Groq/OpenAI API-ключей;
- использовать только разрешённое состояние;
- выбирать только серверные допустимые действия;
- оценивать последствия последовательности действий, а не только непосредственную выгоду;
- учитывать стратегические цели партии;
- адаптироваться к фактическому состоянию после каждого действия;
- выполнять реальные действия через существующую инфраструктуру;
- сохранять действующие ограничения безопасности и архитектуры.

Переход выполняется постепенно. Старые провайдеры и зависимости от внешнего API удаляются только после переноса функциональности и проверки нового алгоритма.

## 25.1. ActionOptions — формирование допустимых действий (РЕАЛИЗОВАНО)

Основной компонент:

```text
DecisionProviders::ActionOptions
```

Формирует список допустимых действий на основании `VisibleState` и доступных действий.

Поддерживаются:

- перемещение техники;
- атаки;
- розыгрыш карт;
- завершение хода.

Список действий формируется заново для каждого симулируемого состояния. Заглушки неизвестных карт не должны становиться доступными для розыгрыша.

## 25.2. StateSimulator — безопасная симуляция действий (ТЕХНИЧЕСКИ ПРОВЕРЕНО)

Основной файл:

```text
app/services/decision_providers/opponent_engine/planning/state_simulator.rb
```

`StateSimulator` создаёт гипотетические состояния для поиска последовательностей действий.

Для симуляции используется только `VisibleState`. Полный `Game.state` не передаётся планировщику.

### Основные принципы

- Строится изолированное состояние, совместимое с `GameEngine`.
- Настоящая рука AI сохраняется.
- Рука противника, колоды и кладбища представляются заглушками в соответствии с известным количеством карт.
- Неизвестные карты не восстанавливаются по скрытым данным.
- Заглушки неизвестных карт не могут быть разыграны.
- После симуляции наружу возвращаются новый `VisibleState` и разрешённые события.
- Исходный `VisibleState` не мутируется.

Для каждого гипотетического действия:

1. Получить допустимые действия для текущего симуляционного состояния.
2. Выбрать соответствующее действие.
3. Нормализовать payload.
4. Создать `GameEngine::Action`.
5. Выполнить действие через настоящий `GameEngine::Engine`.
6. Получить новое состояние.
7. Построить следующий `VisibleState`.
8. Повторно сформировать `ActionOptions`.

Для одной последовательности симуляционных действий используется единый `current_time`.

### Отсутствие побочных эффектов

Симуляция не:

- записывает изменения в базу данных;
- создаёт реальные `GameAction`;
- выполняет Turbo broadcasts;
- изменяет статистику;
- использует `GameActionRunner` для гипотетических действий;
- изменяет реальное состояние игры.

### Исправления

В процессе проверки обнаружена проблема несовпадения типов идентификаторов при перемещении техники. Исправлена проверка принадлежности техники игроку в `GameEngine::Actions::Move`: сравнение идентификаторов нормализовано через `.to_s`.

Добавлен регрессионный тест.

Также исправлена тестовая симуляция:

- `headquarters_participant` вызывается с keyword arguments;
- `player_id` собственной техники в начальном состоянии задаётся строкой.

Перемещение техники через настоящий `GameEngine`, работу `StateSimulator` и `TacticalPlanner` проверили автоматизированными тестами. Браузерная проверка подтвердила корректное перемещение.

**Техническая проверка симуляции выполнена. Это не означает, что стратегическое использование перемещений уже настроено.**

## 25.3. StrategicEvaluator — стратегическая оценка (РЕАЛИЗОВАНО, ТРЕБУЕТ КАЛИБРОВКИ)

Основной файл:

```text
app/services/decision_providers/opponent_engine/planning/strategic_evaluator.rb
```

Оценивает разрешённое состояние игры на основании `VisibleState`.

### Учитываемые характеристики

**Штабы:**

- HP;
- огневая мощь;
- топливо.

**Техника:**

- HP;
- огневая мощь;
- дальность;
- топливо;
- позиция;
- доступные атаки и перемещения.

**Взводы:**

- HP;
- огневая мощь;
- броня;
- топливо.

**Рука и ресурсы:**

- количество карт;
- доступность розыгрыша;
- достаточность ресурсов;
- доступные позиции, слоты и цели.

Также учитываются:

- позиционное продвижение;
- свободные клетки для развёртывания;
- потенциальные атакующие;
- возможности атаки штаба;
- угроза со стороны техники противника;
- терминальные состояния.

Для победы и поражения используется терминальная оценка:

```ruby
WIN_SCORE = 1_000_000
```

### Уже реализованные оценки атак

Реализована оценка нескольких потенциальных атакующих по одной цели. При анализе учитываются не только текущие позиции техники, но и доступные перемещения, после которых техника может получить возможность атаки.

Также реализована оценка возможности открыть атаку штаба по технике противника посредством перемещения собственной техники, обеспечивающего разведку возле цели.

Эти механизмы расширяют оценку потенциальных возможностей, но ещё не гарантируют правильную координацию нескольких танков в реальном плане.

### Текущие проблемы

Браузерная проверка выявила:

- AI иногда отправляет один танк в атаку слишком рано;
- AI не всегда накапливает технику для совместных действий;
- AI может перемещать технику на резервные позиции без достаточной стратегической причины;
- оценка позиции должна учитывать не только продвижение к противнику, но и поддержку других танков;
- необходимо различать полезное освобождение клетки для развёртывания новой техники и ненужное отступление.

При этом AI уже демонстрировал способность оказывать давление на штаб противника последовательными атаками. Улучшение групповой тактики не должно приводить к отказу от выгодных атак штаба.

### Важные ограничения будущей модели

- Свободные клетки возле собственного штаба уже учитываются через `deployment_capacity_score`.
- Не добавлять второй бонус за освобождение той же клетки.
- Доступная для розыгрыша техника может влиять на срочность освобождения клетки, но не должна определять всю её стратегическую ценность.
- Резервная позиция не должна автоматически получать преимущество.
- Не вводить отдельный бонус за карту в руке до проверки базовой модели.
- Позицию перемещаемого танка оценивать отдельно от ценности освобождённой клетки.
- Не увеличивать вес совместной атаки до устранения проблемы преждевременного расходования отдельных танков.

Следующий этап — анализ и корректировка позиционной оценки и остальных весов на конкретных игровых ситуациях.

## 25.4. TacticalPlanner — тактический поиск (РЕАЛИЗОВАНО, ТРЕБУЕТ ПРАКТИЧЕСКОЙ ПРОВЕРКИ)

Основной файл:

```text
app/services/decision_providers/opponent_engine/planning/tactical_planner.rb
```

Используется Beam Search.

Начальные параметры:

```text
depth = 5
width = 10
```

Параметры остаются настраиваемыми.

### Основные принципы

- строить несколько последовательностей действий;
- симулировать действия через `StateSimulator`;
- оценивать состояния через `StrategicEvaluator`;
- сохранять наиболее перспективные варианты;
- сравнивать планы по общей стратегической ценности;
- завершать последовательность при `end_turn`;
- возвращать лучший найденный план.

Ответные действия противника внутри текущего поиска не моделируются.

План содержит последовательность действий, ожидаемые состояния после шагов, итоговую оценку и количество рассмотренных узлов.

Наличие нескольких последовательных действий в плане не доказывает, что AI умеет накапливать силы и координировать атаки. Это требует отдельной проверки.

## 25.5. ActionExecutor — исполнение плана (РЕАЛИЗОВАНО)

Основной файл:

```text
app/services/decision_providers/opponent_engine/action_executor.rb
```

Преобразует шаги плана в реальные игровые действия.

Реализованы:

- выполнение первого действия плана;
- получение ожидаемого `VisibleState`;
- хранение индекса следующего шага;
- проверка структуры плана и индекса;
- создание `GameEngine::Action` с актуальным `state_digest`;
- нормализация payload.

Сохранён интерфейс:

```ruby
ActionExecutor.call(plan:, context:)
```

Дополнительно реализован:

```ruby
ActionExecutor.execute(
  plan:,
  context:,
  step_index: 0
)
```

Симуляционное состояние не применяется к реальной игре. Реальные действия выполняются через `GameActionRunner`.

## 25.6. Интеграция собственного AI и адаптивное продолжение плана (РЕАЛИЗОВАНО)

### DecisionProviders::AI

Основной файл:

```text
app/services/decision_providers/a_i.rb
```

Добавлена поддержка:

```text
AI_PROVIDER=opponent_engine
```

Реализован `call_with_plan`, возвращающий действие, рассчитанный план, ожидаемое состояние и индекс следующего шага.

### Games::RunAiTurns

Основной файл:

```text
app/services/games/run_ai_turns.rb
```

После успешного действия AI получает актуальный контекст и проверяет возможность продолжить ранее рассчитанный план.

План может быть продолжен, если:

- тот же AI продолжает ход;
- ожидаемое состояние и индекс следующего шага существуют;
- следующий индекс находится в пределах плана;
- нормализованный ожидаемый `VisibleState` совпадает с фактическим;
- следующее действие всё ещё допустимо согласно `ActionOptions`.

Для сравнения состояния нормализуются поля времени:

- `server_time`;
- `turn_started_at`;
- `remaining_time` каждого игрока.

При несовпадении состояния, недопустимости следующего действия или ошибке устаревшего состояния план очищается и строится заново.

Все реальные действия проходят через:

```text
Games::RunAiTurns
        ↓
GameActionRunner
        ↓
GameEngine
```

### Интеграционная проверка

Проверено повторное использование одного плана для нескольких последовательных действий AI.

Тест подтверждает:

- выполнение двух последовательных розыгрышей взводов;
- использование одного плана;
- отсутствие повторного вызова планировщика между этими действиями;
- корректное списание ресурсов;
- удаление сыгранных карт из руки;
- появление взводов на поле;
- наличие соответствующих игровых событий.

В проверенном сценарии:

```text
AI actions count: 4
Planner calls: 1
```

Планировщик вызывается один раз, четыре реальных действия выполняются последовательно с проверкой актуальности плана.

**Техническая интеграция и адаптивное продолжение плана завершены.**

## 25.7. Практическая настройка стратегического поведения (СЛЕДУЮЩИЕ ЗАДАЧИ)

Работа выполняется строго в следующем порядке.

### Приоритет 1. Анализ и корректировка весов StrategicEvaluator

Проверить влияние каждого компонента оценки на выбор действий.

Особое внимание:

- ценность сохранения собственной техники;
- ценность нанесения урона штабу противника;
- оценка атаки и контратаки;
- оценка позиции техники;
- поддержка и взаимное расположение танков;
- оценка доступных перемещений;
- оценка ресурсов и карт в руке;
- ценность свободных клеток для развёртывания;
- влияние текущей выгоды на перспективы последующих действий.

Проверить, не провоцирует ли линейная оценка продвижения преждевременные одиночные атаки.

Не компенсировать проблему произвольным увеличением одного коэффициента без проверки влияния на остальные решения.

### Приоритет 2. Улучшение координации нескольких танков

Главная задача — добиться накопления сил до начала совместной атаки, когда это стратегически выгодно.

Необходимо:

- оценивать несколько танков как потенциальную группу;
- учитывать суммарную огневую мощь;
- оценивать взаимное расположение и возможность поддержки;
- определять ситуации, в которых совместная атака выгоднее одиночной;
- учитывать возможность подготовить атаку перемещением;
- оценивать сохранение каждого танка до момента атаки;
- не отправлять танки в одиночную атаку только из-за доступности такого действия.

Не запрещать одиночные атаки. Они оправданы, если позволяют уничтожить опасную цель или дают явное преимущество.

Сначала добиться устойчивого накопления сил. Только после этого калибровать дополнительную ценность совместной атаки.

### Приоритет 3. Оценка выгодности ожидания перед совместной атакой

Проверить, способен ли AI отказаться от немедленной атаки, если ожидание позволяет подготовить более сильную совместную атаку.

Оценивать:

- ожидаемый суммарный урон;
- риск потери или повреждения техники во время ожидания;
- возможность противника изменить позицию;
- вероятность потерять выгодную возможность атаки;
- ценность немедленного давления на штаб;
- доступные действия до завершения хода.

Ожидание должно выбираться только тогда, когда его ожидаемая стратегическая ценность выше немедленного действия.

### Приоритет 4. Устранение ненужного отступления на резервные позиции

Проверить случаи, когда техника перемещается назад на резервные клетки возле собственного штаба без достаточной пользы.

Различать:

- полезное перемещение в резерв;
- перемещение для освобождения клетки;
- подготовку позиции для последующей атаки;
- ненужное отступление, снижающее давление на противника.

Резервная позиция не должна автоматически получать преимущество только из-за своего положения.

### Приоритет 5. Проверка освобождения плацдарма для новой техники

Проверить, способен ли AI осознанно освобождать клетки для последующего развёртывания новой техники.

Учитывать:

- наличие техники, которую можно разыграть;
- доступные клетки для её размещения;
- ценность освобождаемой клетки;
- пользу перемещения существующей техники;
- возможность последующего использования новой техники;
- влияние перемещения на оборону и давление на противника.

Свободные клетки возле штаба уже оцениваются в `deployment_capacity_score`. Новая логика не должна повторно начислять бонус за тот же результат.

Перемещение на резервную клетку считается полезным только при наличии конкретной стратегической цели.

### Приоритет 6. Серия контрольных партий против AI

Провести несколько полноценных партий с наблюдением за поведением алгоритма.

Проверить:

- игру AI за первую сторону;
- игру AI за вторую сторону;
- накопление техники перед совместными атаками;
- выбор между одиночной и групповой атакой;
- своевременность атак;
- сохранение давления на штаб противника;
- использование резервных позиций;
- освобождение клеток для новой техники;
- защиту собственного штаба;
- использование ресурсов;
- отсутствие повторяющихся бесполезных перемещений.

Для каждой партии фиксировать конкретные ситуации, в которых AI принял удачное или неудачное решение.

**Критерий:** накопление сил и координация считаются реализованными только после подтверждения устойчивого целенаправленного поведения в нескольких партиях.

### Приоритет 7. Финальная калибровка и завершение Stage 25

После контрольных партий:

- скорректировать оставшиеся веса `StrategicEvaluator`;
- проверить поведение за обе стороны;
- повторить контрольные партии после изменений;
- проверить отсутствие регрессий;
- проверить производительность Beam Search;
- подтвердить устойчивость адаптивного продолжения плана;
- выполнить полный набор автоматизированных тестов;
- проверить работу собственного AI без внешнего LLM-провайдера;
- определить, какие старые зависимости и настройки можно безопасно удалить.

Stage 25 закрывается только после практического подтверждения качества стратегических решений, а не только после прохождения автоматизированных тестов.

## 25.9. Удаление внешнего LLM-провайдера (ЗАПЛАНИРОВАНО)

## 25.10. Задержка между действиями AI (РЕАЛИЗОВАНО)

Для последовательных действий AI добавлена фиксированная задержка:

```ruby
ACTION_DELAY_SECONDS = 2.5
```

Предусмотрена возможность внедрения `sleeper` для тестов.

Пауза выполняется только если:

- предыдущее действие успешно выполнено;
- тот же AI продолжает свой ход;
- игра остаётся в статусе `started`;
- лимит действий AI ещё не достигнут.

Пауза выполняется после Turbo broadcast и перед следующей итерацией AI-цикла.

Ограничения:

- задержка фиксированная и не подтверждает завершение клиентской очереди анимаций;
- строгая синхронизация потребует отдельного механизма подтверждения готовности клиента;
- при лимите в 20 действий максимальное количество пауз — 19;
- максимальная суммарная задержка — 47,5 секунды;
- синхронный запрос и удерживаемые ресурсы, включая advisory lock и DB connection, остаются занятыми во время ожидания.
