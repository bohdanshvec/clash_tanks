## Текущая архитектура

Основной поток исполнения игровых действий:

```text
Decision Provider
      ↓
    Action
      ↓
GameActionRunner
      ↓
  GameEngine
      ↓
  GameState
```

Архитектура собственного AI:

```text
VisibleState
     ↓
ActionOptions
     ↓
TacticalPlanner
     ├── StateSimulator
     └── StrategicEvaluator
     ↓
ActionExecutor
     ↓
Decision Provider
     ↓
GameActionRunner
     ↓
GameEngine
```

Основные компоненты:

| Компонент | Назначение |
|---|---|
| `ActionOptions` | Формирование допустимых вариантов действий |
| `StateSimulator` | Изолированная симуляция гипотетических действий через `GameEngine` |
| `StrategicEvaluator` | Оценка стратегической ценности состояния |
| `TacticalPlanner` | Поиск последовательностей действий через Beam Search |
| `ActionExecutor` | Подготовка следующего действия плана |
| `DecisionProviders::AI` | Интеграция AI через Decision Provider |
| `Games::RunAiTurns` | Исполнение действий и адаптивное продолжение плана |

Подробное описание компонентов, их взаимодействия и технических ограничений находится в `OPPONENT_ENGINE.md`.

### Stage 25 — собственный стратегический движок AI

<badge color="success">Первоначальная разработка завершена</badge>

Реализованы и интегрированы:

- `StateSimulator` — безопасная симуляция гипотетических действий через настоящий `GameEngine`;
- `ActionOptions` — формирование допустимых действий на основании `VisibleState`;
- `StrategicEvaluator` — первоначальная стратегическая оценка игровых состояний;
- `TacticalPlanner` — поиск последовательностей действий на основе Beam Search;
- `ActionExecutor` — подготовка действий из рассчитанного плана;
- интеграция собственного алгоритма через `DecisionProviders::AI`;
- адаптивное выполнение плана в `Games::RunAiTurns`;
- проверка соответствия ожидаемого состояния фактическому;
- повторное использование одного плана для нескольких последовательных действий;
- повторное планирование при изменении состояния или недопустимости следующего действия;
- прогнозирование потенциальных атакующих для совместной атаки;
- оценка возможности открыть штабную атаку перемещением техники;
- фиксированная задержка между последовательными действиями AI.

Начальные параметры Beam Search:

```text
depth = 5
width = 10
```

Для задержки между действиями:

```ruby
ACTION_DELAY_SECONDS = 2.5
```

Проверена интеграция повторного использования плана. В одном из интеграционных сценариев AI выполнил два розыгрыша взводов, последующую атаку штаба и завершение хода при одном вызове планировщика.

В ходе разработки также исправлена проверка принадлежности техники игроку в `GameEngine::Actions::Move` с учётом несовпадения типов идентификаторов. Добавлена регрессионная проверка.

### Результат первоначальной разработки AI

Собственный движок способен:

- анализировать разрешённое состояние партии;
- моделировать гипотетические действия;
- оценивать стратегическую ценность состояний;
- искать последовательности действий;
- выполнять действия через существующую игровую архитектуру;
- продолжать план при совпадении ожидаемого и фактического состояния;
- перестраивать план при изменении игровой ситуации.

Браузерное тестирование подтвердило способность AI перемещать технику, выполнять последовательности действий и атаковать штаб противника. В одной из проверенных партий давление на штаб привело к победе AI.

При этом наблюдались ситуации, в которых AI отправлял отдельную технику в атаку вместо подготовки группы. Также остаются возможности улучшить выбор момента совместной атаки и оценку резервных позиций.

Эти наблюдения не препятствуют первоначальному закрытию Stage 25. Они зафиксированы как возможные направления дальнейшего развития.

**Дальнейшая калибровка AI отложена до накопления достаточного количества игровых наблюдений.**

## Возможные будущие улучшения AI

Возвращение к развитию собственного AI возможно при наличии достаточного количества наблюдений и конкретных примеров поведения.

Основные направления:

1. Корректировка весов `StrategicEvaluator`.
2. Улучшение накопления техники и координации нескольких танков.
3. Оценка выгодности ожидания перед совместной атакой.
4. Устранение неоправданного отступления на резервные позиции.
5. Улучшение оценки освобождения клеток для размещения новой техники.
6. Проверка производительности Beam Search.
7. Дополнительная проверка поведения в реальных партиях.

При возвращении к этим задачам необходимо:

- сначала анализировать конкретную игровую ситуацию;
- проверять влияние изменений на другие стратегические решения;
- не вводить дополнительные бонусы за уже учитываемые возможности;
- сохранять возможность выгодных одиночных атак;
- не изменять работающие компоненты без подтверждённой причины;
- проверять изменения автоматизированными тестами и браузерными партиями.

Подробности текущей реализации и архитектурные ограничения находятся в `OPPONENT_ENGINE.md`.

## Архитектурные и рабочие ограничения

Основная архитектура:

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

Обязательные правила:

- `GameEngine` — единственный арбитр игровых правил.
- AI выбирает допустимое действие, но не изменяет `GameState` напрямую.
- Реальные действия выполняются через `GameActionRunner`.
- `VisibleState` — граница доступа AI к игровой информации.
- Гипотетические действия выполняются только на изолированном состоянии.
- UI, Stimulus и Turbo не изменяют `GameState`.
- Боевые события описывают результат `GameEngine`.
- Не использовать Redis.
- Не менять PostgreSQL 12/14.
- Не менять игровую механику без согласования.
- Язык интерфейса — украинский.
- CSS и графика не должны влиять на игровые правила.
- Не удалять работающий код на основании неподтверждённых гипотез.
- Не сокращать и не изменять существующие анимации без отдельного согласования.

Рабочие правила и дополнительные ограничения проекта находятся в `AGENTS.md`.
