**Stage 25.2 — безопасная симуляция игровых действий (`StateSimulator`).**

Создан файл:

```text
app/services/decision_providers/opponent_engine/planning/state_simulator.rb
```

Реализуется построение изолированного состояния для гипотетического моделирования действий AI.

Первый целевой прогон теста:

```text
5 runs, 20 assertions, 1 failures, 0 errors, 0 skips
```

Обнаруженная ошибка:

```text
Technique does not belong to player
```

Предварительно установлена причина: `VisibleState` хранит ключи `players` как строки, но `current_player_id` и `player_id` игровых объектов могут сохранять исходный тип. При создании Engine Action используется идентификатор игрока, который должен совпадать по типу с идентификатором владельца объекта.

Предложенное исправление — передавать в Engine Action исходный идентификатор из `VisibleState`:

```ruby
player_id: @visible_state["current_player_id"],
```

вместо внутреннего строкового `@player_id`.

**Исправление ещё не подтверждено повторным тестовым прогоном.**

Следующий шаг:

1. Проверить и применить предложенное исправление.
2. Повторно запустить целевой тест `StateSimulator`.
3. Добиться прохождения целевого теста.
4. После этого выполнить полный `bin/rails test`.

## Обязательные архитектурные границы

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

- GameEngine — единственный арбитр игровых правил.
- AI выбирает Action, но не изменяет GameState.
- GameActionRunner сохраняет только успешные действия.
- AI получает только разрешённое состояние.
- Turbo, Stimulus и UI не изменяют GameState.
- Автотесты не вызывают реальные API.
- Постоянный AI-игрок и его колоды не создаются заново на каждую партию.
- Не вводить Redis.
- Не менять PostgreSQL 12/14.
- Язык интерфейса — украинский.
- Не менять игровую механику без согласования.
- Боевые события описывают результат Engine.
- CSS и графика не должны менять правила.
- Локальные файлы пользователя важнее устаревших копий GitHub.
- Не изменять работающий код на основании неподтверждённых гипотез.
- GitHub используется только для чтения.
- Не сокращать и не изменять существующие анимации без отдельного согласования.

Первоначально использовалась модель:

```text

```

Параметры:

- Structured Outputs со строгой схемой `action_index`;

#### Индикаторы движения

`movement_count` содержит количество оставшихся перемещений.

Для отображения используется:

```ruby
movement_remaining =
  movement_count.clamp(0, movement_limit)
```

Не использовать формулу:

```text
movement_limit - movement_count
```

После выставления техники:

```text
movement_count = 0
```

Количество и цвет колёс отражают оставшиеся перемещения и принадлежность техники.

Подсветка не гарантирует наличие допустимого маршрута.

#### Огневая мощь

Учитываются:

- `has_attacked` в ход владельца;
- `has_counterattacked` в ход противника.

Собственная техника при доступном соответствующем действии отображается зелёным цветом, техника противника — красным. После использования действия значение становится стандартного цвета.

#### Зеркальное отображение

Собственная техника отображается в стандартной ориентации, техника противника зеркально отражается по горизонтали.

Используется:

```css
transform: scaleX(-1);
```

Отражается только иллюстрация. Рамка, название, символ класса, колёса и характеристики не отражаются.

Отдельные зеркальные PNG не создаются.

#### Индикатор способности

**Статус: ВЫПОЛНЕНО И ПРОВЕРЕНО.**

Для техники со способностью отображается компактная иконка на квадратной карте поля.

- Полный текст эффекта на поле не размещается.
- Описание способности доступно при наведении.
- Для сенсорных устройств предусмотрен способ просмотра описания без наведения.
- Индикатор является отдельным элементом интерфейса.
- Данные о способности берутся из карты и разрешённого состояния.
- UI не определяет игровую логику способности.

# Stage 25 — собственный алгоритм AI-соперника (В РАБОТЕ)

## Цель

Заменить внешнюю LLM-модель собственным алгоритмом принятия решений.

Новый AI должен:

- работать без внешних LLM и AI API;
- не требовать Groq/OpenAI API-ключей;
- использовать только разрешённое состояние;
- выбирать только серверные допустимые действия;
- оценивать не только непосредственную выгоду действия, но и последствия последовательности действий;
- учитывать стратегические цели партии;
- адаптироваться к фактическому состоянию после каждого выполненного действия;
- выполнять действия через существующую инфраструктуру;
- сохранять все действующие ограничения безопасности и архитектуры.

Переход выполняется постепенно. Старые провайдеры и зависимости от внешнего API удаляются только после переноса функциональности, проверки зависимостей и подтверждения работоспособности нового алгоритма.

## 25.1. Архитектура собственного AI

Планируемая архитектура состоит из трёх основных компонентов:

```text
StrategicEvaluator
       ↓
TacticalPlanner
       ↓
ActionExecutor
```

### StrategicEvaluator

Отвечает за оценку общей ситуации в партии и определение стратегических целей.

Учитывает:

- безопасность собственного штаба;
- угрозы штабу противника;
- наличие опасных объектов противника;
- боевое преимущество;
- состояние собственной армии;
- возможности развития армии;
- выгодность текущих позиций;
- перспективы будущих атак;
- доступные ресурсы и оставшиеся возможности действий.

Оценка должна учитывать положение на поле и перспективы нескольких последующих действий, а не только локальную выгоду.

### TacticalPlanner

Отвечает за поиск и сравнение последовательностей действий.

Планируется использовать Beam Search.

Начальные параметры поиска:

```text
depth = 5
width = 10
```

Это стартовые параметры для реализации и последующей калибровки, а не окончательные значения.

Основные принципы:

- строить несколько возможных последовательностей действий;
- оценивать промежуточные состояния;
- сравнивать планы по их общей стратегической ценности;
- не выбирать действие исключительно по локальной выгоде;
- учитывать ограничения допустимых действий;
- прекращать поиск текущей последовательности при достижении `end_turn`.

`end_turn` рассматривается как терминальное действие для текущего поиска. На этом этапе не моделируется ответный ход противника.

### ActionExecutor

Отвечает за выполнение найденного плана в реальной партии.

Основные принципы:

- выполнять первое действие рассчитанного плана;
- использовать существующую инфраструктуру `GameActionRunner`;
- не применять симуляционное состояние к реальной игре;
- после выполнения получать актуальное разрешённое состояние;
- сравнивать фактическое состояние с ожидаемым;
- продолжать оставшуюся часть плана, если она всё ещё актуальна;
- перестраивать план, если состояние изменилось или действие стало недопустимым.

План не должен считаться неизменным после первого действия.

## 25.2. Безопасная симуляция действий — StateSimulator (В РАБОТЕ)

### Назначение

`StateSimulator` должен создавать гипотетические состояния для поиска последовательностей действий.

Симуляция нужна только для планирования. Она не должна сохранять изменения в базу данных или вызывать побочные эффекты реальной игры.

Основной файл:

```text
app/services/decision_providers/opponent_engine/planning/state_simulator.rb
```

### Источник данных

Для симуляции используется только `VisibleState`.

Не передавать в `TacticalPlanner` или другие компоненты полного `Game.state`.

Не передавать полную историю боя.

Разрешённые события могут использоваться как дополнительная информация, но не должны раскрывать скрытые данные.

### Построение изолированного состояния

`StateSimulator` должен строить минимальное совместимое с GameEngine состояние на основании `VisibleState`.

Правила:

- настоящая рука AI сохраняется;
- рука противника представляется заглушками в соответствии с известным количеством карт;
- колоды обоих игроков представляются заглушками в соответствии с известным количеством карт;
- кладбища представляются заглушками в соответствии с известным количеством карт;
- открытые объекты поля сохраняются;
- штабы, техника, взводы, ресурсы и таймеры сохраняются в пределах разрешённой информации;
- неизвестные карты не восстанавливаются по скрытым данным;
- неизвестные карты остаются заглушками и не могут разыгрываться;
- после симуляции наружу возвращаются только новый `VisibleState` и разрешённые события;
- внутреннее симуляционное `GameState` не передаётся планировщику.

### Заглушки неизвестных карт

Заглушки должны иметь:

- уникальный строковый `card_id`;
- `card_type: "unknown"`.

`ActionOptions` не должен считать заглушки доступными для розыгрыша.

Нельзя допускать, чтобы симуляция позволяла AI разыграть карту, которой фактически нет в его известной руке.

### Выполнение симуляционного действия

Для каждого гипотетического действия:

1. Получить допустимые действия для текущего симуляционного состояния.
2. Выбрать соответствующее действие.
3. Нормализовать payload рекурсивно из string keys в symbol keys.
4. Создать `GameEngine::Action`.
5. Выполнить действие через настоящий `GameEngine::Engine`.
6. Получить новое состояние.
7. Построить из него следующий `VisibleState`.
8. Повторно создать `ActionOptions` для следующего шага.

После каждого действия допустимые действия должны рассчитываться заново. Нельзя использовать список действий, сформированный для предыдущего состояния.

### Фиксированное время

Для последовательности симуляционных действий используется единый `current_time`.

Это необходимо, чтобы все гипотетические действия одной цепочки оценивались относительно согласованного времени.

`GameEngine::Engine.new(state, current_time:).call(action)` должен использовать переданное фиксированное время и не изменять исходное состояние.

### Отсутствие побочных эффектов

Симуляция не должна:

- записывать изменения в базу данных;
- вызывать ActiveRecord callbacks;
- создавать реальные GameAction;
- выполнять Turbo broadcasts;
- изменять статистику;
- использовать `GameActionRunner` для гипотетических действий;
- изменять реальное состояние игры.

Для симуляции используется настоящий `GameEngine::Engine`, поскольку именно он является арбитром игровых правил.

При этом симуляция работает только с изолированным состоянием, построенным из разрешённого `VisibleState`.

### Текущая проблема

Первый целевой прогон:


Ошибка:

```text

```

Предполагаемая причина — несовпадение типов `player_id` при построении Engine Action.

Предложенное исправление:

```ruby
player_id: @visible_state["current_player_id"],
```

Исправление пока не подтверждено повторным тестом.

**Критерий завершения 25.2:** целевые тесты `StateSimulator` проходят, а симуляция корректно обрабатывает допустимые действия, неизвестные карты, идентификаторы игроков и фиксированное время без побочных эффектов.

## 25.3. Стратегическая оценка — StrategicEvaluator (ЗАПЛАНИРОВАНО)

После завершения безопасной симуляции реализовать оценку состояния партии.

Оценка должна учитывать несколько направлений:

1. Защита собственного штаба.
2. Создание угрозы штабу противника.
3. Устранение непосредственных угроз.

6. Улучшение позиций.
7. Создание возможностей для последующих атак.
8. Сохранение важных игровых объектов.

Стратегическая оценка должна сравнивать состояния, а не просто присваивать высокую оценку отдельному типу действия.

Веса и формулы оценки будут калиброваться на реальных партиях.

## 25.5. Исполнение плана — ActionExecutor (ЗАПЛАНИРОВАНО)

Реализовать адаптивное выполнение плана.

Алгоритм:

1. Получить актуальный `VisibleState`.
2. Рассчитать план.
3. Выполнить первое действие через существующую инфраструктуру.
4. Получить новое реальное состояние.
5. Сравнить фактическое состояние с ожидаемым.
6. Если оставшаяся часть плана актуальна — продолжить.
7. Если состояние отличается или действие больше недопустимо — пересчитать план.

План временно хранить в памяти одного экземпляра `Games::RunAiTurns`.

Не добавлять постоянное хранение планов в базу данных без отдельной необходимости и согласования.

## 25.8. Задержка между действиями AI (РЕАЛИЗОВАНО)

Для последовательных действий AI добавлена фиксированная задержка:

```ruby
ACTION_DELAY_SECONDS = 2.5
```

Предусмотрена возможность внедрения `sleeper` для тестов.

Пауза выполняется только при соблюдении условий:

- предыдущее действие успешно выполнено;
- тот же AI продолжает свой ход;
- игра остаётся в статусе `started`;
- лимит действий AI ещё не достигнут.

Пауза выполняется после Turbo broadcast и перед следующей итерацией AI-цикла.

Назначение — дать клиенту время на обработку обновления игрового интерфейса и воспроизведение визуальных эффектов.

Ограничения текущей реализации:

- это фиксированная задержка, а не подтверждение завершения клиентской очереди анимаций;
- строгая синхронизация потребует отдельного механизма подтверждения готовности клиента;
- при лимите в 20 действий максимальное количество пауз между действиями — 19;
- максимальная суммарная задержка при таком сценарии — 47,5 секунды;
- синхронный запрос и удерживаемые в ходе AI-цикла ресурсы, включая advisory lock и DB connection, остаются занятыми во время ожидания.
