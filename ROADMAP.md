## Обязательные архитектурные границы

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

- GameEngine — единственный арбитр правил; AI выбирает Action, но не изменяет state.
- GameActionRunner сохраняет только успешный Action, проверяет актуальность digest.
- AI получает только VisibleState, не видит скрытые карты противника.
- Turbo/Stimulus/UI не изменяют GameState и не реализуют правила.
- Автотесты не вызывают реальный API и не требуют ключей.
- Постоянный AI-игрок/колоды не создаются на каждую партию.
- Не вводить Redis; не менять PostgreSQL 12/14.

## Stage 21 — AI в игровом процессе (ЗАВЕРШЁН)

### AI-игрок и постоянные колоды

- Game поддерживает `pvp` и `ai`; Player#ai?; уникальный частичный индекс для единственного AI-игрока.
- `AiPlayers::Setup` — постоянный идемпотентный AI-игрок.
- `AiPlayers::DecksSetup` — три постоянные колоды: США вес 13, СССР 22, Германия 28.
- `Matchmaking::AiDeckSelector` — полная совместимая AI-колода ±10% веса, при нескольких — ближайшая.
- Реализован серверный сервис создания AI-игры.

### Решения, применение Action, цикл

- DecisionProviders::AI, Context, Groq/OpenAI adapters, проверка ответа и ограниченные повторы.
- GameActionRunner блокирует игру, сверяет digest, вызывает Engine, сохраняет только успешный state.
- Games::RunAiTurns: максимум 20 действий, максимум 3 stale-state retry, PostgreSQL advisory lock, остановка при смене хода/завершении/ошибке/лимите.
- GamesController запускает AI после хода человека и при открытии игры, если ходит AI.
- **Пошаговый Turbo реализован:** Games::RunAiTurns вызывает on_action после сохранения каждого AI-действия; GamesController перечитывает Game и отправляет broadcast_game_update(action_events) отдельно для каждого действия и каждого игрока. Человеческое действие также рассылается до запуска AI-цикла.
- Тестами проверены отдельные broadcasts, соответствующие events/state, скрытая информация, частичные результаты при ошибке и повторный запуск AI после временной ошибки.
- В браузере подтверждены последовательные действия и завершение полноценной AI-партии, в том числе поражение от пустой колоды.

### Groq — текущая конфигурация

`openai/gpt-oss-20b`, Structured Outputs со строгой JSON-схемой `action_index`, `reasoning_effort=low`, `max_completion_tokens=512`. Адаптер выбирает действие из серверного `legal_actions`, не дублирует `available_actions` в передаваемом состоянии, логирует usage и HTTP-диагностику. Есть ограниченный retry HTTP 429 при распознаваемой положительной задержке и ограниченная обработка временных сетевых ошибок. Если допустимо ровно одно действие, API-вызов пропускается.

Системная инструкция оставлена без сокращения по решению пользователя. Исторически наблюдались HTTP 429/TPM, HTTP 400 `json_validate_failed` в прежнем JSON-режиме и высокий расход completion tokens. Текущая конфигурация успешно работала в полной браузерной партии, но это не гарантирует отсутствия будущих сетевых ошибок и rate limit.

## Stage 22 — дополнительная надёжность AI (ЗАВЕРШЁН)

### Проверенное покрытие

Существующие тесты `DecisionProviders::AI` подтверждают:

- обработку корректного решения и нормализацию payload;
- защиту `player_id` и отсутствие скрытой руки противника;
- повторные попытки при некорректном формате ответа;
- остановку после трёх некорректных решений;
- отсутствие повтора при неожиданном исключении провайдера;
- ограниченные попытки при невалидном индексе действия Groq.

Существующие тесты `Games::RunAiTurns` подтверждают:

- защиту от параллельных AI-циклов одной игры и независимость разных игр;
- освобождение advisory lock после ошибок и невалидных действий;
- сохранение ранее выполненного действия при ошибке следующего решения;
- соблюдение лимита действий;
- повтор решения при stale state и остановку после исчерпания повторов;
- остановку цикла при завершении игры или передаче хода человеку во время решения.

### Проверка интеграции и диагностического логирования

- Полноценный AI lifecycle с реальным Groq уже проверен в браузере на Stage 21.
- После браузерной проверки менялось диагностическое логирование, а не игровой цикл, поэтому повторная партия не потребовалась.
- Убраны подробные данные руки AI, `payload.inspect`, тело HTTP-ошибки и сообщения исключений из ряда диагностических записей.
- Сохранены классы ошибок, token usage, `finish_reason`, HTTP-коды и доступные rate-limit headers.
- Дублирующие тесты не добавлялись.
- Полный набор после изменений прошёл успешно: `534 runs, 2031 assertions, 0 failures, 0 errors, 0 skips`.

**Stage 22 закрыт по решению пользователя.** Абсолютная устойчивость внешнего API не гарантируется. Дальнейшие эксперименты с retry, тайм-аутами, расходом токенов и дополнительными сетевыми сценариями можно выполнять отдельно, если появится конкретная проблема или новая цель.

## Stage 25 — Собственный движок AI-соперника

Разработать и подключить собственный алгоритм AI-соперника, чтобы уменьшить зависимость от внешней модели и расходов API.

Цели:

- принимать решения на основе разрешённого состояния и серверных допустимых действий;
- применять действия только через существующий Action → GameActionRunner → GameEngine;
- не раскрывать скрытую информацию;
- сделать соперника интересным и достаточно сильным;
- сравнить простой наступательный алгоритм, LLM и при необходимости гибридный подход.

Сравнение стратегий — отдельная задача. Оно не требует изменения игровых правил без отдельного согласования.
