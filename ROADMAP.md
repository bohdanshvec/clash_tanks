## Обязательные архитектурные границы

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

- GameEngine — единственный арбитр игровых правил.
- AI выбирает Action, но не изменяет state.
- GameActionRunner сохраняет только успешные действия.
- AI получает только разрешённое состояние.
- Turbo, Stimulus и UI не изменяют GameState.
- Автотесты не вызывают реальные API.
- Постоянный AI-игрок и его колоды не создаются заново на каждую партию.
- Не вводить Redis.
- Не менять PostgreSQL 12/14.
- Язык интерфейса — украинский.
- Не менять игровую механику без согласования.
- Боевые события описывают результат Engine.
- CSS и графика не должны менять правила.
- Локальные файлы пользователя важнее устаревших копий GitHub.
- Не изменять работающий код на основании неподтверждённых гипотез.
- GitHub используется только для чтения.

## Stage 21 — AI в игровом процессе (ЗАВЕРШЁН)

### AI-игрок и постоянные колоды

- Game поддерживает `pvp` и `ai`.
- `Player#ai?`.
- `AiPlayers::Setup` — постоянный AI-игрок.
- `AiPlayers::DecksSetup` — постоянные колоды.
- `Matchmaking::AiDeckSelector` выбирает совместимую колоду в пределах ±10% веса.
- Реализован сервис создания AI-игры.

### Решения и цикл

- Реализованы `DecisionProviders::AI`, Context и адаптеры.
- `GameActionRunner` проверяет digest и сохраняет успешный state.
- `Games::RunAiTurns` ограничивает количество действий и повторов.
- Используется PostgreSQL advisory lock.
- Реализован пошаговый Turbo broadcast.
- AI может начинать игру первым.
- В браузере подтверждена полноценная AI-партия.

### Groq

Используется модель:

`openai/gpt-oss-20b`

Structured Outputs со строгой схемой `action_index`.

`reasoning_effort=low`.

Модель выбирает действие из серверного списка `legal_actions`.

Предусмотрены ограниченные повторы временных ошибок и HTTP 429.

Если доступно одно действие, API не вызывается.

### Общая структура

Для техники предусматривается многослойное отображение:

1. Иллюстрация техники.

### Форматы ресурсов

- Квадратный формат `1024 × 1024 px` — техника на игровом поле.
- Вертикальный формат `848 × 1264 px` — полноразмерная карта в каталоге, колодах, редакторе и руке игрока.

Иллюстрация и рамка — отдельные ресурсы одинакового размера.

Рамка располагается над иллюстрацией.

### Рамки

Для каждой нации предусматривается собственный стиль броневой рамки.

Основные показатели должны располагаться согласованно между нациями.

Рамка техники без способности может иметь более простую композицию.

Рамка техники со способностью должна иметь дополнительную область описания эффекта в полноразмерном варианте.

На квадратной карте поля полный текст способности не размещается.

### Обнаруженная проблема

При проверке техники в браузере пользователь обнаружил белый фон, закрывающий иллюстрацию.

Предварительная диагностика указывает на непрозрачную область PNG-рамки.

Наличие альфа-канала не гарантирует наличие прозрачных пикселей.

Перед изменением CSS необходимо проверить исходный PNG.

Если непрозрачность подтверждается, исправить рамку так, чтобы:

- область иллюстрации была прозрачной;
- декоративные элементы сохранились;
- размеры остались `1024 × 1024 px`;
- рамка и иллюстрация совмещались.

Не использовать случайные CSS-обходы вместо исправления исходного изображения.

| Тип техники | Обозначение |

### Характеристики

На нижней панели:

- огневая мощь;
- HP;
- топливо.

Значения берутся из `VisibleState`.

Правило отображения:

- `0` — существующая характеристика равна нулю;
- `–` — характеристика неприменима.

### Индикаторы движения

Количество индикаторов определяется `movement_limit`.

Использованные перемещения определяются `movement_count`.

Для одного перемещения:

- до движения индикатор красный;
- после движения — стандартный.

Для двух перемещений:

- до первого движения оба индикатора красные;
- после первого один остаётся красным;
- после второго оба становятся стандартного цвета.

Красный цвет используется только во время хода владельца.

Во время хода противника индикаторы стандартного цвета.

Индикаторы не гарантируют наличие допустимого маршрута.

### Огневая мощь

Использовать тот же принцип, что и для штабов:

- `has_attacked` в ход владельца;
- `has_counterattacked` в ход противника.

Неиспользованная атака или контратака обозначается красным цветом.

Допустимость действия определяется сервером.

### Propshaft

При подключении CSS-компонента наблюдалась ошибка:

```text
Propshaft::MissingAssetError:
The asset 'components/technique-field.css'
was not found in the load path.
```

После выполнения:

```bash
bin/rails assets:precompile
```

пользователь подтвердил запуск игры.

Причина первоначальной ошибки окончательно не установлена.

При повторении проверить файл, путь, импорт и конфигурацию Propshaft.

## Шаг 12. Графическое оформление приказов

**Статус: ЗАПЛАНИРОВАНО.**

Приказ не размещается на игровом поле.

Отдельный квадратный формат не требуется.

Для полноразмерных карт использовать вертикальный формат `848 × 1264 px`.

- прозрачную рамку;
- область названия;
- читаемую область описания эффекта;
- динамический текст, не встроенный в PNG.

Не использовать рамку техники с показателями HP, топлива и движения, если эти показатели не относятся к приказу.

## Шаг 13. Графическое оформление взводов

**Статус: ЗАПЛАНИРОВАНО.**

Предусмотреть два формата:

- `1024 × 1024 px` — взвод на игровом поле;
- `848 × 1264 px` — полноразмерная карта в каталоге, колодах, редакторе и руке игрока.

Иллюстрация и рамка должны быть отдельными ресурсами.

### Рамки

Предусмотрены варианты:

- `attack`;
- `defense`.

Выбор варианта определяется данными карты.

Не добавлять характеристики, которых нет в правилах.

### Игровое поле

Область взводов должна учитывать четыре квадратных слота.

Не изменять игровую логику слотов ради визуального оформления.

### Порядок работы
