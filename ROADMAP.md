## Обязательные архитектурные границы

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

- GameEngine — единственный арбитр игровых правил.
- AI выбирает Action, но не изменяет GameState.
- GameActionRunner сохраняет только успешные действия.
- AI получает только разрешённое состояние.
- Turbo, Stimulus и UI не изменяют GameState.
- Автотесты не вызывают реальные API.
- Постоянный AI-игрок и его колоды не создаются заново на каждую партию.
- Не вводить Redis.
- Не менять PostgreSQL 12/14.
- Язык интерфейса — украинский.
- Не менять игровую механику без согласования.
- Боевые события описывают результат Engine.
- CSS и графика не должны менять правила.
- Локальные файлы пользователя важнее устаревших копий GitHub.
- Не изменять работающий код на основании неподтверждённых гипотез.
- GitHub используется только для чтения.
- Не сокращать и не изменять существующие анимации без отдельного согласования.

## Stage 21 — AI в игровом процессе (ЗАВЕРШЁН)

### AI-игрок и колоды

- Game поддерживает режимы `pvp` и `ai`.
- Реализован `Player#ai?`.
- `AiPlayers::Setup` создаёт постоянного AI-игрока.
- `AiPlayers::DecksSetup` создаёт постоянные колоды AI.
- `Matchmaking::AiDeckSelector` выбирает совместимую колоду в пределах ±10% веса.
- Реализован сервис создания AI-игры.

### Решения и игровой цикл

- Реализованы `DecisionProviders::AI`, Context и адаптеры.
- `GameActionRunner` проверяет digest и сохраняет успешное состояние.
- `Games::RunAiTurns` ограничивает количество действий и повторов.
- Используется PostgreSQL advisory lock.
- Реализован пошаговый Turbo broadcast.
- AI может начинать игру первым.
- Полноценная AI-партия проверена в браузере.

### Groq

Используется модель:

```text
openai/gpt-oss-20b
```

Параметры:

- Structured Outputs со строгой схемой `action_index`;
- `reasoning_effort=low`;
- модель выбирает действие из серверного списка `legal_actions`;
- предусмотрены ограниченные повторы временных ошибок и HTTP 429;
- если доступно одно действие, внешний API не вызывается.

```text

```

```text

{nation}_{display}_{type}_{variant}_border.png
```

```ruby
card_image_path(
  nation:,
  display:,
  type:,
  code:
)

card_border_path(
  nation:,
  display:,
  type:,
  variant: nil
)
```

Проверена поддержка Unicode в путях изображений, в том числе немецкой буквы `ß`. Не выполнять произвольную транслитерацию.

#### Индикаторы движения

`movement_count` содержит количество оставшихся перемещений.

Для отображения используется:

```ruby
movement_remaining =
  movement_count.clamp(0, movement_limit)
```

Не использовать формулу:

```text
movement_limit - movement_count
```

После выставления техники:

```text
movement_count = 0
```

Количество и цвет колёс отражают оставшиеся перемещения и принадлежность техники.

Подсветка не гарантирует наличие допустимого маршрута.

#### Огневая мощь

Учитываются:

- `has_attacked` в ход владельца;
- `has_counterattacked` в ход противника.

Собственная техника при доступном соответствующем действии отображается зелёным цветом, техника противника — красным. После использования действия значение становится стандартного цвета.

#### Зеркальное отображение

Собственная техника отображается в стандартной ориентации, техника противника зеркально отражается по горизонтали.

Используется:

```css
transform: scaleX(-1);
```

Отражается только иллюстрация. Рамка, название, символ класса, колёса и характеристики не отражаются.

Отдельные зеркальные PNG не создаются.

#### Индикатор способности

**Статус: ВЫПОЛНЕНО И ПРОВЕРЕНО.**

Для техники со способностью отображается компактная иконка на квадратной карте поля.

- Полный текст эффекта на поле не размещается.
- Описание способности доступно при наведении.
- Для сенсорных устройств предусмотрен способ просмотра описания без наведения.
- Индикатор является отдельным элементом интерфейса.
- Данные о способности берутся из карты и разрешённого состояния.
- UI не определяет игровую логику способности.

- атакующий взвод — круг;
- защитный взвод — крест X.

Выбор варианта определяется данными карты.

Реализованы четыре квадратных слота с каждой стороны поля:

```text
.platoon-bar
.platoon-slot
```

Высота панели взводов соответствует высоте центрального поля.

Характеристики отображаются динамически. Цветовая индикация принадлежности различает собственные взводы и взводы противника.

Огневая мощь атакующих взводов использует индикацию готовности, связанную с возможностью атаки штаба. Защитные взводы от этого правила не зависят.

## Боевые эффекты и адаптивность

### 14. Очередь боевых эффектов

**Статус: ВЫПОЛНЕНО.**

Используется Stimulus-контроллер:

```text
app/javascript/controllers/game_combat_effects_controller.js
```

Реализована очередь последовательного воспроизведения событий.

Основные принципы:

- события обрабатываются последовательно;
- следующий эффект запускается после завершения предыдущего;
- повторный запуск обработки не создаёт параллельную очередь;
- на время воспроизведения эффектов управление блокируется;
- визуальные эффекты используют серверные события;
- JavaScript не определяет игровой результат и не рассчитывает урон;
- после завершения очереди управление возвращается в обычное состояние.

#### Реализованные эффекты

- выстрел и контратака;
- подсветка клетки;
- попадание;
- повреждение и изменение HP;
- разрушение щита при потере HP;
- уничтожение техники и взводов;
- повреждение штаба;
- урон от приказов;
- урон штабу при попытке взять карту из пустой колоды;
- визуальная индикация пустой колоды;
- визуальные эффекты приказов;
- отображение направления перемещения техники.

Для перемещения используется событие:

```text
technique_moved
```

Направление перемещения отображается визуальной стрелкой для обоих игроков. Старый локальный обработчик клика для отображения стрелки удалён. При отключении Stimulus-контроллера созданная стрелка удаляется.

Эффекты используют серверные события и не рассчитывают игровые результаты на клиенте.

**Существующие анимации не сокращать и не изменять без отдельного согласования.**

Изменения `prefers-reduced-motion` в текущий объём работ не входят.

### 17. Окно завершения партии

**Статус: ВЫПОЛНЕНО И ПРОВЕРЕНО.**

После завершения партии отображается центральное окно результата.

Оно содержит:

- кнопку выхода;

Игровой интерфейс приглушается и блокируется для взаимодействия.

Заголовок определяется относительно текущего игрока:

```text

```

```text

```

Партію завершено
```

Источник данных:

visible_state["result"]
```

### 18. Адаптивная геометрия игрового поля

**Статус: ВЫПОЛНЕНО И ПРОВЕРЕНО.**

Размеры центрального поля, панелей взводов и информационных колонок связаны общей системой CSS-переменных:

```css
--battlefield-width
--battlefield-height
--platoon-slot-size
--player-info-width
```

Центральное поле имеет геометрию:

```text
3 строки × 5 столбцов
```

Высота:

```css
--battlefield-height: calc(
  var(--battlefield-width) * 3 / 5
);
```

Размер квадратного слота взвода:

```css
--platoon-slot-size: calc(
  var(--battlefield-width) * 3 / 20
);
```

Ширина информационной колонки:

```css
--player-info-width: calc(
  var(--battlefield-width) * 145 / 900
);
```

Для текста, кнопок и отступов используются адаптивные размеры, в том числе `clamp()`.

Пользователь проверил уменьшение окна браузера и подтвердил корректный результат.

Завершение адаптивного оформления для проверенных размеров не означает автоматического подтверждения полноценной мобильной версии.

## Stage 25 — собственный алгоритм AI-соперника

Разработать собственный алгоритм AI.

### Цели

- использовать только разрешённое состояние;
- выбирать серверные допустимые действия;
- применять Action только через GameActionRunner;
- не раскрывать скрытые данные;
- уменьшить зависимость от внешнего API;
- обеспечить достаточно сильного соперника.

### Архитектурные ограничения

Собственный AI должен соблюдать существующую архитектуру:

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

AI отвечает за выбор действия, но не за проверку и исполнение игровых правил.

Не переносить игровую логику из GameEngine в алгоритм AI.
