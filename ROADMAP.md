### Текущая работа Stage 25

Основные технические компоненты собственного AI реализованы и интегрированы.

Текущая архитектура:

```text
VisibleState
     ↓
ActionOptions
     ↓
TacticalPlanner
     ├── StateSimulator
     └── StrategicEvaluator
     ↓
ActionExecutor
     ↓
Games::RunAiTurns
     ↓
GameActionRunner
     ↓
GameEngine
```

Планирование выполняется на разрешённом `VisibleState`. Гипотетические действия проходят через изолированный `GameEngine`, а реальные действия — через существующую инфраструктуру `GameActionRunner`.

Реализовано адаптивное продолжение плана: после каждого реального действия проверяется соответствие фактического состояния ожидаемому и допустимость следующего действия. Если план больше не соответствует состоянию игры, AI строит новый.

## Обязательные архитектурные границы

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState
```

- GameEngine — единственный арбитр игровых правил.
- AI выбирает Action, но не изменяет GameState.
- GameActionRunner сохраняет только успешные действия.
- AI получает только разрешённое состояние.
- Turbo, Stimulus и UI не изменяют GameState.
- Автотесты не вызывают реальные API.
- Постоянный AI-игрок и его колоды не создаются заново на каждую партию.
- Не вводить Redis.
- Не менять PostgreSQL 12/14.
- Язык интерфейса — украинский.
- Не менять игровую механику без согласования.
- Боевые события описывают результат Engine.
- CSS и графика не должны менять правила.
- Локальные файлы пользователя важнее устаревших копий GitHub.
- Не изменять работающий код на основании неподтверждённых гипотез.
- GitHub используется только для чтения.
- Не сокращать и не изменять существующие анимации без отдельного согласования.

- `Matchmaking::AiDeckSelector` выбирает совместимую колоду в пределах ±10% веса.
- Реализован сервис создания AI-игры.

### Решения и игровой цикл

- Реализованы `DecisionProviders::AI`, Context и адаптеры.
- `GameActionRunner` проверяет digest и сохраняет успешное состояние.
- `Games::RunAiTurns` ограничивает количество действий и повторов.
- Используется PostgreSQL advisory lock.
- Реализован пошаговый Turbo broadcast.
- AI может начинать игру первым.
- Полноценная AI-партия проверена в браузере.

### Groq

Первоначально использовалась модель:

```text
openai/gpt-oss-20b
```

Параметры:

- Structured Outputs со строгой схемой `action_index`;
- `reasoning_effort=low`;
- модель выбирала действие из серверного списка `legal_actions`;
- предусматривались ограниченные повторы временных ошибок и HTTP 429;
- если доступно одно действие, внешний API не вызывался.

**Примечание:** внешний LLM-провайдер является частью прежней реализации. В Stage 25 предусмотрен переход на собственный алгоритм и последующее удаление ненужных зависимостей от внешнего API.

Обозначения создаются средствами интерфейса, не встраиваются в PNG.

Цветовая индикация относительно наблюдателя:

- собственная техника — зелёный `#32cd32`;
- техника противника — красный `#ff3030`.

#### Индикаторы движения

`movement_count` содержит количество оставшихся перемещений.

Для отображения используется:

```ruby
movement_remaining =
  movement_count.clamp(0, movement_limit)
```

Не использовать формулу:

```text
movement_limit - movement_count
```

После выставления техники:

```text
movement_count = 0
```

Количество и цвет колёс отражают оставшиеся перемещения и принадлежность техники.

Подсветка не гарантирует наличие допустимого маршрута.

#### Огневая мощь

Учитываются:

- `has_attacked` в ход владельца;
- `has_counterattacked` в ход противника.

Собственная техника при доступном соответствующем действии отображается зелёным цветом, техника противника — красным. После использования действия значение становится стандартного цвета.

#### Зеркальное отображение

Собственная техника отображается в стандартной ориентации, техника противника зеркально отражается по горизонтали.

Используется:

```css
transform: scaleX(-1);
```

Отражается только иллюстрация. Рамка, название, символ класса, колёса и характеристики не отражаются.

Отдельные зеркальные PNG не создаются.

#### Индикатор способности

**Статус: ВЫПОЛНЕНО И ПРОВЕРЕНО.**

# Stage 25 — собственный алгоритм AI-соперника (В РАБОТЕ)

## Цель

Заменить внешнюю LLM-модель собственным алгоритмом принятия решений.

Новый AI должен:

- работать без внешних LLM и AI API;
- не требовать Groq/OpenAI API-ключей;
- использовать только разрешённое состояние;
- выбирать только серверные допустимые действия;
- оценивать не только непосредственную выгоду действия, но и последствия последовательности действий;
- учитывать стратегические цели партии;
- адаптироваться к фактическому состоянию после каждого выполненного действия;
- выполнять действия через существующую инфраструктуру;
- сохранять все действующие ограничения безопасности и архитектуры.

Переход выполняется постепенно. Старые провайдеры и зависимости от внешнего API удаляются только после переноса функциональности, проверки зависимостей и подтверждения работоспособности нового алгоритма.

## 25.1. Архитектура собственного AI

Реализованная архитектура:

```text
VisibleState
     ↓
ActionOptions
     ↓
TacticalPlanner
     ├── StateSimulator
     └── StrategicEvaluator
     ↓
ActionExecutor
     ↓
Games::RunAiTurns
     ↓
GameActionRunner
     ↓
GameEngine
```

### ActionOptions

`DecisionProviders::ActionOptions` формирует список допустимых действий на основании `VisibleState` и доступных действий.

Поддерживаются:

- перемещение техники;
- атаки;
- розыгрыш карт;
- завершение хода.

Список действий формируется заново для каждого симулируемого состояния. Заглушки неизвестных карт не должны становиться доступными для розыгрыша.

### StateSimulator

Отвечает за безопасное моделирование гипотетических действий на изолированном состоянии.

Использует настоящий `GameEngine::Engine`, но не изменяет реальную игру и не создаёт побочных эффектов.

### StrategicEvaluator

Отвечает за оценку разрешённого состояния игры и сравнение стратегической ценности вариантов.

### TacticalPlanner

Выполняет поиск последовательностей действий с использованием Beam Search.

### ActionExecutor

Преобразует найденные шаги плана в реальные `GameEngine::Action` и передаёт их существующему игровому циклу.

### Games::RunAiTurns

Организует выполнение действий, хранит план в памяти текущего экземпляра сервиса и проверяет его актуальность после каждого реального действия.

## 25.2. Безопасная симуляция действий — StateSimulator (ЗАВЕРШЕНО)

### Назначение

`StateSimulator` создаёт гипотетические состояния для поиска последовательностей действий.

Симуляция нужна только для планирования. Она не сохраняет изменения в базу данных и не вызывает побочные эффекты реальной игры.

Основной файл:

```text
app/services/decision_providers/opponent_engine/planning/state_simulator.rb
```

### Источник данных

Для симуляции используется только `VisibleState`.

Полный `Game.state` не передаётся в `TacticalPlanner` или другие компоненты планирования.

Полная история боя не передаётся планировщику.

После симуляции наружу возвращаются только новый `VisibleState` и разрешённые события. Внутреннее симуляционное `GameState` не передаётся планировщику.

### Построение изолированного состояния

`StateSimulator` строит минимальное совместимое с GameEngine состояние на основании `VisibleState`.

Реализованы следующие принципы:

- настоящая рука AI сохраняется;
- рука противника представляется заглушками в соответствии с известным количеством карт;
- колоды обоих игроков представляются заглушками в соответствии с известным количеством карт;
- кладбища представляются заглушками в соответствии с известным количеством карт;
- открытые объекты поля сохраняются;
- штабы, техника, взводы, ресурсы и таймеры сохраняются в пределах разрешённой информации;
- неизвестные карты не восстанавливаются по скрытым данным;
- неизвестные карты остаются заглушками и не могут разыгрываться;
- после симуляции наружу возвращаются новый `VisibleState` и разрешённые события;
- исходный `VisibleState` не мутируется.

### Заглушки неизвестных карт

Заглушки используют:

- уникальный строковый `card_id`;
- `card_type: "unknown"`.

`ActionOptions` не считает заглушки доступными для розыгрыша.

Симуляция не позволяет AI разыграть карту, которой фактически нет в его известной руке.

### Выполнение симуляционного действия

Для каждого гипотетического действия:

1. Получить допустимые действия для текущего симуляционного состояния.
2. Выбрать соответствующее действие.
3. Нормализовать payload рекурсивно из string keys в symbol keys.
4. Создать `GameEngine::Action`.
5. Выполнить действие через настоящий `GameEngine::Engine`.
6. Получить новое состояние.
7. Построить из него следующий `VisibleState`.
8. Повторно создать `ActionOptions` для следующего шага.

После каждого действия допустимые действия рассчитываются заново.

### Фиксированное время

Для последовательности симуляционных действий используется единый `current_time`.

Это обеспечивает согласованное время оценки всех гипотетических действий одной цепочки.

`GameEngine::Engine.new(state, current_time:).call(action)` использует переданное фиксированное время.

### Отсутствие побочных эффектов

Симуляция не:

- записывает изменения в базу данных;
- вызывает ActiveRecord callbacks;
- создаёт реальные GameAction;
- выполняет Turbo broadcasts;
- изменяет статистику;
- использует `GameActionRunner` для гипотетических действий;
- изменяет реальное состояние игры.

Для симуляции используется настоящий `GameEngine::Engine`, поскольку именно он является арбитром игровых правил.

При этом симуляция работает только с изолированным состоянием, построенным из разрешённого `VisibleState`.

### Исправленная проблема идентификаторов

Во время первоначальной реализации был обнаружен тестовый сбой:

```text
Technique does not belong to player
```

Причина заключалась в несовпадении типов идентификаторов игроков при построении Engine Action.

Исправление использует исходный идентификатор из `VisibleState`:

```ruby
player_id: @visible_state["current_player_id"],
```

Исправление подтверждено повторными тестами.

**Критерий завершения 25.2 выполнен:** симуляция корректно обрабатывает проверенные сценарии, неизвестные карты, идентификаторы игроков и фиксированное время без побочных эффектов.

### Условия продолжения плана

План может быть продолжен, если:

- тот же AI продолжает ход;
- ожидаемое состояние и индекс следующего шага существуют;

- `server_time`;
- `turn_started_at`;
- `remaining_time` каждого игрока.

При ошибке устаревшего состояния план также очищается перед повторной попыткой.

## 25.9. Задержка между действиями AI (РЕАЛИЗОВАНО)

```ruby
ACTION_DELAY_SECONDS = 2.5
```

Пауза выполняется только при соблюдении условий:

- предыдущее действие успешно выполнено;
- тот же AI продолжает свой ход;
- игра остаётся в статусе `started`;
- лимит действий AI ещё не достигнут.

Пауза выполняется после Turbo broadcast и перед следующей итерацией AI-цикла.

Назначение — дать клиенту время на обработку обновления игрового интерфейса и воспроизведение визуальных эффектов.

Ограничения текущей реализации:

- это фиксированная задержка, а не подтверждение завершения клиентской очереди анимаций;
- строгая синхронизация потребует отдельного механизма подтверждения готовности клиента;
- при лимите в 20 действий максимальное количество пауз между действиями — 19;
- максимальная суммарная задержка при таком сценарии — 47,5 секунды;
- синхронный запрос и удерживаемые в ходе AI-цикла ресурсы, включая advisory lock и DB connection, остаются занятыми во время ожидания.
