# ARCHITECTURE.md

## Основной поток

```text
Decision Provider → Action → GameActionRunner → GameEngine → GameState

Browser → Controller → Decision Provider → Action → GameActionRunner → GameEngine → GameState
                                                                         ↓
Browser ← Stimulus ← Turbo ← VisibleState ← сохранённый GameState
```

GameEngine — единственный арбитр игровых правил.

`GameEngine::Action` содержит:

- `player_id`;
- `type`;
- `payload`.

`GameEngine::Result` содержит результат выполнения, новое состояние и events.

Engine работает с копией GameState.

При ошибке новое состояние не сохраняется.

Человек использует `DecisionProviders::Human`.

AI использует `DecisionProviders::AI`.

Любое действие проходит через GameActionRunner и GameEngine.

AI может самостоятельно планировать последовательность действий, но не применяет их напрямую. Каждое реальное действие исполняется через GameActionRunner и GameEngine.

## Game и GameState

`Game.state` — authoritative JSONB snapshot.

Основные поля:

- `status`;
- `turn_number`;
- `current_player_id`;
- `turn_started_at`;
- `players`;
- `field`;
- `result`.

Состояние игрока:

- `nation_id`;
- `hand`;
- `deck`;
- `graveyard`;
- `platoons`;
- `resources`;
- `remaining_time`;
- `empty_deck_draw_attempts`.

GameState не обращается к ActiveRecord.

Постоянная Deck не меняется во время партии.

Для waiting:

`Game.state == nil`

AI-игра создаётся сразу в started.

### Игровое поле

`field` содержит HQ и Technique.

Platoon хранится в:

`state["players"][player_id]["platoons"]`

Четыре слота сохраняют пустые позиции после уничтожения.

Логические координаты не зависят от визуальной перспективы.

DOM использует:

`data-position="row,column"`

### Runtime Technique

Содержит:

- тип;
- идентификаторы;
- имя;
- характеристики;
- флаги атаки;
- счётчики движения.

Не содержит `price`, `weight`, `card_type` или вложенный `technique`.

У Technique нет Armor.

### Runtime Platoon

Содержит:

- `firepower`;
- `hp`;
- `armor`;
- `fuel`.

Правила определяются `GAME_RULES.md`.

## Decision Provider

Provider выбирает намерение, но не применяет игровые правила.

### Base и Context

`DecisionProviders::Base` задаёт интерфейс `call`.

`DecisionProviders::Context` формирует:

- `player_id`;
- `visible_state`;
- available actions.

Контекст рекурсивно заморожен.

Provider не получает полный скрытый state.

### Human

`DecisionProviders::Human` преобразует:

- `move`;
- `attack`;
- `play_card`;
- `end_turn`;
- `surrender`.

Результат — `GameEngine::Action`.

Controller передаёт действие в GameActionRunner.

### AI

`DecisionProviders::AI` — единая точка входа для AI-решений.

AI не изменяет GameState и не исполняет игровые правила.

Для выбора действия используется один из настроенных механизмов принятия решений.

Текущая реализация собственного AI — `opponent_engine`.

При использовании собственного алгоритма AI:

1. Получает `DecisionProviders::Context`.
2. Использует только `VisibleState` и разрешённые действия.
3. Формирует варианты действий через `ActionOptions`.
4. Строит план через `TacticalPlanner`.
5. Передаёт выбранный шаг в `ActionExecutor`.
6. Возвращает `GameEngine::Action` для обычного исполнения через GameActionRunner.

`AI#call_with_plan` возвращает `PlanDecision`, содержащий:

- `action`;
- `plan`;
- `expected_visible_state`;
- `next_step_index`.

При некорректном или недопустимом решении применяется ограниченная повторная попытка.

Формат ответа Provider не заменяет проверку Engine.

### Внешние LLM-провайдеры

Исторически AI использовал:

- `DecisionProviders::GroqAdapter`;
- `DecisionProviders::OpenAiAdapter`.

Groq Chat Completions API использовал модель:

`openai/gpt-oss-20b`

Модель получала разрешённое состояние и серверные `legal_actions`, возвращая `action_index`.

Использовались Structured Outputs, строгая JSON-схема и подменяемый HTTP transport.

Автотесты не вызывают реальные API.

Внешний LLM-механизм сохраняется до завершения проверки собственного AI и проверки зависимостей. После этого планируется удалить ненужные адаптеры, настройки и переменные окружения.

`AI_PROVIDER` используется для выбора реализации. Для собственного AI предусмотрено значение:

`opponent_engine`

## Собственный AI — Opponent Engine

Основная реализация:

`app/services/decision_providers/opponent_engine/`

Цель — самостоятельный алгоритм принятия решений, который строит последовательность допустимых действий и оценивает их стратегическую ценность.

Основные компоненты:

```text
VisibleState
    ↓
ActionOptions
    ↓
TacticalPlanner
    ├── StateSimulator
    │       └── GameEngine::Engine
    └── StrategicEvaluator
    ↓
ActionExecutor
    ↓
GameActionRunner
    ↓
GameEngine
```

### ActionOptions

Файл:

`app/services/decision_providers/action_options.rb`

Формирует варианты действий на основе `VisibleState.available_actions`.

Поддерживаемые действия:

- `move`;
- `attack`;
- `play_card`;
- `end_turn`.

Варианты строятся из серверных разрешённых действий.

Неизвестные карты, представленные заглушками, не могут быть разыграны.

`ActionOptions` не заменяет проверку GameEngine.

### StateSimulator

Файл:

`app/services/decision_providers/opponent_engine/planning/state_simulator.rb`

Создаёт изолированное симуляционное состояние на основе `VisibleState`.

Использует настоящий:

`GameEngine::Engine`

Симуляция выполняется без сохранения изменений в БД и без реальных побочных эффектов.

Основные ограничения:

- не изменяет исходный `VisibleState`;
- не обращается к скрытым данным противника;
- использует настоящую руку AI;
- неизвестные карты противника и колод представлены заглушками;
- использует фиксированный `current_time` в пределах цепочки симуляции;
- возвращает новый `VisibleState` и разрешённые events.

Симулятор не является альтернативной реализацией игровых правил. Все игровые действия проверяются и исполняются настоящим GameEngine на копии состояния.

### StrategicEvaluator

Файл:

`app/services/decision_providers/opponent_engine/planning/strategic_evaluator.rb`

Оценивает стратегическую ценность состояния.

Использует только `VisibleState`.

Учитываются:

- HP и firepower штабов;
- fuel штабов;
- HP, firepower, range и fuel техники;
- HP, firepower, armor и fuel взводов;
- позиции техники;
- доступные атаки и перемещения;
- доступные для розыгрыша карты;
- ресурсы;
- количество карт в руке;
- завершение партии.

Победа и поражение имеют терминальные оценки:

- победа: `+1_000_000`;
- поражение: `-1_000_000`.

Начальные веса реализованы. Они требуют дальнейшей калибровки по результатам реальных партий.

### TacticalPlanner

Файл:

`app/services/decision_providers/opponent_engine/planning/tactical_planner.rb`

Использует Beam Search.

Текущие параметры:

- глубина поиска: 5;
- ширина поиска: 10.

Каждый узел содержит:

- `visible_state`;
- `actions`;
- `steps`;
- `score`;
- `terminal`.

Каждый шаг сохраняет:

- выбранный `action`;
- ожидаемый `expected_visible_state`.

Результат плана содержит:

- `actions`;
- `steps`;
- `score`;
- `expanded_nodes`.

Переход хода, `end_turn` и завершение игры являются терминальными условиями поиска.

Текущая реализация не моделирует ответный ход противника.

Параметры поиска и качество стратегических оценок требуют проверки на реальных партиях.

### ActionExecutor

Файл:

`app/services/decision_providers/opponent_engine/action_executor.rb`

Преобразует шаг плана в `GameEngine::Action`.

Поддерживает:

`ActionExecutor.call(plan:, context:)`

Этот интерфейс возвращает первое действие плана.

Для последовательного исполнения используется:

`ActionExecutor.execute(plan:, context:, step_index:)`

Результат содержит:

- `action`;
- `expected_visible_state`;
- `next_step_index`.

Проверяются индекс шага, наличие действий, наличие шагов и соответствие действий сохранённому плану.

Для Action используется актуальный `context.state_digest`.

Payload рекурсивно преобразуется к ожидаемому формату ключей.

ActionExecutor не исполняет действие самостоятельно.

### Повторное использование плана

`Games::RunAiTurns` хранит план в памяти текущего экземпляра сервиса.

Постоянное хранение плана в БД не требуется.

Перед каждым следующим действием проверяются:

1. Совпадение игрока.
2. Соответствие фактического состояния ожидаемому `VisibleState`.
3. Допустимость следующего действия в актуальном `ActionOptions`.
4. Корректность индекса следующего шага.

При сравнении состояния исключаются изменяемые временные поля:

- `server_time`;
- `turn_started_at`;
- `remaining_time`.

Если фактическое состояние соответствует ожидаемому и следующее действие остаётся допустимым, план продолжается.

Если состояние изменилось, действие больше недопустимо или план не соответствует контексту, старый план очищается и строится новый.

Таким образом, план не считается гарантией исполнения: каждое реальное действие повторно проверяется актуальным состоянием и GameEngine.

### Текущий статус Opponent Engine

Реализованы:

- `ActionOptions`;
- `StateSimulator`;
- `StrategicEvaluator`;
- `TacticalPlanner`;
- `ActionExecutor`;
- интеграция с `DecisionProviders::AI`;
- адаптивное повторное использование плана в `Games::RunAiTurns`.

Техническая интеграция выполнена.

Качество стратегических решений ещё не подтверждено достаточным количеством реальных партий.

Следующие задачи:

- проверить поведение за первого и второго игрока;
- выявить тактические ошибки;
- проверить выбор атак, перемещений и карт;
- оценить эффективность планирования;
- откалибровать веса `StrategicEvaluator`;
- проверить производительность Beam Search;
- после проверки собственного AI удалить устаревшие внешние LLM-компоненты.

## Action и GameActionRunner

`GameEngine::Action` содержит:

- `player_id`;
- `type`;
- `payload`.

Вложенные Hash/Array копируются и замораживаются.

GameActionRunner:

1. Блокирует игру.
2. Проверяет digest.
3. Вызывает Engine.
4. Сохраняет только успешный результат.

Отказанный или устаревший Action не должен менять state.

AI не может изменять GameState напрямую.

Даже если AI заранее симулировал действие, реальное исполнение всегда проходит через GameActionRunner и GameEngine.

## VisibleState и AvailableActions

`GameEngine::VisibleState` — разрешённая граница данных UI/AI.

Игрок видит свою руку.

Противник видит только разрешённую публичную информацию и количества карт.

Содержимое чужих hand/deck/graveyard скрыто.

`GameEngine::AvailableActions` формирует серверные подсказки для:

- перемещений;
- атак;
- размещения техники;
- размещения взводов;
- приказов.

Эти подсказки не заменяют проверку Engine.

`ActionOptions`, `StateSimulator`, `StrategicEvaluator` и `TacticalPlanner` работают в пределах разрешённого `VisibleState`.

Нельзя передавать собственному AI полный GameState или раскрывать скрытые данные противника ради улучшения оценки.

## Attack и контратака

Боевая механика разделена между Action, Rules и Attacks.

### GameEngine::Actions::Attack

Файл:

`app/services/game_engine/actions/attack.rb`

Отвечает за:

- проверку действия;
- выбор сценария;
- запуск исполнения;
- события;
- завершение партии.

### GameEngine::Rules::CombatType

Файл:

`app/services/game_engine/rules/combat_type.rb`

Сценарии:

- `:ranged`;
- `:normal`;
- `:ptsau_first`.

Определяет сценарий, но не исполняет выстрелы.

### GameEngine::Rules::Counterattack

Файл:

`app/services/game_engine/rules/counterattack.rb`

Проверяет допустимость контратаки.

Не наносит урон и не изменяет GameState.

### GameEngine::Attacks::CombatExecutor

Файл:

`app/services/game_engine/attacks/combat_executor.rb`

Исполняет:

- дальний бой;
- обычный бой;
- специальный сценарий ПТ-САУ;
- выстрелы;
- разрешённые контратаки.

### GameEngine::Attacks::HeadquartersCombat

Файл:

`app/services/game_engine/attacks/headquarters_combat.rb`

Отвечает за:

- огневую мощь штаба;
- повреждения взводов;
- поглощение урона бронёй;
- уничтожение взводов;
- graveyard;
- сохранение пустых слотов;
- урон штабу.

### Правила, которые необходимо сохранять

- Дальний бой не вызывает контратаку.
- В обычном бою атакующий стреляет первым.
- Выживший защитник может ответить при соблюдении условий.
- В специальном сценарии ПТ-САУ стреляет первой.
- Уничтоженный атакующий не выполняет ответный выстрел.
- Контратака штаба против штаба не выполняется.
- Повторная контратака ограничена правилами.
- Флаг контратаки устанавливается только при выполненном выстреле.
- Уничтоженный объект не стреляет.
- Огневая мощь штаба учитывает взводы.
- Взводы получают повреждения после выстрела штаба.
- Броня взводов поглощает входящий урон.
- Уничтоженные взводы отправляются в graveyard.
- Пустые слоты не уплотняются.
- Уничтожение штаба завершает партию через `GameEngine::FinishGame`.

### Границы ответственности

```text
Actions::Attack
    ├── Rules::CombatType
    ├── Attacks::CombatExecutor
    │       ├── Rules::Counterattack
    │       └── Attacks::HeadquartersCombat
    └── GameEngine::FinishGame
```

Не менять механику без согласования.

## Games::RunAiTurns

Файл:

`app/services/games/run_ai_turns.rb`

Сервис выполняет последовательность реальных действий AI.

Ограничения:

- максимум 20 действий;
- PostgreSQL advisory lock;
- до трёх stale-state retry;
- перечитывание Game;
- остановка при смене хода;
- остановка при завершении;
- сохранение частичных результатов.

`on_action` вызывается после сохранения успешного действия.

Callback не изменяет state.

Для собственного `opponent_engine` сервис может сохранять план в памяти одного экземпляра `RunAiTurns` и адаптивно использовать его для нескольких последовательных действий.

Перед каждым следующим шагом проверяются ожидаемое состояние и допустимость действия.

При несовпадении состояния план очищается и решение пересчитывается.

Все реальные действия выполняются через GameActionRunner.

При stale state план очищается перед повторной попыткой.

## UI, Turbo и перспектива

Каждый игрок подписан на:

`[game, current_player_id]`

`GamesController#broadcast_game_update(events)` формирует отдельный VisibleState.

Скрытый полный state не передаётся браузеру.

Пошаговый AI broadcast:

```text
Human Action
  → GameActionRunner
  → save
  → broadcast human events
  → RunAiTurns
      → AI Action
      → GameActionRunner
      → save
      → broadcast AI events
      → next AI Action
```

Не возвращаться к накоплению всех AI-событий в один broadcast.

Controller организует рассылку.

Engine отвечает за правила.

## Графическое отображение игровых объектов — Stage 24

### Общий принцип

Игровые объекты отображаются многослойными HTML/CSS-компонентами.

Статические графические ресурсы отделены от динамических характеристик.

Источник характеристик — `GameEngine::VisibleState`.

UI не изменяет GameState.

Основные форматы:

- 1024 × 1024 px — квадратные изображения объектов игрового поля;
- 848 × 1264 px — вертикальные изображения карточек.

Иллюстрация и рамка являются отдельными ресурсами.

Динамические характеристики не встраиваются в изображения.

### Штабы

Используется общий компонент `headquarters-field` для:

- USA;
- СССР;
- Германии.

Структура:

```text
headquarters-field
├── headquarters-field__illustration
│   └── изображение штаба
├── headquarters-field__frame
│   └── прозрачная национальная рамка
└── headquarters-field__stats
    ├── headquarters-field__stat--firepower
    ├── headquarters-field__stat--hp
    └── headquarters-field__stat--fuel
```

Иллюстрация располагается под рамкой.

CSS обрезает изображение по форме рамки.

Характеристики находятся поверх рамки.

### Графические ресурсы штабов

Каталог:

`app/assets/images/headquarters/`

Шаблоны имён:

```text
{nation}_field_picture_headquarters.png
{nation}_field_border_headquarters.png
```

Поддерживаемые значения:

- `usa`;
- `ussr`;
- `germany`.

Размер:

1024 × 1024 px.

Для всех трёх наций используется единый ERB-шаблон.

Числовые характеристики не встраиваются в изображения.

### Динамические характеристики

На нижней панели:

- `firepower`;
- `hp`;
- `fuel`.

Значения поступают из текущего `VisibleState`.

Нулевые значения отображаются как `0`.

Обновление выполняется существующим механизмом Turbo.

### Цветовая индикация огневой мощи штаба

Для текущего игрока готовность определяется через:

`!cell["has_attacked"]`

Для штаба противника:

`!cell["has_counterattacked"]`

При доступной огневой мощи используется цвет готовности.

После выстрела или контратаки значение отображается стандартным цветом.

CSS-класс:

`headquarters-field__stat--ready`

Индикация не гарантирует допустимость атаки.

GameEngine остаётся единственным арбитром правил.

### Техника

Реализован многослойный компонент отображения техники.

Общая структура:

```text
technique-field
├── illustration
├── frame
├── technique-type-symbol
├── movement-indicators
├── stats
│   ├── firepower
│   ├── hp
│   └── fuel
└── effects
```

Иллюстрация и национальная рамка остаются отдельными ресурсами.

Обозначение типа техники размещается в верхнем правом углу.

Используются масштабируемые SVG-символы.

Техника противника отображается с горизонтальным зеркалированием иллюстрации.

Цветовые индикаторы учитывают владельца объекта и текущий ход.

### Индикаторы движения техники

Количество индикаторов определяется:

`movement_limit`

Использованные перемещения определяются:

`movement_count`

Во время хода владельца красным цветом показываются неиспользованные перемещения.

Для одного перемещения:

```text
movement_count = 0 → 1 красный индикатор
movement_count = 1 → 0 красных индикаторов
```

Для двух перемещений:

```text
movement_count = 0 → 2 красных индикатора
movement_count = 1 → 1 красный индикатор
movement_count = 2 → 0 красных индикаторов
```

Во время хода противника все индикаторы стандартного цвета.

Для техники без возможности перемещения индикаторы не должны показывать доступное перемещение.

Красный индикатор не гарантирует наличие допустимого маршрута.

### Индикация атаки техники

Используется тот же принцип, что и для штабов:

- `has_attacked` в ход владельца;
- `has_counterattacked` в ход противника.

Для атакующей техники огневая мощь отображается цветом готовности, пока штаб владельца ещё не израсходовал возможность атаки.

После атаки или контратаки штаба цвет готовности снимается.

Для защитной техники аналогичная индикация не применяется.

Цветовая индикация не заменяет `AvailableActions`.

### Взводы

Для взводов используются отдельные варианты рамок:

- `attack`;
- `defense`.

Тип определяется по характеристикам:

- `firepower > 0` — атакующий взвод;
- `armor > 0` — защитный взвод.

Основная характеристика:

- атакующий взвод — `firepower`;
- защитный взвод — `armor`.

Верхний правый символ:

- атакующий взвод — круг;
- защитный взвод — повёрнутый крест/X.

Для атакующих взводов индикация огневой мощи связана с готовностью штаба владельца к атаке.

Если штаб уже атаковал или контратаковал, цвет готовности снимается.

Для защитных взводов эта индикация не применяется.

Взводы размещаются в четырёх отдельных слотах.

Слоты имеют квадратную форму, визуально согласованную с клетками поля, и сохраняют пустые позиции после уничтожения взводов.

### Рамки карточек и графические ресурсы

Иллюстрации карточек используются отдельно от рамок.

Формат вертикальных иллюстраций:

848 × 1264 px.

Формат квадратных изображений объектов поля:

1024 × 1024 px.

Национальные рамки:

- USA — песочные/коричневые;
- СССР — зелёные/оливковые;
- Германия — серые/графитовые.

Типы рамок:

- HQ;
- Technique;
- Platoon attack;
- Platoon defense;
- Order.

Для Technique используется рамка способности с вертикальной областью текста эффекта.

Для отображения способности на поле используется отдельный символ и описание при наведении, а не полная текстовая рамка карточки.

Для приказов используется вертикальная рамка без характеристик fuel, HP и огневой мощи.

Прозрачность рамок должна обеспечиваться реальными прозрачными пикселями, а не только наличием альфа-канала.

### Каталог графических ресурсов

Основные каталоги:

- `app/assets/images/headquarters/`;
- `app/assets/images/cards/`.

Путь к изображению карточки формируется существующим helper:

`card_image_path`

Изображения должны соответствовать утверждённым шаблонам именования и национальным вариантам рамок.

После проверки графических ресурсов не должно быть отсутствующих или неожиданных файлов относительно каталога карточек и ожидаемых иллюстраций.

### Будущие игровые эффекты

Предусматривается отдельный слой.

Источник событий:

`GameEngine::Result.events`

Подготовлены события:

- `shot_fired`;
- `counterattack_fired`;
- `damage_applied`;
- `technique_destroyed`;
- `platoon_damaged`;
- `platoon_destroyed`;
- `empty_deck_draw_attempt`.

Планируемые визуальные реакции:

- выстрел;
- контратака;
- попадание;
- повреждение техники;
- повреждение штаба;
- повреждение взвода;
- уничтожение техники;
- уничтожение взвода;
- урон от приказа;
- урон при пустой колоде.

Эффекты не должны изменять характеристики или повторно применять урон.

### Архитектурные ограничения

1. GameEngine остаётся единственным арбитром правил.
2. VisibleState является границей данных UI.
3. ERB формирует отображение.
4. CSS отвечает за внешний вид.
5. Stimulus обрабатывает взаимодействия и эффекты.
6. Turbo обновляет интерфейс.
7. Изображения не содержат динамических характеристик.
8. DOM-якоря сохраняются.
9. Графика не изменяет игровую механику.

## Редактор колод

Редактор использует ERB и Stimulus.

Текущие решения:

- создание рядом с заголовком;
- сохранение и отмена в верхней области;
- сортировка по типу, весу и названию;
- перенос карточек по строкам;
- украинские надписи;
- вертикальные изображения карточек;
- согласованное отображение штабов и карточек.

Изменения оформления не меняют правила Deck.

## Authentication и matchmaking

```text
browser session → current_player → GamePlayer → Action.player_id → GameEngine
```

Гость создаётся при `/play`.

Получает три starter Deck.

Переиспользуется в сессии.

PvP matchmaking использует совместимость веса ±15%.

`Matchmaking::Join` применяет блокировку.

`CleanupStaleWaitingGames` очищает устаревшие waiting games.
