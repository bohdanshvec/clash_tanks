# ART_STYLE.md

Основной документ художественного направления Clash Tanks.

Документ фиксирует согласованные требования к визуальному стилю, исходным изображениям, рамкам игровых карт, многослойному отображению, динамическим характеристикам и будущим игровым эффектам.

Описанные как требования элементы не считаются реализованными до фактического внедрения и проверки в браузере.

## 1. Назначение

Цель — создать единый узнаваемый стиль для сайта и игровой части Clash Tanks.

Документ применяется к:

- фоновым изображениям;
- Header и навигации;
- основным страницам;
- штабам;
- технике;
- взводам;
- приказам;
- рамкам игровых карт;
- условным обозначениям;
- динамическим характеристикам;
- индикаторам движения и способностей;
- анимациям и игровым эффектам.

Художественное оформление не должно менять игровую механику или нарушать архитектуру проекта.

**Главный архитектурный принцип: GameEngine определяет результат, UI отображает его.**

## 2. Основное художественное направление

Стиль — военно-историческая реалистичная цифровая живопись с заметной художественной обработкой.

Основные ориентиры:

- реалистичные формы и пропорции техники;
- исторически правдоподобное вооружение, снаряжение и окружение;
- металл, броня и другие правдоподобные материалы;
- умеренные следы эксплуатации;
- оливковые, тёмно-зелёные, графитовые и песочные оттенки;
- умеренные золотистые акценты;
- выразительное, но естественное освещение;
- читаемый силуэт основного объекта;
- ясная визуальная иерархия;
- единая художественная подача для всех наций;
- композиция, соответствующая назначению изображения.

Иллюстрации должны выглядеть как художественные изображения, а не как необработанные фотографии или трёхмерные модели.

При этом художественная обработка не должна искажать узнаваемые особенности исторической техники.

Проект должен иметь собственный стиль, не копирующий логотипы и графические материалы других игр.

**Главный принцип: художественная выразительность сочетается с удобством использования.**

При оформлении новых компонентов по возможности использовать существующие CSS-переменные темы.

Не вводить новые цвета без необходимости.

### 3.1. Национальные особенности рамок

Для игровых карт используются национальные особенности оформления:

- США — песочные и светло-коричневые оттенки;
- СССР — зелёные и оливковые оттенки;
- Германия — серые, графитовые и стальные оттенки.

Национальные различия должны сохранять общий художественный стиль Clash Tanks.

### 3.2. Цвета игровых индикаторов

Красный цвет используется для обозначения неиспользованного игрового действия или другого состояния, определённого конкретным компонентом.

Для динамических характеристик:

- красный — соответствующее действие ещё не использовано;
- стандартный цвет — действие использовано либо индикатор неактивен.

Цветовая индикация не должна создавать впечатление, что действие обязательно допустимо.

Например, красная огневая мощь не гарантирует наличие допустимой цели.

Точные правила цветовой индикации определяются соответствующими компонентами.

## 4. Фоны

### 4.1. Основные страницы

Основные страницы используют статичный фон сайта.

Предусмотренный путь:

`app/assets/images/backgrounds/site_background.png`

Таблица стилей:

`app/assets/stylesheets/site-background.css`

Точные актуальные пути необходимо проверять по локальным файлам.

Требования:

- не искажать пропорции изображения;
- не затемнять фон чрезмерно;
- не снижать читаемость текста;
- не мешать взаимодействию с элементами интерфейса;
- сохранять визуальную согласованность на разных экранах.

### 4.2. Header

Header является самостоятельной визуальной областью.

Основной фон страницы не должен автоматически распространяться на Header.

Допускаются:

- тёмно-оливковая поверхность;
- текстура металла;
- отдельный фон;
- логотип проекта.

### 4.3. Страница правил

Страница правил должна обеспечивать комфортное чтение длинного текста.

Декоративный фон не должен мешать контрасту и читаемости.

### 4.4. Игровой экран

Игровой экран использует отдельное оформление.

Фон должен быть приглушённым и не конкурировать с:

- игровым полем;
- картами;
- штабами;
- техникой;
- взводами;
- сообщениями;
- игровыми эффектами.

## 5. Два утверждённых формата игровых карт

Используются два исходных формата для разных областей интерфейса.

**Эти форматы утверждены и не должны изменяться без отдельного согласования.**

### 5.1. Квадратный формат — 1024 × 1024 px

Применение: объекты, отображаемые непосредственно на игровом поле.

Квадратный формат используется для:

- штабов;
- техники;
- взводов.

Иллюстрация объекта и прозрачная рамка создаются как отдельные изображения одинакового исходного размера.

Не использовать вертикальную иллюстрацию, механически обрезанную до квадрата, вместо подготовленного квадратного исходника.

На поле взводы размещаются в четырёх квадратных слотах.

Высота области взводов должна учитывать четыре квадратных места для отображения объектов.

Приказ не размещается на игровом поле, поэтому отдельный квадратный формат приказа не требуется.

### 5.2. Вертикальный формат — 848 × 1264 px

Применение: полноразмерные карты в следующих областях:

- каталог «Карти»;
- раздел «Колоди»;
- редактор колоды;
- рука игрока во время партии.

Формат используется для:

- штабов;
- техники;
- взводов;
- приказов.

Для каждой карты иллюстрация и рамка — отдельные PNG-ресурсы одинакового размера.

Перед интеграцией проверять совмещение рамки и изображения.

Рамка располагается поверх иллюстрации.

### 5.3. Масштабирование

Размеры `1024 × 1024 px` и `848 × 1264 px` — размеры исходных ресурсов, а не фиксированные CSS-размеры отображения.

На страницах карты масштабируются средствами интерфейса.

Не создавать отдельные исходные изображения только ради разных размеров карточек на экране.

Не растягивать изображения с нарушением пропорций.

### 5.4. Композиция вертикальных иллюстраций

При подготовке вертикальных изображений основной объект должен оставаться хорошо различимым после масштабирования.

Если исходное изображение переводится из квадратного формата в вертикальный, предпочтительно расширять сюжет сверху и снизу, а не обрезать основной объект.

Допускается располагать основной объект немного выше геометрического центра, если это улучшает композицию и оставляет пространство для нижней части рамки.

Конкретное положение зависит от типа карты и её рамки.

## 6. Многослойная структура карты

Общая концепция слоёв:

1. Иллюстрация объекта.
2. Прозрачная рамка соответствующего типа карты и нации.
3. Условные обозначения, если они необходимы.
4. Динамические характеристики и текст.
5. Интерактивные индикаторы и эффекты.

Фактический состав слоёв зависит от компонента.

Рамка должна соответствовать геометрии иллюстрации.

Необходимо проверять:

- прозрачные области;
- масштабирование;
- положение деталей;
- взаимное наложение слоёв;
- читаемость текста;
- отсутствие перекрытия важных частей иллюстрации.

### 6.1. Содержимое иллюстрации

Не встраивать в иллюстрацию:

- название карты;
- текущие HP;
- огневую мощь;
- топливо;
- стоимость;
- динамические индикаторы;
- текст способности;
- элементы управления страницей.

Эти элементы должны оставаться отдельными интерфейсными элементами.

### 6.2. Содержимое рамки

Рамка содержит только постоянные декоративные элементы:

- броневые панели;
- национальные эмблемы;
- декоративные границы;
- площадки для названия;
- площадки для характеристик;
- декоративные элементы, соответствующие типу карты.

Числовые значения, названия и изменяемые игровые обозначения не должны быть встроены в PNG-рамку.

### 6.3. Прозрачность рамки

**Прозрачность является обязательным техническим требованием.**

Область рамки, предназначенная для отображения иллюстрации, должна быть действительно прозрачной.

Наличие альфа-канала у PNG само по себе не означает, что изображение содержит прозрачные пиксели.

В частности, PNG в режиме RGBA может оставаться полностью непрозрачным.

Для альфа-канала в диапазоне 0–255:

- `0` — полностью прозрачный пиксель;
- `255` — полностью непрозрачный пиксель;
- промежуточные значения — частичная прозрачность.

Декоративные элементы рамки могут оставаться непрозрачными.

Основная область иллюстрации должна пропускать нижний слой.

Не следует автоматически удалять все светлые пиксели рамки: светлые декоративные детали могут быть частью художественного оформления.

### 6.4. Проверка прозрачности

Перед подключением новой рамки необходимо:

1. Открыть PNG в редакторе с поддержкой прозрачности.
2. Проверить наличие прозрачных областей.
3. Проверить, что белый фон не закрывает иллюстрацию.
4. Наложить рамку на тестовую иллюстрацию.
5. Проверить совпадение размеров.
6. Проверить положение декоративных элементов.
7. Проверить результат в браузере.

Если изображение под рамкой не видно из-за непрозрачного фона, сначала исправлять исходный PNG.

Не использовать случайные CSS-обходы для исправления дефектов прозрачности.

## 7. Рамки разных типов карт

Единый художественный стиль не означает одинаковую композицию рамок.

У каждого типа карты может быть собственное расположение:

- названия;
- эмблемы;
- характеристик;
- описания способности;
- индикаторов.

### 7.1. Штаб

Рамка штаба должна учитывать отображение национальной иллюстрации и динамических характеристик.

Для штабов на игровом поле подтверждена многослойная схема:

1. Иллюстрация.
2. Прозрачная национальная рамка.
3. Динамические характеристики.

В нижней панели отображаются:

- огневая мощь;
- HP;
- топливо.

Значения поступают из актуального `VisibleState`, а не из PNG.

Для штабов предусмотрены отдельные национальные рамки.

Не добавлять дополнительный символ штаба, если национальная эмблема уже выполняет необходимую декоративную функцию.

### 7.2. Техника

Рамка техники предусматривает:

- область названия;
- национальную эмблему;
- условное обозначение класса;
- индикаторы движения;
- огневую мощь;
- HP;
- топливо;
- индикатор способности, если способность имеется.

Для квадратной рамки техники утверждена следующая композиция:

| Элемент | Расположение |
|---|---|
| Национальная эмблема | Верхний левый угол |
| Название | Верхняя центральная часть |
| Символ класса техники | Верхний правый угол |
| Иллюстрация | Центральная область |
| Индикаторы движения | Слева, над огневой мощью |
| Огневая мощь | Нижняя левая панель |
| HP | Нижняя центральная панель |
| Топливо | Нижняя правая панель |

Для всех трёх наций расположение динамических элементов должно быть согласованным.

Национальные рамки могут отличаться декоративными деталями.

### 7.3. Техника без способности

Использовать более простую композицию без дополнительной области текста способности.

Освободившееся пространство можно использовать для улучшения читаемости и сбалансированного расположения характеристик.

Не добавлять несуществующие характеристики.

### 7.4. Техника со способностью

Для вертикальной карты техники со способностью предусматривается дополнительная область описания эффекта.

Характеристики могут быть расположены немного выше, чтобы оставить место под описание.

Содержимое области способности формируется интерфейсом из данных карты.

Текст не встраивается в изображение.

Квадратный вариант для поля должен сохранять компактность и не содержать полного текста способности.

Вместо текста используется отдельный индикатор способности.

### 7.5. Приказы

Приказ имеет собственную композицию рамки.

Главный акцент:

- название;
- иллюстрация;
- читаемое описание эффекта.

Не использовать для приказа характеристики техники, например:

- топливо;
- HP;
- индикаторы движения;
- огневую мощь,

если они не относятся к данным этого типа карты.

Приказ не размещается на игровом поле, поэтому отдельный квадратный вариант для поля не нужен.

Для приказов используется вертикальный формат `848 × 1264 px`.

### 7.6. Взводы

Для взвода предусматривается собственная композиция рамки, учитывающая его роль и реальные характеристики карты.

Утверждены варианты рамок:

- `attack`;
- `defense`.

Выбор варианта должен соответствовать актуальным данным карты.

Не вводить визуальные обозначения, которые создают ложное впечатление о несуществующих игровых свойствах.

Не добавлять в рамку показатели, которых нет в актуальных данных карты или правилах.

### 7.7. Отображение взводов на игровом поле

Боковая область взводов должна учитывать четыре квадратных слота.

Каждый занятый слот предусматривает:

1. Квадратную иллюстрацию взвода.
2. Соответствующую прозрачную рамку.
3. Динамические данные, предусмотренные игровыми правилами.

Исходный формат — `1024 × 1024 px`.

В каталоге, колодах, редакторе и руке используются вертикальные изображения `848 × 1264 px`.

## 8. Национальные особенности

Для Германии, США и СССР используются отдельные национальные иллюстрации и рамки там, где это соответствует типу карты.

Национальные отличия передаются:

- цветом;
- формой декоративных элементов;
- эмблемами;
- деталями рамки;
- особенностями иллюстрации.

Все три национальных набора должны сохранять общую художественную идентичность Clash Tanks.

### 8.1. Германия

Основные особенности:

- серые и графитовые металлические рамки;
- стальные декоративные элементы;
- немецкая историческая военная символика, соответствующая изображаемому объекту;
- реалистичная немецкая техника.

### 8.2. США

Основные особенности:

- песочные и светло-коричневые рамки;
- характерные американские военные обозначения;
- реалистичная американская техника.

### 8.3. СССР

Основные особенности:

- зелёные и оливковые рамки;
- характерные советские военные обозначения;
- реалистичная советская техника.

Национальные различия не должны нарушать единое расположение игровых характеристик внутри рамок одного типа.

## 9. Карты на страницах и в руке игрока

Полноразмерные карточки используют вертикальный формат `848 × 1264 px`.

Каталог, колоды, редактор и рука игрока должны использовать согласованную визуальную систему.

### 9.1. Каталог карт

Карты должны содержать:

- соответствующую иллюстрацию;
- рамку своего типа;
- название;
- предусмотренные характеристики;
- описание способности или приказа, если применимо.

Динамические данные отображаются средствами HTML/CSS.

### 9.2. Колоды и редактор

Использовать те же вертикальные исходные изображения, что и в каталоге.

Не создавать отдельные PNG только для изменения размера карточки.

Кнопки управления располагаются вне изображения карты.

### 9.3. Рука игрока

- Карты масштабируются CSS до подходящего размера.
- При наведении карточка увеличивается, чтобы можно было рассмотреть иллюстрацию и прочитать характеристики.
- Увеличенная карта должна располагаться над соседними картами.
- Не допускать обрезания карточки границами контейнера.
- Не перекрывать важные элементы управления.
- Полный текст способности должен оставаться читаемым.
- На сенсорных устройствах предусмотреть альтернативу наведению, например выбор карты или отдельную панель подробностей.

Не создавать отдельные PNG для состояния обычного отображения и увеличения.

Кнопки действий, например «В бой» или «Редагувати», располагаются вне изображения карты, а не внутри PNG-рамки.

## 10. Индикатор способности на игровом поле

Полный текст способности не следует размещать на компактной квадратной карте техники.

Для техники со способностью предусматривается компактная постоянно видимая иконка.

Требования:

- иконка не должна заслонять важные характеристики;
- расположение должно быть согласовано с квадратной рамкой;
- стиль иконки должен соответствовать Clash Tanks;
- при наведении курсора отображается описание способности;
- на сенсорных устройствах должен существовать альтернативный способ просмотра описания.

Точный внешний вид и положение иконки необходимо окончательно согласовать на реальной квадратной рамке техники.

В качестве возможного художественного направления рассматривается небольшая золотистая иконка, напоминающая волшебную палочку или специальный эффект.

Это предварительная идея, а не окончательно утверждённый символ.

Интерфейс должен получать сведения о наличии способности и её описании из данных карты.

Не создавать отдельные ручные исключения для каждой карты без необходимости.

UI только отображает способность.

Игровое действие и его допустимость определяются серверной логикой.

**Статус: запланировано, реализация не подтверждена.**

## 11. Динамические характеристики и условные обозначения

Названия, значения характеристик, текст способности, индикаторы движения и состояния атаки должны быть отдельными элементами интерфейса.

Для характеристик использовать актуальные данные, предоставленные разрешённым состоянием игры.

Не включать динамические индикаторы в растровые иллюстрации.

Не допускать, чтобы цвет был единственным способом передачи важной игровой информации.

### 11.1. Отображение числовых значений

Утверждено единое правило для всех типов карт:

**Если характеристика существует и равна нулю, необходимо отображать `0`.**

Прочерк `–` используется только тогда, когда характеристика неприменима.

Примеры:

| Состояние | Отображение |
|---|---|
| Огневая мощь равна нулю | `0` |
| HP равны нулю | `0` |
| Топливо равно нулю | `0` |
| Характеристика неприменима | `–` |
| Для характеристики нет области в рамке | Не отображается |

Не подменять числовой ноль прочерком.

Не добавлять отдельные текстовые поля для характеристик, которые не предусмотрены композицией рамки.

### 11.2. Огневая мощь штабов

Для штабов применяется существующий принцип цветовой индикации.

Во время хода владельца используется:

`has_attacked`

Во время хода противника:

`has_counterattacked`

Если соответствующая атака или контратака ещё не использована, значение огневой мощи отображается красным.

После использования значение становится стандартного цвета.

Красный цвет не гарантирует допустимость действия.

### 11.3. Огневая мощь техники

Для техники используется аналогичный принцип:

- `has_attacked` — состояние атаки;
- `has_counterattacked` — состояние контратаки.

Значение отображается красным, если соответствующее действие ещё не использовано.

При этом необходимо учитывать текущего игрока и владельца техники.

Не вычислять допустимость атаки на основании одного цвета.

### 11.4. Условные обозначения классов техники

Утверждены пять обозначений.

| Тип техники | Код | Символ |
|---|---|---|
| Лёгкий танк (ЛТ) | `light_tank` | Ромб |
| Средний танк (СТ) | `medium_tank` | Узкий горизонтальный прямоугольник |
| Тяжёлый танк (ТТ) | `heavy_tank` | Квадрат |
| ПТ-САУ | `tank_destroyer` | Треугольник |
| САУ | `artillery` | Узкий вертикальный прямоугольник |

Символ размещается в верхнем правом круглом элементе рамки техники.

Символ должен масштабироваться средствами CSS или SVG.

Не встраивать его непосредственно в PNG.

### 11.5. Цвет символов классов техники

**Текущее утверждённое решение: все символы красные.**

В дальнейшем можно рассмотреть:

- собственная техника — зелёный;
- техника противника — красный.

Это возможное развитие интерфейса.

Не вводить разделение цветов без отдельного согласования.

### 11.6. Индикаторы движения

Индикаторы движения выполняются в виде колёс.

Расположение:

**Левая нижняя часть квадратной рамки техники, над областью огневой мощи.**

Количество колёс определяется характеристиками техники:

- лёгкий танк — два колеса при двух доступных перемещениях;
- остальные классы — одно колесо при одном доступном перемещении.

Технически количество индикаторов должно определяться значением `movement_limit`, а не только названием класса.

Использованные перемещения определяются `movement_count`.

Количество оставшихся перемещений:

`movement_limit - movement_count`

Результат не должен быть отрицательным.

### 11.7. Цвет индикаторов движения

Красный цвет означает, что соответствующее перемещение ещё не использовано.

Стандартный цвет означает, что перемещение использовано.

Для одного перемещения:

| Состояние | Индикатор |
|---|---|
| До перемещения | Красный |
| После перемещения | Стандартный |

Для двух перемещений:

| Состояние | Первый индикатор | Второй индикатор |
|---|---|---|
| До первого перемещения | Красный | Красный |
| После первого перемещения | Красный | Стандартный |
| После второго перемещения | Стандартный | Стандартный |

Красный цвет используется для доступного перемещения в соответствующую фазу хода.

Во время хода противника индикаторы движения должны иметь стандартный цвет, если правила не предусматривают иного действия.

Индикаторы не гарантируют наличие допустимого маршрута.

### 11.8. Техническая реализация колёс

Индикаторы должны быть отдельными элементами интерфейса.

Допускается использование:

- CSS;
- SVG.

Не создавать отдельные PNG для каждого состояния движения.

При изменении `movement_count` состояние колёс должно обновляться вместе с игровым интерфейсом.

### 11.9. Доступность

Не использовать цвет как единственный способ передачи важной информации.

Для интерактивных индикаторов предусматривать понятные названия или подсказки.

На сенсорных устройствах нельзя полагаться исключительно на `hover`.

## 12. Игровые эффекты и анимации

Предусматриваются визуальные эффекты для:

- выстрела;
- попадания;
- контратаки;
- повреждения техники;
- повреждения штаба;
- повреждения взводов;
- уничтожения техники;
- уничтожения взводов;
- урона от приказа;
- урона штабу при попытке взять карту из пустой колоды.

Эффекты должны соответствовать серверным событиям.

JavaScript и Stimulus отображают результат, но не определяют исход боя и не изменяют правила.

Анимации не должны мешать управлению или скрывать важные характеристики.

Следует учитывать `prefers-reduced-motion`.

### 12.1. Источники событий

Для будущих анимаций предусмотрены подробные события:

- `shot_fired`;
- `counterattack_fired`;
- `damage_applied`;
- `technique_destroyed`;
- `platoon_damaged`;
- `platoon_destroyed`;
- `empty_deck_draw_attempt`.

События должны использоваться как источник визуальных эффектов.

Не создавать отдельную клиентскую систему расчёта урона.

### 12.2. Порядок визуальных эффектов

Предполагаемая последовательность:

1. Отображение выстрела.
2. Отображение попадания.
3. Отображение нанесённого урона.
4. Обновление характеристик.
5. Отображение уничтожения, если объект уничтожен.

Для контратаки используется отдельное событие.

Окончательная последовательность анимаций должна соответствовать фактическому порядку событий Engine.

## 13. Технические требования

### 13.1. Форматы

- PNG — прозрачные рамки и многослойные графические ресурсы.
- WebP — оптимизированные растровые иллюстрации, когда формат подходит для конкретного использования.
- SVG — векторные иконки и простые масштабируемые обозначения.

Текущая утверждённая структура иллюстраций карт использует PNG.

Переход отдельных ресурсов на WebP возможен только при сохранении совместимости с системой именования и загрузки изображений.

### 13.2. Проверки перед интеграцией

- размер исходного изображения;
- соответствие пропорций утверждённому формату;
- совпадение размеров иллюстрации и рамки;
- фактическая прозрачность рамки;
- отсутствие нежелательных прозрачных полей;
- корректное взаимное расположение слоёв;
- читаемость характеристик;
- отображение на обычном и узком экране;
- отсутствие лишнего текста, водяных знаков и случайных логотипов;
- приемлемый размер файла.

Не растягивать изображения с нарушением пропорций.

### 13.3. Проверка прозрачности PNG

Для проверки можно использовать ImageMagick.

Пример:

```bash
identify -format '%f: %[channels], alpha min=%[fx:minima.a], alpha max=%[fx:maxima.a]\n' \
  app/assets/images/cards/germany/technique/germany_field_technique_border.png
```

В данном выражении значения альфа-канала нормализованы в диапазоне от `0` до `1`.

Для рамки с полностью прозрачными областями ожидается минимальное значение `0`.

Максимальное значение обычно равно `1`, если рамка содержит непрозрачные декоративные элементы.

Однако минимальное значение `0` само по себе не гарантирует правильную прозрачность центральной области.

Необходимо дополнительно проверить расположение прозрачных пикселей.

### 13.4. Propshaft и CSS

Проект использует Rails 8 и Propshaft.

Новые CSS-компоненты размещаются в:

`app/assets/stylesheets/components/`

Перед добавлением нового файла необходимо проверить существующую систему подключения CSS.

Не вводить дополнительный механизм сборки без необходимости.

После изменения ассетов при необходимости выполнять:

```bash
bin/rails assets:precompile
```

Успешная сборка не заменяет проверку результата в браузере.

Если появляется ошибка `Propshaft::MissingAssetError`, необходимо проверить:

1. Существование файла.
2. Правильность пути.
3. Подключение файла.
4. Доступность ресурса для Propshaft.
5. Состояние предварительно собранных ассетов.

Не считать предварительную сборку универсальным решением ошибок CSS.

### 13.5. Проверка в браузере

После подключения нового графического компонента проверять:

- загрузку иллюстрации;
- загрузку рамки;
- отсутствие белого фона;
- положение элементов;
- читаемость характеристик;
- правильность условных обозначений;
- обновление динамических данных;
- работу игровых действий;
- Turbo-обновления.

Структура:

```text
app/assets/images/cards/
├── germany/
│   ├── headquarters/

│   ├── order/
│   └── platoon/
├── usa/

│   └── platoon/

```

Эта структура утверждена для дальнейшей разработки.

Не создавать параллельные каталоги для тех же типов изображений без необходимости.

### 14.2. Именование иллюстраций

Формат имени:

```text
{nation}_{display}_{type}_{card_code_without_nation_and_type_prefix}.png
```

Параметры:

- `nation` — код нации;
- `display` — `field` или `card`;
- `type` — тип карты;
- последняя часть — код карты без префиксов нации и типа.

Примеры:

```text
usa_field_headquarters_second_front.png
usa_card_headquarters_second_front.png
usa_field_technique_m3_lee_grant.png
usa_card_technique_m3_lee_grant.png
usa_card_order_lend_liz.png
germany_field_headquarters_operation_weiß.png
```

Символы Unicode в кодах карт необходимо сохранять.

В частности, немецкая буква `ß` не должна заменяться или удаляться.

### 14.3. Именование рамок

Основной формат:

```text
{nation}_{display}_{type}_border.png
```

Для вариантов рамок:

```text
{nation}_{display}_{type}_{variant}_border.png
```

Примеры:

```text
usa_field_headquarters_border.png
usa_card_headquarters_border.png
germany_field_technique_border.png
germany_card_technique_border.png
usa_card_order_border.png
ussr_field_platoon_attack_border.png
ussr_field_platoon_defense_border.png
```

### 14.4. Варианты рамок

Для разных типов предусмотрены:

| Тип | Варианты |
|---|---|
| Headquarters | Обычная рамка, вариант `ability` |
| Technique | Обычная рамка, вариант `ability` |
| Order | Обычная рамка |
| Platoon | `attack`, `defense` |

Вариант выбирается по данным карты и назначению изображения.

Не выбирать вариант случайным образом.

## 15. Генерация иллюстраций

Базовое описание стиля:

> Реалистичная военно-историческая цифровая живопись для тактической карточной стратегии Clash Tanks. Правдоподобная бронетехника, сдержанная оливково-зелёная, графитовая и песочная палитра, естественное драматическое освещение, реалистичные материалы, выразительная композиция, высокая детализация. Без текста, водяных знаков и случайных логотипов.

Каждый запрос дополнительно уточняет:

- конкретный объект;
- нацию;
- исторический период;
- ракурс;
- композицию;
- формат и пропорции;
- наличие или отсутствие фона;
- необходимость прозрачности;
- назначение изображения: игровое поле или полноразмерная карта.

### 15.1. Иллюстрации техники

Основная техника должна быть хорошо различима.

Не допускать:

- случайного изменения конструкции;
- неестественных пропорций;
- чрезмерного перекрытия техники окружением;
- случайного текста;
- водяных знаков.

Историческая символика должна соответствовать изображаемой армии и периоду.

### 15.2. Иллюстрации приказов

Для приказов допускаются сюжетные композиции, показывающие:

- военные действия;
- артиллерийские удары;
- передвижение войск;
- снабжение;
- взаимодействие подразделений;
- последствия боевых действий.

Иллюстрация должна передавать смысл приказа без встроенного текста.

### 15.3. Расширение композиции

При изменении формата изображения необходимо по возможности сохранять:

- основную идею;
- цветовую палитру;
- художественный стиль;
- исторические детали;
- главный объект.

Если требуется переход к вертикальному формату, предпочтительно добавлять сюжет сверху и снизу, а не обрезать важные части исходного изображения.

### 15.4. Подготовка рамок

Рамки создаются отдельно от иллюстраций.

Для рамки необходимо заранее определить:

- расположение названия;
- расположение эмблемы;
- область иллюстрации;
- расположение характеристик;
- области индикаторов;
- необходимость области способности.

Рамка должна иметь прозрачную область для изображения.

Не создавать рамку с непрозрачным белым фоном в области иллюстрации.

## 17. Ограничения

1. Художественное оформление не меняет правила игры.
2. CSS и JavaScript не являются источником игровых решений.
3. `GameEngine` остаётся единственным арбитром игровой механики.
4. Все новые видимые надписи интерфейса должны быть на украинском языке.
5. Не встраивать динамические характеристики в изображения.
6. Не навязывать одинаковую композицию рамок разным типам карт.
7. Не создавать отдельные растровые изображения только для разных CSS-размеров.
8. Не считать концепцию реализованной без проверки.
9. Не изменять работающие компоненты без конкретной причины.
10. Не использовать непрозрачные рамки, закрывающие иллюстрации.
11. Не заменять числовой ноль прочерком.
12. Не вводить новые игровые характеристики ради оформления.
13. Не изменять Engine ради визуальных индикаторов.
14. Не создавать ручные исключения для отдельных карт, если данные позволяют использовать общий компонент.
15. Не удалять старые графические ресурсы до проверки новых.
16. Не считать успешную сборку ассетов подтверждением правильного отображения в браузере.
17. Не изменять утверждённые размеры исходных изображений без согласования.
